# 과제 0 [먼저 했다] — "한 번에 한 절씩"은 **압축 전용**이다

## 0-a. 두 줄을 직접 열어 읽은 결과

`CLAUDE.md` 를 열어 두 자리를 그대로 인용한다(실행값: `sed -n '402,403p' CLAUDE.md`,
`sed -n '405p;418,419p' CLAUDE.md`, `awk 'NR>=405 && NR<=444 && /^- /{print NR}' CLAUDE.md` → **412·413·415·418**).

```
# CLAUDE.md:402-403
**이 절을 갱신하는 규칙.** 항목을 지우지 않는다. 새 사이클에서 같은 패턴이 재발하면 근거를 **추가**한다
— 재발 횟수가 그 규칙의 무게다. 새로운 종류의 반복이 두 사이클 이상에서 관측되면 항목을 추가한다.

# CLAUDE.md:405  (불릿 넷의 머리)
**압축 규칙(architect, 2026-09-04 추가).** 위 규칙이 단조 증가만 허용해 §6 은 CLAUDE.md 의 절반을 …

# CLAUDE.md:418-419  (:405 아래 **네 번째** 불릿)
- **한 번에 한 절씩.** 리뷰어가 압축된 절을 읽고 통과시킨 뒤 다음 절로 간다 — 5회차가 가르친 대로
  "방금 이 규칙을 썼다"의 방어력은 0이고, 잡은 것은 언제나 바깥에서 읽은 리뷰어였다.
```

## 0-b. 판정 — **압축 전용이다. 모든 CLAUDE.md 편집에 걸리지 않는다.**

세 가지가 각각 독립으로 그것을 말한다.

| 근거 | 실행값·인용 |
|---|---|
| **구조** — `:418` 은 `:405` 의 소속 불릿이다 | `:405` 가 불릿 넷의 머리(`**압축 규칙 … 추가).**`)이고, `awk '/^- /'` 가 그 아래에서 내는 줄 번호는 **412·413·415·418** 넷뿐이다. `:418` 앞에 다른 `##`·`###`·굵은 머리말이 없다 |
| **문장 자신** — 대상을 스스로 한정한다 | *"리뷰어가 **압축된 절**을 읽고 통과시킨 뒤"*. "편집된 절"이 아니다 |
| **근거의 범위** — 그 불릿이 인용하는 5회차는 압축 사건이다 | 같은 불릿의 괄호가 *"(압축분: `685cbc5` = §6-3 재발 서사 … **§6-2·§6-4 는 압축하지 않는다**)"* 로 **압축분 목록**을 잇는다. 압축이 아닌 편집에는 그 목록이 받을 칸이 없다 |

반대편 `:402`(**이 절을 갱신하는 규칙**)에는 **절 제한이 없다.** 그 문장이 요구하는 것은
*"항목을 지우지 않는다 / 재발하면 근거를 **추가**한다"* 이고, 한 사이클에 몇 절을 만질지에 대해
**아무 말도 하지 않는다.**

**→ 근거를 추가하는 편집(=이 사이클의 §6-1 33·15)은 `:402` 의 규칙만 받고 `:418` 을 받지 않는다.
그러므로 이 사이클에 병행 커밋으로 들어간다.**

## 0-c. 내 잘못을 기록한다

계획 0010 §후속 25 는 *"CLAUDE.md 는 한 사이클에 한 절이고"* 라 적었고 §M-8 은 그 위에
*"대기열은 이제 25 · 32 · 33 · 34 이고 「한 사이클 한 절」 규칙에서 **네 사이클**이 걸린다"* 는
일정을 세웠다. **`:418` 을 열지 않고 그 불릿을 「모든 CLAUDE.md 편집」으로 확장한 것은 architect(나)다.**
그것은 CLAUDE.md §6-1 말미가 금지한 모양 자신이다 — *"다른 절을 가리켜 확인을 갈음하지 않는다 —

*역방향 확인 — 이 판정이 풀지 않는 것.* 압축 전용이라는 것이 **"한 사이클에 몇 절이든 만져도 된다"**

**절 단위 커밋**으로 답한다(아래 작업 7: §6-1 만 만지고 §6-3·§6-5 는 만지지 않는다). 근거는
`:415` 불릿이 요구하는 리뷰 가능성이다 — 한 커밋이 한 절만 담으면 리뷰어가 그 절만 읽고 판정한다.

# 과제 1 — 이 사이클의 범위

## 목표

**주: §후속 29 — 부분집합을 postgres 축으로 돌리면 `tests/postgres.measured.json` 이 그 부분집합의
값으로 덮인 채 남는다.** 쓰기가 바닥값 단언보다 **먼저**라서다. 이 사이클이 그것을 닫고,
**§M-9 26 의 포트 축**을 같은 파일에서 함께 답한다.

**왜 지금인가**(리뷰어 근거): 뒤의 세 사이클(**§후속 17 → 16 → 31**)이 postgres 탐침을 지금보다 훨씬
많이 돌린다. 그 전에 닫아야 비용이 준다. **이 사이클에만 세 사람이 그 부작용을 만났다** —
`qa`(계획 0010 작업 3 의 탐침) · architect(계획 0010 §M-0: *"이 마감의 `EXPLAIN` 탐침이
`tests/postgres.measured.json` 을 `tests_on_postgres: 1` 로 덮었다"*) · 리뷰어(m7 의 재측정).
**이 계획 자신이 네 번째다** — 아래 §전수 목록 A 가 그 원복 횟수를 값으로 적는다.

## 1-a. 무엇이 일어나는가 — 실행으로 갈랐다

기전은 `tests/integration/conftest.py:64-66` 세 줄이다(코드 인용):

```python
    floor = axis.read_floor()
    axis.write_measured(RECORDER, floor)   # 단언 전에 쓴다 — 실패해도 드리프트가 diff 로 보이도록
    axis.check_contract(dialect=RECORDER.dialect, tests_on_postgres=RECORDER.tests_on_postgres, floor=floor)
```

`db_axis_contract` 는 **autouse 세션 픽스처**라 `tests/integration` 의 **어떤 부분집합**을 돌려도
teardown 이 반드시 실행되고, 쓰기가 단언 앞에 있어 **바닥값 미달인 실행도 파일을 먼저 덮는다.**

**이 계획이 잰 값(N=3, 세 가지 좁힘 형태).**

| # | 좁힌 형태 | 파일에 남은 값 | 죽은 자리 |
|---|---|---|---|
| 1 | `pytest tests/integration -k test_report_line_carries_every_field_the_ci_log_needs` | `dialect: **null**` · `server_version: null` · `tests_on_postgres: **0**` · `engines: 0` | `postgres_axis.py:213` = **계약 ①(방언)** |
| 2 | `pytest tests/integration/test_20_*.py -k test_cancel_names_the_decision` | `tests_on_postgres: **1**` | `postgres_axis.py:217` = 계약 ②(바닥값) |
| 3 | `pytest tests/integration/test_20_mapping_decision_cancel.py` (**`-k`·`--deselect` 없음, 경로만**) | `tests_on_postgres: **14**` | 계약 ②(바닥값) |

**1번은 §후속 29 가 적은 것보다 나쁘다.** §후속 29 의 관측값은 *"`tests_on_postgres: 1`"* 하나였는데,
`client` 픽스처를 쓰지 않는 부분집합은 **엔진을 하나도 관측하지 않아** 파일에 `dialect: null` 을 남긴다.
그 상태로 커밋되면 **저장소가 "이 축은 postgres 위에서 돈 적이 없다"고 영구히 말한다** — 그것은
§후속 10 이 연 결함(*"축을 못 읽고 조용히 sqlite 로 떨어진다"*)을 **커밋된 파일로 기술한 것**이고,
바닥값 단언이 잡는 실패 ①과 같은 모양이다. §후속 29 는 이 갈래를 적지 않았다.

**3번이 선택지 ⓑ 의 판정 축을 가른다** — 아래 §1-b.

## 1-b. 선택지 판단 — **ⓑ 를 고르되, §후속 29 가 적은 판정 축은 기각한다**

§후속 29 가 적은 셋:

| 선택지 | 이 계획의 판정 | 근거 |
|---|---|---|
| **ⓐ** 그대로 두고 사용법을 파일 주석에 적는다 | **기각** | 주석은 **원복을 자동으로 만들지 않는다.** 이 사이클에만 네 사람이 만났고 매번 손으로 `git checkout` 했다. CLAUDE.md §6-1: *"「놓칠 수 있다」고 적는 것은 커버리지가 아니다"* — 사용법을 적는 것은 정확히 그 모양이다 |
| **ⓑ** 부분집합 실행에서는 **쓰지 않는다**(기록만) | **채택** | 아래 |
| **ⓒ** `.gitignore` 로 옮기고 CI 아티팩트로만 남긴다 | **기각(이월)** | 이것은 §후속 23 과 **같은 결정**이 된다(§후속 29 자신이 그렇게 적는다). 23 의 재개 조건은 *"`server_version` 을 읽는 자리에 단언·비교가 하나라도 생기는 순간"* 이고 아직 오지 않았다. 그리고 커밋된 파일을 지우면 **CI 아티팩트 스텝이 기대는 「커밋된 값과의 드리프트」가 사라진다**(코드 인용, `.github/workflows/buildtwin-ci.yml:167`: *"tests/postgres.measured.json 은 postgres 스텝이 덮어쓴다 — 커밋된 값과의 드리프트를 아티팩트로 남긴다"*). ⓑ 는 그 성질을 지운 채로 부작용만 없앤다 |

### ⓑ 의 판정 축을 바꾼다 — **호출 형태가 아니라 값으로 판정한다**

§후속 29 는 ⓑ 를 *"(`-k`/`--deselect` 가 있으면 기록만 하고 파일을 건드리지 않는다)"* 라고 적었다.
**그 판정 축은 오늘 실측이 반증한다** — 위 표 3번은 `-k` 도 `--deselect` 도 없이 **경로만**으로 좁혔고
`tests_on_postgres=14` 로 파일을 덮었다. 그 축을 그대로 구현하면 **오늘 일어난 세 사건 중 하나를
못 막는다.** (그리고 `-x` 조기 종료 · `--lf` · 크래시로 끊긴 실행도 같은 칸이다.)

**대신 쓰는 축: 바닥값을 만족했는가.**

```python
# tests/helpers/postgres_axis.py  (qa 소유 — 이 계획이 지정하는 것은 계약이지 구현이 아니다)
def should_write_measured(*, tests_on_postgres: int, floor: int) -> bool:
    return tests_on_postgres >= floor
```

이 축이 옳은 이유 넷:

1. **호출 형태에 무관하다.** 경로 좁힘·`-k`·`--deselect`·`-x`·`--lf`·xdist 를 **전부** 같은 칸에 넣는다.
2. **CI 는 한 글자도 달라지지 않는다.** CI 의 postgres 스텝은 `pytest tests/integration -q …`(전량)라
   `181 >= 181` 로 쓰기가 그대로 일어나고 아티팩트도 그대로다(코드 인용:
   `.github/workflows/buildtwin-ci.yml:166`).
3. **파일이 스스로 말하는 목적과 같은 축이다** — `postgres_axis.py:11` *"이 바닥값의 이름은 커버리지가
   아니라 **「조용히 줄어들지 않음」의 감시**"*. 감시가 성립하지 않는 실행의 값을 감시 파일에 쓰지 않는다.
4. **위 1번 갈래(`dialect: null`)까지 닫는다** — `0 >= 181` 이 거짓이라 쓰지 않는다.
   호출-형태 축은 이 갈래를 **`-k` 가 있을 때만** 막는다.

*역방향 확인 — 이 축이 놓치는 것 / 옛 배치가 잡던 것.* 오늘의 배치가 산 것은
*"실패해도 드리프트가 **diff** 로 보인다"* 이고, 바닥값 게이트는 그것을 **잃는다**: 통합 스위트가
**진짜로** 줄어든 전량 실행에서 파일이 안 바뀌므로 `git diff` 가 침묵한다. **잃지 않는 것**은 값 자신이다 —
`check_contract` 의 실패 메시지가 실제 수를 싣고(`postgres_axis.py:218` 코드 인용:
`f"postgres 위에서 SQL 을 실행한 테스트가 {tests_on_postgres}건으로 바닥값 {floor} 미만이다"`),
`[db-axis]` 줄이 **초록·빨강·teardown ERROR 어느 쪽에서든** 찍힌다(`conftest.py:69-85` 의 근거 주석).
**그러므로 ⓑ 는 「보이는 자리」를 diff 에서 로그로 옮기는 것이고, 없애는 것이 아니다** — 그리고 그것이
ⓑ 의 이름이 *"기록만"* 인 이유다. 이 맞바꿈을 **완료 조건에 값으로 박는다**(아래 작업 3 조건 4).

*역방향 확인 — 값이 **오르는** 경우.* 통합이 늘어 `tests_on_postgres=200` 이 되면 `200 >= 181` 이라
쓰기가 일어나고 파일이 200 을 싣는다 → 커밋된 181 과의 **diff 가 보인다**. 즉 게이트는
*"따라오지 않는 것"*(`postgres_axis.py:15-16` 이 적은 한계)을 **더 잘 보이게** 한다. 이 방향은 잃지 않는다.

## 1-c. §M-9 26 — 포트가 공유 자원인가. **쟀다: 스키마 격리는 성립한다**

§M-9 26 이 남긴 것: *"두 에이전트가 같은 URL 을 쓰면 같은 스키마 이름 공간을 나눠 쓴다 — 세션 전용
스키마가 그것을 막는지는 재지 않았다."*

**이 계획이 쟀다.** 같은 URL(`…@127.0.0.1:55434/buildtwin`)에 대해 **서로 다른 두 통합 파일을 동시에**
띄우고 3회 반복했다.

| 회차 | A `test_20_mapping_decision_cancel.py` | B `test_19_rejection_reason.py` | 남은 스키마 |
|---|---|---|---|
| 1 | **14 passed**, FAILED 0 | **8 passed**, FAILED 0 | — |
| 2 | **14 passed**, FAILED 0 | **8 passed**, FAILED 0 | — |
| 3 | **14 passed**, FAILED 0 | **8 passed**, FAILED 0 | — |
| 끝 | 각 실행의 유일한 ERROR 는 **teardown 바닥값**(= §후속 29 의 그 부작용) | 같음 | `select count(*) from pg_namespace where nspname like 'bt_test_%'` → **0** |

**판정.** 이름은 `bt_test_{os.getpid()}_{secrets.token_hex(4)}`(코드 인용,
`postgres_axis.py:74-76`)라 **pid + 32비트 난수**로 갈리고, `drop_schema` 는
*"데이터베이스가 아니라 **스키마만** 지운다"*(`postgres_axis.py:93-95`). 3/3 에서 교차 실패 **0건**,
누수 스키마 **0개**. **→ 같은 URL·같은 포트를 두 에이전트가 나눠 써도 DB 쪽은 안전하다.**

**그러면 실제로 부딪히는 공유 자원은 DB 가 아니라 `tests/postgres.measured.json` 하나다** — 위
동시 실행에서 **두 프로세스가 같은 저장소 파일을 각각 덮었고 마지막 쓰기가 이겼다**(코드 인용:
`conftest.py:65` 의 무조건 `axis.write_measured(...)` 는 프로세스 간 어떤 잠금도 쓰지 않는다).
**작업 3 이 그 경합까지 함께 지운다** — 탐침 두 개가 동시에 돌아도 둘 다 바닥값 미달이라 아무도 쓰지 않는다.

> **그래서 §M-9 26 은 이 사이클에 닫힌다**(포트는 **관례**로만 남는다: 자기 포트를 계획 §0 에 적는다).
> 닫지 **않는** 것: *"CI 서비스 컨테이너에서도 같은가"* — CI 는 한 잡에 한 실행이라 동시성이 없고,
> 이 계획은 CI 에서 아무것도 재지 않았다(§확인하지 않은 것 1).

## 1-e. §후속 35 (m7) — **라벨과 인덱스 이름이 틀렸다. 결론·계약·코드는 옳다**

> ### ⚠ 이 절의 1차 판정(*"재현되지 않는다"*)은 **반증됐다**(2026-09-07 리뷰 M1).
> 아래 §1-e-2 가 정정이고, **§1-e-1 은 무엇을 어떻게 잘못 셌는지의 기록으로 남긴다** — 지우면

#### 1-e-1. 1차 판정과 그 근거 (반증됐다 — 기록으로 남긴다)

리뷰어가 배역의 ORM 문장을 `literal_binds` 로 컴파일해 세 번 재니 전부
`ix_review_requests_project_id` 였다. 이 계획이 저장소 밖 플러그인으로 배역의 **실제 실행 문장**에
`EXPLAIN` 을 걸어 **59/59** 를 재고 같은 결론을 냈다(`711e12f`, 포트 55434).

| 잰 것 | N | 계획 |
|---|---|---|
| **배역의 문장이라고 **믿은** 것** | **59/59**(한 세션) | `Index Scan using **ix_review_requests_project_id**  (cost=0.14..8.17)` · `Index Cond: project_id = 'p-…'` · **`Filter: (status AND kind AND activity_id)`** ← **이 `status` 가 반증의 열쇠였다** |
| `activity_id` 술어를 뺀다(`project_id` 상수) | 1 | `ix_review_requests_project_id` (cost 0.14..8.16) |
| `project_id` 를 비상수로(`PREPARE`+7회차 generic plan) | 1 | `ix_review_requests_project_id` |
| 세 술어 전부 비상수(generic plan, 7회차) | 1 | `ix_review_requests_project_id` (cost 0.14..8.17) |
| `project_id` 술어를 뺀다 | 1 | `ix_review_requests_kind` (cost 0.14..8.16) |
| `kind` 만 | 1 | `ix_review_requests_kind` (cost 0.14..8.16) |

거기서 내린 결론 — *"갈리는 조건은 `project_id` 술어의 유무 하나뿐이고 `kind` 인덱스는 배역에서
재현되지 않는다"* — 은 **거짓이다.**

#### 1-e-2. 정정 — **재현된다. 같은 문장이 세션마다 다른 btree 로 간다**

**무엇이 틀렸나(§후속 34 의 다섯 번째 실례 — "무엇을 어떻게 셌나").** 위 59 는 문장을 **텍스트로**
걸러 센 값이다. `activity_id` 는 **SELECT 컬럼 목록에도** 있어서, 배역의 세-술어 조회 말고
**`status` 를 포함한 네-술어 문장**(`_sync_pending_document_mapping_reviews` 계열)까지 함께 잡혔다.
**리뷰어의 첫 시도도 같은 함정에 빠졌다.**

**`WHERE` 절의 술어 집합으로 갈라 다시 셌다**(architect 재측정, 잰 트리 `68b5795`, **포트 55437**,
저장소 밖 플러그인 `predicate_probe.py`). 한 세션의 분해:

| `WHERE` 술어 집합 | 히트 |
|---|---|
| `project_id`+`kind`+`activity_id` — **배역의 문장** | **12** |
| `project_id`+`kind`+`activity_id`+**`status`** | **47** |
| **합** | **59** ← 1차 판정의 59 가 정확히 이 둘의 합이다 |

**세션을 축으로 다시 쟀다.** 배역의 세-술어 문장만, 세션당 12회씩:

| 배치 | N(세션) | `ix_review_requests_kind` | `ix_review_requests_project_id` | 세션 내 일관성 |
|---|---|---|---|---|
| 1 | 10 | **6** | **4** | 모든 세션 12/12 동일 |
| 2(비용 포착) | 6 | 2 | 4 | 모든 세션 12/12 동일 |
| 3(OID 포착) | 6 | 4 | 2 | 모든 세션 12/12 동일 |
| **합** | **22** | **12** | **10** | **22/22 세션이 세션 내 12/12 동일**, `Seq Scan` **0** |

**배치 1 은 리뷰어의 6/10 ↔ 4/10 과 정확히 같다**(리뷰어는 `68b5795`·포트 55436, 나는 포트 55437).
**`qa` 는 같은 트리·포트 55435 에서 5/10 을 쟀다**(`3dddf58` 의 그 docstring). **세 측정이 갈리는 것이
정상이다** — 세션마다 뽑는 동전이고, 셋이 일치하는 것은 비율이 아니라 ① 두 계획이 다 나온다
② 비용이 `cost=0.14..8.17` 로 똑같다 ③ 세션 내 일관성 ④ `status` 인덱스·`Seq Scan` 0 이다.
**그러므로 어느 문서도 비율을 계약처럼 적지 않는다.**

**두 인덱스의 비용은 같다.** 배치 2 의 실행값: 고른 인덱스가 `kind` 든 `project_id` 든
**`cost=0.14..8.17` 로 동일**하다. 그러므로 결정하는 것은 **선호가 아니라 동률 타이브레이크**다.

**타이브레이크의 축(N=6, 배치 3).** 두 인덱스 중 **OID 가 큰 쪽**이 **6/6** 에서 선택됐다. 세션마다
스키마를 새로 만들어 두 인덱스의 OID 순서가 뒤집히고, 그때 선택도 따라 뒤집혔다:

| 세션 | OID 순서 | 고른 것 |
|---|---|---|
| 1 | `project_id` 27905 < `kind` **27907** | **kind** |
| 2 | `project_id` 28250 < `kind` **28252** | **kind** |
| 3 | `project_id` 28595 < `kind` **28597** | **kind** |
| 4 | `kind` 28940 < `project_id` **28942** | **project_id** |
| 5 | `kind` 29285 < `project_id` **29287** | **project_id** |
| 6 | `project_id` 29630 < `kind` **29632** | **kind** |

*한정*: N=6 의 **상관**이고 기전이 아니다. **OID 순서가 왜 세션마다 다른지는 재지 않았다** —
ADR 0015 §Deferred 6 으로 열었다.

**결함은 없다. 그리고 결론은 오히려 강해진다.** ADR 0015 §2-1 이 *"기대는 대상은 **어떤 특정
인덱스**가 아니라 「플래너가 고르는 btree 가 중복을 heap TID 로 담는다」는 성질"* 로 일반화한 것이
이제 **같은 문장·같은 비용에서 세션마다 갈린다**는 실측으로 뒷받침된다. `Seq Scan` 은 22세션 어디에도
없다. 고칠 것은 **라벨과 이름** 둘이고, 고치는 방향은 *"인덱스 이름을 다른 이름으로 바꾼다"* 가
아니라 **"이름에 기대지 않는 문구로 바꾼다"** 다.

- `test_20` 의 그 docstring → *"서 있는 자리는 **플래너가 고르는 그 btree**"*, 그리고 **한 인덱스
  이름을 계약처럼 적지 않는다**(`qa` 소유 · 작업 5).
- ADR 0015 §2-1 표 1행 → *"재현된다. 다만 세션마다 갈린다(kind 6/10 ↔ project_id 4/10, 비용 동일)"*.

> **1차 판정이 왜 반증됐는지가 이 사이클의 교훈이다.** 나는 N 을 **59** 라고 적었지만 그 59 는
> **세션 1개**의 값이었고, 게다가 **두 문장의 합**이었다. §후속 27(N 을 함께 적는다)을 지켰는데도
> 틀린 이유는 **N 의 단위가 「히트」였기 때문**이다 — 갈리는 축은 세션이었다.
> **N 을 적을 때 「무엇의 N 인가」를 함께 적는다.** 이것을 §후속 34 의 다섯 번째 실례로 등록한다.

*역방향 확인 — 이 정정이 지우면 안 되는 것.* 표 1행을 **지우지 않는다.** 그 행이 있어야 §2-1 의
*"두 실행이 서로 다른 인덱스를 골랐다"* 가 무엇을 근거로 한 문장인지 보이고, 그 문장이 만든 결론
(*"특정 인덱스가 아니라 그 성질"*)은 **정정 뒤에도 참**이다 — 오늘은 **조건이 아니라 세션**에 따라
갈린다는 것이 더해졌을 뿐이다. **§1-e-1 도 지우지 않는다**(같은 이유의 한 층 아래: 반증된 판정을
지우면 *왜* 반증됐는지가 사라지고, 이 사이클이 배운 것의 전부가 거기 있다).
지우면 옳은 결론이 근거를 잃는다(CLAUDE.md §6-5 *"항목을 지우지 않는다"* 와 같은 판단).

## 1-f. §후속 36 (m8) — **못박음을 좁힌 것이 부작용을 냈다**

ADR 0015 §0 초판: *"이 문서의 **모든** `파일:줄`·커밋 참조는 HEAD `743bcb9` 트리의 것이다."*
계획 0010 의 M1 처분이 그것을 *"이 문서의 **§0~§1** 의 모든 …"* 으로 좁혔다(코드 인용, ADR 0015:26).
**그래서 §2 이하의 참조가 어느 못박음에도 안 걸린다.** 전수(이 계획이 루트에서 다시 세었다):

| ADR 줄 | 참조 | 어느 트리의 값인가 | HEAD `711e12f` 실측 |
|---|---|---|---|
| §2-1 :167 | `test_20:269` · `:278-281` | `f6ad00e`(M1·m6 이 나중에 쓴 자리) | `:269` = *"이것도 보장은 아니다"* **일치**. `:278-281` = EXPLAIN 값 **일치**(그러나 그 값 자신이 §후속 35 로 틀렸다) |
| §2-2 :172 | `test_20:865` | `743bcb9` | HEAD 에서는 **`:935`** |
| §3 :207 | `persistence.py:480` | `743bcb9` | **두 트리 동일**(`return sorted(rows, key=lambda r: r.created_at)`) |
| §4 :248 | `test_document_mapping_review_lifecycle.py:282-285` | `743bcb9`(= `_plant_row_at_end_of_scan`, 그 트리 `:282`) | HEAD 의 `:282-285` 는 **다른 구역**이다(그 헬퍼는 오늘 `:307` `_make_scan_order_disagree_with_created_at`). **줄 번호만 낡았다 — 그 행의 주장(*"이름까지 같은"*)은 오늘도 참이다**: `f6ad00e` 가 단위·통합 **양쪽을 함께** 개명해 오늘도 이름이 같다(통합 `:254`) |
| §5 :266 | `persistence.py:475-480` | `743bcb9` | **두 트리 동일**(`diff` 출력 없음 — IDENTICAL) |
| §5 :269 | `test_20:865-866` | `743bcb9` | HEAD 에서는 `assert` **`:935`** + 메시지 **`:936-937`**(두 줄이 세 줄이 됐다) |

> **지시받은 값과 갈린 두 자리를 먼저 적는다.** ① *"`test_20:865-866` 은 HEAD 에서 `:935-936`"* —
> 실측은 `:935`(assert) + `:936-937`(메시지 두 줄)이라 **`:935-937`** 이다(`f6ad00e` 가 메시지에 힙
> 진단을 실으며 한 줄이 두 줄이 됐다). ② *"§2-1 의 `persistence.py:475-480`"* — 그 참조는 **§5 의 표
> 1행**에 있다(그 행이 다루는 **대상**이 §2-1 일 뿐이다). 그리고 **못박히지 않은 자리는 둘이 아니라
> 다섯이다**(§2-2 · §3 · §4 · §5 ×2). 그중 **§4 :248 은 m8 도 리뷰어도 이름 붙이지 않은 자리**이고,
> 유일하게 **줄 번호가 오늘 다른 구역을 가리킨다**.
>
> *역방향 확인 — 그렇다고 그 행이 거짓인 것은 아니다(처음에 나는 그렇게 적었고 실행이 그것을 고쳤다).*
> 그 행의 주장은 *"단위 짝이 **이름까지 같은** 심기를 갖는다"* 인데, `f6ad00e` 가 단위·통합 **양쪽을
> 함께** `_make_scan_order_disagree_with_created_at` 로 개명했으므로 **이름이 같다는 사실은 오늘도
> 참이다**(실행값: 단위 `:307` · 통합 `:254`). **낡은 것은 줄 번호 하나뿐**이다. 이 칸을
> *"문장이 거짓이 됐다"* 로 적었다가 `grep -n "^def _"` 로 갈랐다 — §6-3 이 요구하는 것이 정확히
> 이것이다(한정어를 세운 뒤 **실행으로 태운다**).

**고칠 방향(m8 이 적은 그대로, 범위만 실측대로 넓힌다).** 좁히지 말고 **전체를 못박고 예외를 적는다**:

> 이 문서의 **모든** `파일:줄`·커밋 참조는 HEAD `743bcb9` 트리의 것이다. **다만 아래 자리는 2026-09-07
> 리뷰 처분(M1·m6)과 계획 0011 로 나중에 편집됐고 각각 `f6ad00e`·`e6fa92f`·`711e12f` 를 인용한다:
> §2-1 의 「착지로」 역방향 확인(`f6ad00e`) · §3 완료 조건 3 의 절대값(`e6fa92f`) · §2-1 표 1행의
> 정정(`711e12f`, 계획 0011 §후속 35).** 그리고 **`743bcb9` 에 못박힌 참조 중 그 뒤 트리에서 자리가
> 옮겨진 것**은 다음 셋이다(값은 참이고 자리만 옮겼다 — 갱신하지 않는다, §3-13 첫째 갈래):
> §2-2 `test_20:865` → `711e12f` 의 `:935`, §5 `test_20:865-866` → `:935-937`,
> §4 `test_lifecycle.py:282-285` → **HEAD 에서 다른 것을 가리킨다**(그 심기 헬퍼는 `f6ad00e` 가 이름을
> 바꿨다 — 자리 대신 **심볼**로 읽는다).

*역방향 확인 — 왜 §4 :248 만 심볼로 바꾸는가.* §3-13 첫째 갈래는 *"HEAD 가 움직였다고 뒤늦게
갱신하지 않는다"* 이고, 그것이 지키는 것은 **"보고하는 실측과 인용 트리가 어긋나지 않는 것"** 이다.
§2-2·§5 의 `test_20:865` 는 그 트리에서 **참이었고 지금도 그 트리에서 참**이라 못박음 하나로 족하다.
§4 :248 은 다르다 — 그것이 말하는 것은 *"오늘의 단위 짝이 이름까지 같은 심기를 갖는다"* 로
**현재형 주장**이고, `f6ad00e` 가 그 이름을 바꿔 **문장 자신이 거짓이 됐다**(§6-4 1: 사실과 다른 문구는
그것을 만든 사이클이 고친다 — 그 사이클이 놓쳤으므로 이 사이클이 고친다). 자리를 갱신하는 것이 아니라
**주장을 오늘의 사실로** 고치는 것이다.

## 1-g. CLAUDE.md §6-1 커밋 (33 + 15) — 과제 0 판정에 따라 **병행**

**한 커밋에 §6-1 만 담는다.** 두 항목 모두 **근거 추가**(`:402`)이고 규칙 문장은 건드리지 않는다.

- **33** — §6-1 의 *역방향 확인* 불릿(`CLAUDE.md:254-259`)이 세는 **표기 집합**에 **보간**
  (f-문자열·`.format`·문자열 결합)을 더한다. 세 번째 관측이다: `moved=9` 의 표기 변종(1) ·
  ADR 0013 규칙 9 의 활용형·동의어(2, §6-1 표 11회차) · 계획 0010 §M-2-2 의 f-문자열(3).
  **밀려난 것**: 계획 0010 목록 A ②는 *"영어 표기"*·*"말하지 않고 기대는 자리"* 를 적었는데
  **보간은 그 셋 어디에도 없었다.**
- **15** — §6-1 **12회차 행**의 *"밀려난 것"*·*"관측값"* 칸을 넓힌다. 표본이 **2 → 3** 이다:
  계획 0007(§후속 8·5) + **계획 0010(§후속 12·13)**. 그리고 이 사이클이 더하는 새 사실 둘 —
  ① 계획 0010 은 **열린 항목을 전부 재측정하고도**(그 계획 §전수 목록 B) 12·13 을 놓쳤다 →
  *"재측정 시점"* 기준에는 **"재측정 뒤 같은 사이클의 커밋"** 칸이 없다.
  ② **그 행이 처음으로 읽혀서 작동했다** — `qa` 가 커밋 본문에 *"다음 이월 목록이 12 를 「열림」으로
  옮기면 §6-1 12회차의 재발이다"* 라 적어 넘겼고 리뷰어가 13 을 잡았다(계획 0010 §M-3).
  **행을 넓히는 것보다 읽히는 것이 먼저 필요했다** — 그 관측을 관측값 칸에 남긴다.

*역방향 확인 — 33·15 를 한 커밋에 담는 것이 §6-5 를 어기는가.* 아니다. `:418` 은 **압축**에만 걸리고
(§0-b), `:402` 는 절 수를 말하지 않는다. 이 커밋이 지키는 것은 `:415` 가 요구하는 **리뷰 가능성**이다 —
한 커밋 = 한 절이라 리뷰어가 §6-1 만 읽고 판정한다. §6-3(32)·§6-5(25·27·34)는 **만지지 않는다.**

### 작업 3 완료 조건 (여섯 칸 — **전부** 만족해야 한다)

1. **부분집합이 파일을 안 건드린다.** 위 §1-a 표의 **세 형태 전부**(`-k` · 경로+`-k` · **경로만**)에서
   실행 전후 `tests/postgres.measured.json` 의 바이트가 같다.
2. **전량은 그대로 쓴다.** 파일을 **실측과 다른 센티널**로 덮은 뒤 전량을 돌리면 실측값으로 **바뀐다**
   (센티널 없이는 "쓴다"와 "안 쓴다"가 같은 바이트를 낳아 구별되지 않는다 — §6-2 1).
3. **판정 축이 값이지 호출 형태가 아니다.** `-k`·`--deselect`·`sys.argv`·`config.option` 을 읽는
   코드가 **하나도 없다**(루트 실행값으로 확인: `grep -rn "deselect\|config.option\|testscollected" tests/`
   가 오늘의 히트(문서·docstring)를 넘지 않는다).
4. **잃은 것을 값으로 붙든다.** 바닥값 미달 실행에서 ⓐ teardown 이 **여전히 빨갛다** ⓑ 실패 메시지가
   실제 `tests_on_postgres` 수를 싣는다 ⓒ `[db-axis]` 줄이 **찍힌다**. 셋을 각각 단언한다
   (§6-2 2·4 — "쓰지 않았다"만 보면 쓰기를 통째로 지운 구현이 그대로 통과한다).
5. **문구가 사실과 같아진다.** `measured_report` 의 `_comment`(`postgres_axis.py:160-167`)가
   *"부분집합을 postgres 축으로 돌리면 이 파일이 그 부분집합의 값으로 덮인 채 남는다"* 라고 적는데
   이 작업이 그것을 거짓으로 만든다 → **같은 커밋에서** 고친다(§6-4 1). `postgres_axis.py` 머리
   docstring 의 한계 문단도 같다.
6. **포트 축을 같은 파일에 적는다.** `postgres_axis.py` 머리에 §1-c 의 실측(동시 3/3 · 누수 스키마 0 ·
   이름 규약 `bt_test_{pid}_{token_hex(4)}`)과 그 결론(*"같은 URL 을 나눠 써도 스키마는 안전하고,
   부딪히던 것은 이 측정 파일이었다"*)을 적는다. **N 과 재는 법을 함께 적는다**(§후속 34 를 손으로 적용).

> **작업 3 이 부딪힐 자리를 미리 적는다(qa 가 늦게 발견하지 않도록).** `test_99` 의 자식 프로세스

## 검증 시나리오 (§6-2 — 각 시나리오에 **"결함 있는 코드가 이 기대값을 그대로 만족하는가"** 를 물었다)

**결함 코드 후보 셋을 먼저 이름 붙인다** — 시나리오는 이 셋을 **각각** 죽여야 한다.

- **D1** 게이트를 **항상 `True`** 로(= `should_write_measured` 가 늘 참 → **늘 쓴다** = 오늘과 같다).
- **D2** 게이트를 **항상 `False`** 로(= 늘 거짓 → **아무 때도 안 쓴다**).

> **초판은 이 둘의 리터럴이 뒤집혀 있었다**(2026-09-07 리뷰 m2). `should_write_measured` 는
> **`True` 가 "쓴다"** 인데 D1 을 *"항상 `False` 로(= 늘 쓴다)"* 라 적었다. 리뷰어 실측: `return False`
> 를 넣으면 S1 이 지목한 두 시나리오가 **둘 다 초록**이고 죽는 것은 전량 쪽이다 — 즉 뒤집힌 표대로
> 변이를 태우면 *"테스트가 안 잡는다"* 는 **잘못된 결론**에 닿는다. 이 계획이 만든 거짓 문장이고,
> 그것을 만든 사이클이 고친다(§6-4 1). 같은 뒤집힘이 `test_99` 의 변이↔테스트 표에도 갔고
> 그쪽은 `qa` 가 고친다(소유).
- **D3** 게이트는 옳으나 **`check_contract` 호출까지 함께 게이트**했다(= 부분집합이 **초록**이 된다).

## 열린 질문 / 리스크

1. **바닥값 게이트가 「진짜 축소」의 diff 를 지운다.** 완화: 실패 메시지 + `[db-axis]` 줄(위 §6-3 표
   2행). **닫지 않는다** — 맞바꿈이고, 그 사실을 `postgres_axis.py` 머리에 적는 것이 작업 3 조건 5 다.
2. **전량 둘을 동시에 돌리면 여전히 둘 다 쓴다.** 이 계획은 재지 않았고 닫지 않는다(§확인하지 않은 것 4).
   위험은 낮다 — 두 전량이 같은 값을 쓰므로 결과 바이트가 같다(**단, `server_version` 이 다르면 갈린다**).
3. **작업 5 가 작업 4 와 같은 파일이다.** 한 커밋으로 묶으면 리뷰어가 두 축을 한 번에 읽어야 한다.
   완화: 커밋 본문에 축 둘을 적는다(§2 커밋 규칙의 정신). **소유가 같으므로 §2 위반은 아니다.**
4. **작업 7 이 §6 의 자수를 늘린다** — §6-5 가 이름 붙인 **불안전한 방향**(분모가 못박힌 15,148 위)이
   더 커진다. 이 사이클은 압축하지 않으므로 **값만 적어 두고**(§0-f) §6-5 사이클에 넘긴다.
5. **`test_99` 자식 기구와의 충돌을 코드로만 판정했다**(§작업 3 상자). 실행으로 확인하는 것은 작업 3 이다.

## ADR 필요 여부

**필요 없다.** 이 사이클이 바꾸는 것은 **ADR 0014 §2-5 계약의 「언제 쓰는가」** 하나이고, 계약 셋

단언보다 먼저"* 는 그 ADR 의 **결정**이 아니라 **구현 서술**이다(그 자리는 `conftest.py` 다).

다시 열어야 한다. **ⓑ 는 그 성질을 지키므로 ADR 을 열지 않는다.** ADR 0015 는 **정정만** 받는다
(작업 2 — 새 결정 없음).

## M-2. 계획이 틀린 자리 — **주 판정 하나가 반증됐고, 원인은 「무엇을 셌나」였다**

### M-2-1. §후속 35 의 판정이 거짓이었다 (리뷰 M1, major)

계획 §1-e 는 *"`ix_review_requests_kind` 는 배역에서 **재현되지 않는다**"* 로 판정했고 ADR 0015
§2-1 표 1행을 그렇게 고쳤다. **거짓이다.** 정정과 그 실측은 **§1-e-2** 에 있다. 요지 셋:

1. **재현된다** — 같은 세-술어 문장이 세션마다 다른 btree 를 고른다(독립 측정 셋: qa 5/10 ·
   리뷰어 6/10 · architect 6/10, 전부 `68b5795`).
2. **두 계획의 비용이 같다**(`cost=0.14..8.17`). 그래서 선택은 선호가 아니라 **동률 타이브레이크**다.
   *이것은 세 사람 중 아무도 1차에 재지 않은 값이고, 재고 나니 결론이 뒤집힌 게 아니라 강해졌다.*
3. **내 59/59 는 두 문장의 합이었다** — 술어 집합으로 가르니 **12(세-술어) + 47(네-술어, `status`
   포함) = 59**. `activity_id` 가 **SELECT 컬럼 목록에도** 있어 텍스트 필터가 남의 문장을 잡았다.

**왜 §6-1·§6-3 을 지키고도 틀렸나 — 이 사이클의 진짜 교훈.** 나는 §후속 27 이 요구하는 대로
**N 을 적었다**(*"59/59"*). 그런데도 틀렸다. **N 의 단위가 「히트」였기 때문**이고, 갈리는 축은
**세션**이었다. 그리고 그 59 는 **한 세션**의 값이라 세션 표본은 **1** 이었다.
→ **§후속 34 의 다섯 번째 실례**이고, 그 항목에 **"N 을 적을 때 「무엇의 N 인가」를 함께 적는다"**
를 더한다(§후속 34 참조).

*이 자리가 §6-1 ②를 정확히 재연한다*: 목록의 생성 기준(= 문장을 고르는 필터)이 곧 목록의 한계였고,
**밀려난 것은 「내가 잰 것이 내가 재려던 것인가」** 였다. 계획 §전수 목록 A ②는 *"측정 파일 표면"* 의
블라인드 스팟은 적었지만 **탐침 자신의 필터**에는 §6-1 을 걸지 않았다.

    47회를 함께 잡아 판정을 뒤집었다. **규약의 자리는 CLAUDE.md 이고 §6-1 이며, 순서는
    25 → 32 → 33(닫힘) → 34 뒤다.** 그때까지는 계획마다 손으로 적는다.

## M-5. 확인하지 않은 것 (본문 1~28 을 번호로 옮기고, 이 마감이 처분한 것만 적는다)
