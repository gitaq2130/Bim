## Context

### 1. 하나의 문자열이 두 가지 일을 하고 있다

`Document.title_normalized` 는 두 역할을 겸한다.

- **식별**: `doc_id = "doc-" + sha256("{doc_type}|{sender_normalized}|{seq_normalized}|{title_normalized}")[:16]`
  (ADR 0007 §2-1)의 네 번째 재료.
- **대조**: 문서 제목 ↔ Activity 이름 유사도 매칭(§4-2 규칙 1)의 입력.

그리고 두 역할이 **같은 config 블록** 하나를 읽는다.

```
services/progress/importers/document_register.py:431
    title_normalize_cfg = cfg.get("title_matching", {}).get("normalize", {})
                               └─ 매칭 튜닝용 블록 ─┘
:311  title_normalized = _title_normalized(title_val, title_normalize_cfg)
:347  doc_id = _compute_doc_id(doc_type, sender_normalized, seq_normalized, title_normalized)
```

**이 튜닝은 반드시 일어난다.** `config/document_register.yaml` 의 `min_similarity: 0.22` 는 그 주석이 스스로
"합성 픽스처 6쌍으로만 잰 것이라 아직 보정되지 않았다. 실제 대장·공정표가 들어오면 반드시 다시 잰다"고
적어 두었고, 임계를 다시 재는 사람은 같은 블록의 `normalize` 도 함께 만진다(같은 절, 같은 화면, 같은 목적).

```
   open      doc=doc-fa3357c8c57fd080 note=None
   rejected  doc=doc-e2dfc7f22b37f1a9 note='CM 반려: 이 문서는 이 작업과 무관하다'

A100 readiness: 1.0 → 0.9249999999999999
  components after : {..., "drawing_approval": 0.5, ...}
  blockers after   : [{"component": "drawing_approval", "reason": "문서 매핑 1건이 CM 검토 대기 — 확정 전까지
                       도면 승인 근거로 쓰지 않음", "related_ids": ["doc-6a0dd6596625abb1"], ...}]
```

네 가지가 동시에 일어났고, 넷 다 예상대로였다.

1. **적재된 문서 10건 중 6건이 새 문서가 되고 옛 6건은 고아가 됐다.** 대장은 바뀌지 않았다.
2. **CM 이 확정한 매핑(A100)이 고아 문서를 가리키게 됐다.** 확정 행 자체는 남지만
   `confirmed_required_documents` 가 `ignore_orphaned_documents`(§5-2 규칙 6)로 걸러내므로 **증거로서는 사라졌다.**
   같은 Activity 에 새 doc_id 로 미확정 후보가 다시 열렸다.
3. **반려의 영구성이 깨졌다(ADR 0007 §4-2 규칙 6 ⑥ 위반).** A400 에는 제목이 **글자 하나까지 똑같은**
   문서가 "CM 이 반려한 것"과 "새로 검토해 달라는 것" 두 개로 동시에 존재한다. `_drop_already_confirmed` 는
   옛 `(activity_id, doc_id)` 쌍을 보고 있는데 새 후보는 새 `doc_id` 라 그 필터를 그대로 통과한다.
4. **readiness 의 도면 승인 근거가 무너졌다.** `drawing_approval` 1.0 → 0.5, 총점 1.0 → 0.925.
   착수 가능 판단의 15%가 config 한 줄에 움직였다.

**그리고 이 전부가 조용하다.** job 은 `done`, 예외 없음, `/startable` 200, 화면 정상. 유일한 신호인
`document_possibly_renamed` 경고는 **사실과 다른 말을 한다** — 제목은 전혀 바뀌지 않았는데 메시지는
"제목만 다르고 (종류·발신·번호)가 같은 기존 문서가 있음"이라고 적는다.

```
document_possibly_renamed [TFA#4]: 제목만 다르고 (종류·발신·번호)가 같은 기존 문서가 있음 — 자동 병합하지 않음
  (new_doc_id=doc-6a0dd6596625abb1, previous_doc_id=doc-ca45b33c16825a28,
   doc_number='동부-HG-TFA-구조-26-049', title='시공상세도 승인요청 - 1F 기둥 배근도 (Z1)')
```

### 2-1. 세 가지 튜닝의 폭발 반경(픽스처 10건 기준, 파서 직접 실측)

| 튜닝 | `doc_id` 변경 |
|---|---|
| baseline | 0/10 |
| `strip_patterns` 에 `"승인요청"` 추가 | **6/10** |
| `strip_chars` 에서 괄호 제거 | **7/10** |
| `lowercase: false` | **9/10** |
| `min_similarity` 0.22 → 0.30 (정규화는 안 건드림) | 0/10 |

마지막 줄이 함정이다. 임계값만 만지면 아무 일도 없으므로 "매칭 설정을 바꿔도 괜찮더라"는 잘못된 학습이
먼저 일어나고, 그 다음에 정규화를 만진다.

### 3. 두 실패 모드는 대칭이 아니다 (실측)

정체성 규칙이 틀리는 방향은 둘뿐이고, 결과가 전혀 다르다.

**(가) 분리(split) — 보수적으로 틀렸을 때.** 같은 문서가 두 `doc_id` 를 얻는다. 위 §2 가 그 모습이다.
행이 남고, 고아 표시가 붙고, 경고가 뜨고, 검토요청이 다시 열린다. **관측 가능하고 되돌릴 수 있다.**

**(나) 병합(merge) — 공격적으로 틀렸을 때.** 서로 다른 두 문서가 한 `doc_id` 를 갖는다. 재현했다.
반려 후 재제출이라 같은 `번호` 아래 1차·2차 두 행이 있는 대장(현장에서 흔하다)에, 매칭 담당자가
`strip_patterns` 에 `\d+\s*차` 를 추가한다 — `discriminative_tokens` 에 이미 `revision` 규칙이 있으니
"차수는 유사도 텍스트에서 지워도 판별에는 영향 없다"는 **매칭 관점에서는 옳은 튜닝**이다.

```
--- 현재 config (차수를 지우지 않음) ---
  문서 11건 → doc_id 유니크 11건 (충돌 0건)

--- 차수 제거 튜닝 후 (strip_patterns += '\d+\s*차') ---
  문서 11건 → doc_id 유니크 10건 (충돌 1건)
  *** 같은 doc_id doc-ca45b33c16825a28 를 공유하는 2건:
        '시공상세도 승인요청 - 1F 기둥 배근도 (Z1) 1차'  승인상태=REJECTED
        '시공상세도 승인요청 - 1F 기둥 배근도 (Z1) 2차'  승인상태=APPROVED
```

TestClient 로 끝까지 태우면(두 행의 `문서번호` 를 다르게 둬 `duplicate_doc_number` 경고가 뜨지 않게 했다):

```
job: done {"document_count": 11, "created": 1, "updated": 10, "orphaned": 2, ...}
warnings:
   - doc_number_mismatch [TFA#8]: ...
   - header_row_not_found [NCR]: ...
   - document_possibly_renamed [TFA#4]: ... (new_doc_id=doc-ca45b33c16825a28, previous_doc_id=doc-ab0aaac7becb0504 ...
   - document_possibly_renamed [TFA#4]: ... (new_doc_id=doc-ca45b33c16825a28, previous_doc_id=doc-d7a2fdd3ecf25706 ...

   doc-ca45b33c16825a28  '시공상세도 승인요청 - 1F 기둥 배근도 (Z1) 2차'  APPROVED  orphaned=False
```

**반려된 1차가 승인된 2차 뒤로 사라졌다.** `services/ingest/persistence.py` 의 upsert 루프는 같은 업로드
안에서 두 번째로 나온 같은 `doc_id` 를 "기존 행 갱신"으로 처리하므로(`existing` 딕셔너리에 방금 자기가
넣은 행이 있다), 마지막 시트 행이 이긴다. 남은 행의 `approval_status` 가 그대로 `drawing_approval`
논리곱(§5-1)의 입력이 된다. `document_count` 는 11 인데 실제 행은 10 이고, 그 차이를 보고하는 곳이 없다.
`created`/`updated` 합도 11 로 맞아떨어져 산술로도 드러나지 않는다.

유일하게 남은 흔적은 `document_possibly_renamed` 두 줄이 **같은 `new_doc_id`** 를 가리킨다는 것뿐이다 —
이 ADR 이 그 신호를 §5-2 의 탐지 규칙으로 승격한다.

정리하면:

| | 분리(보수적 실패) | 병합(공격적 실패) |
|---|---|---|
| 데이터 | 두 행 모두 남는다 | **한 행이 사라진다** |
| 관측 | 고아 표시 + `document_possibly_renamed` + 검토요청 재개 | ~~없음(경고 문구가 우연히 남을 뿐)~~ → ~~**개정 1**: `DOCUMENT_IDENTITY_COLLISION` 경고 + `cause ∈ {merge_overwritten, merge_absorbed}` 로 CM 큐~~ → **개정 2**: `cause ∈ {row_replaced, row_absorbed}` 로 **CM 큐**(§5-2). 개정 1 은 이 칸을 **충돌 묶음이 있는 병합에 한해** 참으로 만들었다 — 두 행이 한 적재에 함께 있지 않으면 여전히 관측이 없었다(§5-5) |
| 복구 | config 되돌리면 원래 `doc_id` 로 돌아온다 | **불가** — 덮어쓴 값은 없다 |
| readiness | 근거가 사라져 점수가 **내려간다**(보수적) | 잘못된 `approval_status` 가 근거로 **올라간다** |

마지막 줄이 결정적이다. 분리는 착수 가능을 과소평가하고, 병합은 **미승인 도면 위에서 착수 가능을 띄운다.**

**개정 1 정정 — "관측: 없음"은 이제 사실이 아니다.** 초판은 이 칸을 "없음"으로 적고, 그러면서도 §5-2 에서
병합을 **경고까지만** 배정했다. 그 두 문장이 한 ADR 안에 나란히 있는 것이 이 사이클의 blocker 를 만들었다.
지금은 §5-2 가 병합을 두 경위(`merge_overwritten`/`merge_absorbed`)로 나눠 사람의 판단이 걸린 경우 CM 큐에
올린다. **다만 "복구: 불가"와 "readiness: 올라간다"는 그대로다** — 덮어쓰기 자체는 여전히 일어나고(대장이
정본이라 마지막 행이 이긴다), 이 ADR 이 바꾼 것은 그것이 **조용하지 않다**는 점 하나뿐이다.
실측(개정 1, TestClient):

```
CM 이 "반려된 도면"임을 확인하고 A300 매핑을 확정해 차단  → drawing_approval 0.0, blocker document_unapproved
sender_aliases 별칭표 통합 한 줄(동부건설 ← 동부이앤씨) 후 같은 대장 재업로드
  created=0 updated=12 orphaned=1  identity_drift_moved=0 identity_drift_merged=1
  문서 doc-v1-2ab48f2b5f6b911e: REJECTED → APPROVED, doc_number 도 다른 행의 것, is_orphaned=False
  drawing_approval 0.0 → 1.0, blocker 사라짐, score 0.55 → 0.70
  identity_drift_lost_decisions=1  cause="merge_overwritten"  → document_identity_drift 검토요청 1건
```

개정 전 코드에서는 마지막 줄만 없었다 — **미승인 도면 위에서 착수 가능이 뜨고 아무도 몰랐다.**

**개정 2 정정 — 위 실측은 "두 행이 한 적재에 함께 있을 때"의 것이다.** 같은 별칭표 통합이라도 **옛
법인명 행이 대장에서 빠지면**(사명 변경 주의 정상 운영) 충돌 묶음이 만들어지지 않아 개정 1 의 탐지가
전부 침묵했다 — 같은 뒤집힘(`drawing_approval` 0.0 → 1.0), 경고 0건, 검토요청 0건. §5-5 가 그 재현과
정정을 남긴다. 이 표에서 병합 열이 뜻하는 것은 "한 적재 안의 충돌"이 아니라 **"서로 다른 대장 행이 한
`doc_id` 를 갖게 됐다"** 이며, 그것이 한 적재 안에서 일어나는지 두 적재에 걸쳐 일어나는지는
**결과에 아무 차이도 만들지 않는다.**

### 4. 흔들리는 것은 제목만이 아니다 — 식별 표면 전수

**전수 목록을 만든 기준(반드시 함께 읽을 것).** `_compute_doc_id(doc_type, sender_normalized,
seq_normalized, title_normalized)` 의 **인자 네 개를 각각 뒤로 따라가** 그 값을 만드는 입력을 찾고,
그 입력을 실제로 바꿔 `doc_id` 를 다시 계산했다. 코드를 읽고 판단하지 않고 전부 실행으로 확인했다.

| 재료 | 만드는 함수 | 입력 | 실측(픽스처 10건) |
|---|---|---|---|
| `doc_type` | `_sheet_doc_type` | `register_layout.sheet_doc_types` + 워크북 **시트명** | 별칭 하나 바꾸면 **8/10** 변경 |
| `sender_normalized` | `_sender_normalized`→`_squash` + 별칭표 | `normalization.sender_aliases`, `column_aliases.sender` | 표준명 표기 변경 **7/10**, 새 별칭 추가 **1/10**, `column_aliases.sender` 변경 **10/10** |
| `seq_normalized` | `_seq_normalized` (숫자만, 코드 고정) | `column_aliases.seq_raw` | 아래 §4-1 |
| `title_normalized` | `_title_normalized` | `title_matching.normalize`, `column_aliases.title` | §2-1 표 |

**이 기준이 놓치는 것**(ADR 0008 계획이 `grep "session.get(...)"` 하나로 전수를 만들었다가 시그니처 변경
호출부와 Celery 잡 안에서 삼켜지는 경로를 통째로 놓친 전례를 그대로 되풀이하지 않기 위해 명시한다):

1. **파서 밖에서 입력이 바뀌는 경로.** 사용자가 엑셀에서 시트명을 `TFA` → `승인요청서` 로 바꾸면 config 는
   그대로인데 `doc_type` 이 바뀐다. 이 기준은 config 만 흔들어 봤으므로 그 경로를 직접 보지 못한다
   (효과는 `sheet_doc_types` 변경과 같으므로 폭발 반경은 대리 측정됐다).

   **개정 1 — 대리 측정으로는 부족했다.** 이 경로를 직접 태워 보니 폭발 반경(8/10)만 같았을 뿐 **관측
   가능성이 전혀 달랐다**: `doc_type` 이 함께 바뀌어 옛 행이 **고아가 되지 않고**(실측 `orphaned=0`,
   `moved=8`), config 를 한 글자도 안 바꿨으므로 **지문도 그대로다**(`fingerprint_changed=False`).
   초판 §5-2 는 판정 조건을 "고아"로, 보완 신호를 "지문"으로 적었으므로 이 경로에서 **둘 다 침묵한다.**
   블라인드 스팟을 적어 두는 것만으로는 부족하고, **적어 둔 스팟은 실제로 태워 봐야 한다**(CLAUDE.md §6-1).
2. **`doc_id` 를 `documents` 밖에 **저장**하는 자리.** 위 표는 "누가 `doc_id` 를 만드는가"만 본다.
   "누가 이미 만들어진 `doc_id` 를 붙들고 있는가"는 별도 조사가 필요하고, 그것이 §6 마이그레이션 표다.
   그 조사는 `grep doc_id` 로 만들었으므로 **다른 키 이름으로 저장하거나 자유형 JSON 안에 묻힌 자리는
   놓친다** — 지금 저장소에서는 그런 자리를 찾지 못했지만 "없다"고 단정하지 않는다.
3. **미래에 추가되는 재료.** 이 표는 오늘의 네 인자다. 재료를 늘리는 변경은 §5 규칙 4에 따라
   `DOC_ID_SCHEME` 를 올려야 하며, 그 규칙이 이 목록을 다시 만들도록 강제한다.

#### 4-1. 곁가지 실측 — `seq` 는 생각보다 약한 재료다

`column_aliases.seq_raw` 의 별칭 목록에 `"no."`/`"no"` 가 있다. 대장에 `번호` 컬럼이 없으면
**행번호 `No` 컬럼이 조용히 대신 채택된다**(실측: `seq_raw = ['1','2',...,'8','1','2']`).
그 상태에서 대장 맨 앞에 문서 한 건을 끼워 넣고 `No` 를 다시 매기면:

```
행 하나 삽입 후: 기존 문서 10건 중 doc_id 가 바뀐 것 8건
```

`required_columns` 는 `["title"]` 하나뿐이므로(§2-5 규칙 3) 이 대장은 정상 적재된다. 즉 **오늘의 `doc_id`
는 대장의 행 순서에 매달릴 수 있다.** 이 ADR 은 이 문제를 고치지 않고(§Deferred 1) 기록만 한다 —
`seq_raw` 별칭을 바꾸는 것 자체가 식별 표면 변경이므로 §5 규칙 4 절차를 밟아야 한다.

## Decision

### 1. `title_normalized` 를 두 개로 나눈다

| 필드 | 소유 | 용도 | 바꿔도 되나 |
|---|---|---|---|
| `title_identity` (신설) | **코드** — `packages/core/models/document.identity_title()` | `doc_id` 재료 | 아니오. 바꾸려면 §5 규칙 4 |
| `title_normalized` (기존, 의미 정정) | `config/document_register.yaml` `title_matching.normalize` | 제목 ↔ Activity 대조 | 예. 자유롭게 |

`title_normalized` 의 **계산은 한 글자도 바뀌지 않는다.** 바뀌는 것은 "이 값이 `doc_id` 재료다"라는 사실
하나뿐이다. ADR 0007 §2-3 컬럼 표는 이미 이 필드를 "대조용 정규화 텍스트"라고 적어 두었다 — 그 서술이
사실이 아니었고, 이 ADR 이 서술 쪽이 아니라 코드 쪽을 서술에 맞춘다.

`services/progress/document_mapper._build_mapping` 은 이미 `doc.title` 에서 매번 다시 정규화해 쓰고
저장된 `title_normalized` 를 읽지 않는다 — 즉 **대조 경로는 이 분리에 아무 영향을 받지 않는다.**

### 2. 식별용 정규화는 config 가 아니라 **코드**에 둔다

`config/` 에 `identity_normalization:` 블록을 만들고 `_assert_invariant` 로 지키는 안을 검토했고
**채택하지 않는다.** 근거:

- ADR 0007 §9 의 `UnsafeConfigOverrideError` 는 **코드가 읽지 않는 키**를 지키는 장치다. "값을 바꿔도
  아무 일도 안 일어나는 것"이 위험하므로 요란하게 실패시킨다는 논리다. 식별 정규화는 정반대로
  **코드가 반드시 읽어야 하는 값**이라 같은 장치가 성립하지 않는다.
- 정규화 규칙은 정규식 목록·문자 집합·불리언의 중첩 구조다. "요구값과 같은가"를 검사하려면 그 구조 전체를
  코드에 또 한 벌 적어 두고 깊은 비교를 해야 한다. 그러면 진실 원천이 두 개가 되고, 둘이 어긋나는 순간
  **어느 쪽이 진짜인지 아무도 모른다.**
- config 에 키가 **보이면** 만지게 된다. 안전 장치의 최선은 "만졌을 때 막는 것"이 아니라 "만질 손잡이가
  없는 것"이다.

따라서 `title_identity` 를 만드는 함수는 `packages/core/models/document.py`(architect 소유)에 있고
`config/` 를 읽지 않는다. `doc_id` 를 만드는 유일한 승인 경로도 같은 모듈의 `compute_doc_id()` 다.

```python
DOC_ID_SCHEME = 1

def identity_title(title: str) -> str:
    return _IDENTITY_WHITESPACE_RE.sub(" ", unicodedata.normalize("NFKC", title)).strip().casefold()

def compute_doc_id(doc_type: str, sender_normalized: str, seq_normalized: str | None, title: str) -> str:
    material = f"{doc_type}|{sender_normalized}|{seq_normalized or ''}|{identity_title(title)}"
    return f"doc-v{DOC_ID_SCHEME}-" + hashlib.sha256(material.encode("utf-8")).hexdigest()[:16]
```

**`compute_doc_id` 의 마지막 인자가 정규화된 제목이 아니라 원문 제목인 것이 설계다.** 호출자가 자기
나름대로 정규화한 문자열을 재료로 끼워 넣을 수 없다. 오늘의 사고는 정확히 "호출자가 재료를 골랐다"에서
비롯됐다.

**동결의 두 번째 강제 지점**: `Document` 모델의 `model_validator` 가 `title_identity` 를 언제나
`title` 에서 다시 계산해 **호출자가 준 값을 버린다.** 파서든 DB 읽기든 테스트 헬퍼든 같은 `title` 이면
같은 `title_identity` 다. `doc_id` 는 파생시키지 **않는다** — DB 에서 읽을 때 `doc_id` 를 다시 계산하면
`DOC_ID_SCHEME` 가 올라간 순간 **읽기만 해도 키가 바뀌어** 이 ADR 이 막으려는 사고가 그대로 재현된다.

**세 번째 강제 지점**은 config 로더다. `load_document_register_config()` 가 `title_matching.normalize` 아래
`affects_doc_id` 키를 `false` 로 고정 검사하고(§9 의 기존 패턴), 식별 정규화를 config 로 되돌리려는
키(`title_matching.identity_normalization`, `normalization.title_identity`)가 **존재하기만 해도**
`UnsafeConfigOverrideError` 로 실패시킨다. 값이 아니라 **키의 존재**를 막는 것은 이 저장소에 없던 형태다 —
"안전 불변식을 문서화하는 키"와 "안전 불변식을 되돌리려는 키"는 다르게 다뤄야 하기 때문이다.

### 3. 식별 정규화는 **대조 정규화보다 보수적**이다

`identity_title` 이 하는 일은 셋뿐이다.

1. `unicodedata.normalize("NFKC", ...)`
2. 연속 공백 → 한 칸 + 앞뒤 공백 제거
3. `casefold()`

**하지 않는 일**: 괄호·하이픈 제거, 머리말·확장자·첨부 표기 제거, 잡음 토큰 삭제. 전부 대조용이 한다.

경계선은 **"표기 인코딩은 정규화하고, 내용은 절대 건드리지 않는다"** 이다. 전각/반각, 논브레이킹 스페이스,
중복 공백, 대소문자는 엑셀에서 IME 상태에 따라 저절로 섞여 들어오는 것이지 사람이 문서를 고쳐 쓴 것이
아니다. 반면 괄호나 하이픈이 사라진 것은 **누군가 제목을 편집한 것**이고, 그것은 정체성이 흔들릴 수도
있는 사건이므로 시스템이 대신 판단해서는 안 된다.

실측(픽스처 제목 1건에 대한 9가지 표기 변형):

```
  원문                     같음    '시공상세도 승인요청 - 1f 기둥 배근도 (z1)'
  공백 2칸                  같음
  앞뒤 공백                  같음
  전각 괄호 （Z1）             같음
  전각 영문 Ｚ                같음
  대문자 F→소문자              같음
  논브레이킹 스페이스             같음
  하이픈 제거                 다름 ***
  괄호 제거                  다름 ***
```

마지막 두 줄은 **의도한 동작**이다 — 그때는 §3 (가) 분리 경로로 들어가고, 고아 표시·경고·재검토가 붙는다.

보수 쪽을 고르는 근거를 한 줄로 적으면: **확신이 없을 때 정체성은 나누는 쪽으로 틀린다.** 이는
ADR 0001("스캔 AI 는 추정까지, 확정은 사람"), ADR 0007 §3-2("공란·해석 불가를 승인으로 추측하지 않는다"),
§4-2 규칙 4("애매한 매핑은 만들지 않는다")와 같은 방향이다. 셋 다 "모르면 사람에게 넘긴다"이고, 분리는
사람에게 넘기는 실패, 병합은 사람 몰래 답을 정하는 실패다.

### 4. 제목을 재료에서 빼지 않는다 — 실측 근거

`seq_normalized` 가 이미 있으니 제목을 빼면 정규화 문제 자체가 사라진다는 선택지를 검토했고,
**채택하지 않는다.** `번호` 가 비는 대장이 실제로 가능하기 때문이다(`required_columns: ["title"]`).

```
--- 번호·No 컬럼 모두 없는 대장 ---
  문서 10건 / seq 결측 10건
  현재 doc_id(제목 포함) 유니크: 10/10
  제목 뺀 doc_id 유니크        : 5/10  → 충돌 5건
    충돌 키 ('TFA', '동부건설', '') × 6
       TFA '시공상세도 승인요청 - 1F 기둥 배근도 (Z1)' → 승인상태 APPROVED
       TFA '시공상세도 승인요청 - 1F 보 배근도 (Z1)'   → 승인상태 APPROVED_WITH_COMMENTS
       TFA '시공상세도 승인요청 - 1F 슬래브 배근도 (Z1)' → 승인상태 UNKNOWN
       TFA '자재승인원 - 외벽 조적 벽돌 (1F Z1)'       → 승인상태 REJECTED
       TFA '시공상세도 승인요청 - 2F 기둥 배근도 (Z1)' → 승인상태 APPROVED
       TFA '시공상세도 승인요청 - 1F 기둥 배근도 (Z2)' → 승인상태 APPROVED

--- 일부 행만 번호가 빈 대장(현장에서 더 흔한 형태) ---
  문서 10건 / seq 결측 3건 → 제목 뺀 doc_id 충돌 2건
```

제목을 빼면 **승인·반려·미기재가 뒤섞인 6건이 한 행으로 붕괴**한다. 이는 §3 (나) 병합 실패를 설계
차원에서 상시화하는 것이다. 게다가 §4-1 이 보였듯 `seq` 자체가 행번호로 폴백될 수 있어 단독 재료로는
더 약하다. **제목은 이 대장에서 문서를 실제로 구별하는 유일한 필드다.** 재료에 남긴다.

### 5. 규칙 (이 저장소의 불변식)

1. **`doc_id` 는 `packages/core/models/document.compute_doc_id()` 로만 만든다.** 다른 모듈에 해시 계산을
   복제하지 않는다. `services/progress/importers/document_register._compute_doc_id` 는 삭제한다.
2. **`title_matching.*` 아래 어떤 값도 `doc_id` 를 움직이지 않는다.** 이것이 이 ADR 의 핵심 계약이며
   §7 검증 시나리오 V1 이 이 계약 자체를 테스트로 고정한다.
3. **식별 표면(§4 표)에 속하는 config 를 바꾸는 변경은 스키마 마이그레이션과 같은 무게로 다룬다.**
   `title` 은 §2 로 표면에서 빠졌지만 `sender_aliases`·`sheet_doc_types`·`column_aliases` 는 운영상
   반드시 바꿀 수 있어야 하므로 동결할 수 없다 — 대신 §5-2 가 **탐지**한다.
4. **재료·정규화·`identity_title` 이 바뀌면 `DOC_ID_SCHEME` 를 올린다.** 올리는 PR 은 §6 마이그레이션을
   함께 담아야 한다. 값만 올리고 끝내는 변경은 reviewer 가 반려한다.
5. **`doc_id` 문자열에 스킴 번호가 실린다**(`doc-v1-<16hex>`). 접두사가 없으면 재적재가 "새 문서가
   들어왔다"인지 "같은 문서의 키 규칙이 바뀌었다"인지 **데이터만 보고는 구분할 수 없다** — 오늘의 사고가
   조용했던 이유가 정확히 그것이다.

#### 5-1. 동결할 수 없는 식별 표면 — 무엇을 할 수 없는가

`normalization.sender_aliases`(새 협력사가 들어오면 반드시 추가해야 한다),
`register_layout.sheet_doc_types`·`column_aliases`(대장 서식이 현장마다 다르다, §2-5)는 운영 필수라
동결 대상이 아니다. 실측 폭발 반경은 각각 7/10, 8/10, 10/10 이다. 이들에 대해 이 ADR 이 하는 일은
**막는 것이 아니라 알아채는 것**이다.

#### 5-2. 탐지 — `document_identity_drift`

> **개정 1에서 전면 재작성됐고, 개정 2에서 (나)·(다)·(라)·(마)를 다시 썼다.** 초판의 표는 이 사이클
> 첫 blocker 의 **원인**이었고, 그것을 고친 **개정 1 의 표가 두 번째 원인**이었다. 무엇을 어떻게
> 틀렸는지는 지우지 않고 §5-4(초판)·§5-5(개정 1)에 그대로 남긴다 — 다음 사람이 같은 함정을 피하려면
> 그 기록이 필요하다. 아래 서술의 **정본은 구현**이다(`services/ingest/persistence.py` +
> `services/progress/document_mapper.py`). 개정 2의 모든 수치·문구는 실행으로 확인했다(§5-2 (바) 표).
>
> **이 절을 고칠 사람에게.** 이 조건절은 **같은 방식으로 세 번** 틀렸다 — 초판 "고아", 개정 1 "새",
> 개정 1 "한 적재 안에서". 세 번 모두 한정어 하나가 §3 이 최악이라 분류한 경로를 표 밖으로 밀어냈고,
> 세 번 모두 근거는 이 문서 안에 이미 있었다. 여기에 한정어를 더하기 전에 CLAUDE.md §6-3 의 역방향
> 확인을 **적어서** 하고, §5-2 (바)의 표에 줄을 더해 실행으로 확인하라.

대장 적재는 두 가지를 함께 계산한다.

- **식별 표면 지문(`identity_fingerprint`)**: 식별에 관여하는 config 부분집합(§4 표의 입력들)만 모아
  해시한 값(`services/progress/identity_surface.identity_surface_fingerprint`). **적재 단위** 값이며
  적재한 문서 행마다 함께 저장한다(`imported_at` 과 같은 형태 — 별도 테이블을 만들지 않는다).
- **드리프트 관측**: 아래 두 갈래. 어느 쪽도 **지문을 판정 조건으로 쓰지 않는다.**

**지문은 판정 조건이 아니라 보고 값이다(개정 1 정정).** 초판은 "판정이 '일어났다'를, 지문이 '무엇이
바뀌어서'를 답한다"고 적었는데, 그 문장은 지문이 언제나 함께 움직인다는 전제를 몰래 깔고 있었다.
사용자가 **엑셀 시트명을 바꾸는 경로**는 config 를 한 글자도 바꾸지 않으므로 지문이 그대로다
(실측: `fingerprint_changed=False` 인데 `moved=8`). 지문을 조건에 넣었으면 이 경로 전체가 조용히
지나간다. 지문이 답하는 것은 **"어디를 되돌려야 하는가"** 하나다 — 바뀌었으면 config(§4 표), 그대로면
대장 파일 쪽(시트명 등 config 밖 입력).

##### (가) 관측 1 — 이동(`moved`)

이번 적재에 **나타나지 않은 기존 행**과, 이번 적재에서 **새로 생긴 문서** 사이에서 `title` **원문이 글자
그대로 같고** `doc_number` 가 어긋나지 않는 쌍을 1:1 로 짝짓는다(`_pair_identity_moves`; `doc_number` 는
한쪽이 비면 통과 — 대장에 문서번호 열이 없는 현장이 있다). 대장은 그대로인데 우리 규칙이 움직인 것이다.

**후보를 "고아"로 좁히지 않는다(개정 1 정정).** 초판은 조건을 "고아 ↔ 신규 쌍"이라고 적었다. 그런데
시트명을 바꾸면 `doc_type` 이 함께 바뀌고, ADR 0007 §2-2 규칙 2 가 "이번 업로드에 등장한 `doc_type`"
에만 고아 처리를 하므로 옛 행은 **고아가 되지도 않는다** — 실측 `orphaned=0`, `moved=8`. "고아"로 좁힌
구현은 이 경로를 통째로 놓친다. 좌변은 `is_orphaned` 가 아니라 **이번 적재에 나타나지 않은 기존 행 전부**다.

`rename_index`(ADR 0007 §2-2 규칙 4)에 기대서도 안 된다. 그 키는 `(doc_type, sender_normalized,
seq_normalized)` 이고 `doc_id` 는 거기에 `title_identity` 를 더한 해시다 — 키가 같고 제목 원문도 같으면
재료 넷이 모두 같아 **애초에 같은 `doc_id`** 라서 그 분기는 발화할 수 없고, 반대로 `sender_aliases` 를
바꾸면 키가 어긋나 `document_possibly_renamed` 가 한 건도 뜨지 않는다(실측: 7건 이동, rename 경고 0건).

##### (나) 관측 2 — 담긴 대장 행이 **바뀌었다**(`replaced`)

> **개정 2에서 다시 쓴 절이다.** 개정 1 은 이것을 "**한 적재 안에서** 두 개 이상의 대장 행이 같은
> `doc_id` 로 수렴하면 병합"이라고 적었고, 그 **"한 적재 안에서"** 가 구현의 조건 ①(충돌 묶음)이 됐다.
> 초판의 "고아"·"새"를 걷어낸 자리에 **새 한정어 하나가 남았고**, §3 이 최악이라 분류한 경로가 다시 표
> 밖으로 나갔다. 무엇이 어떻게 틀렸는지는 §5-5 에 남긴다. **같은 조건절이 같은 방식으로 세 번 틀렸다.**

**판별해야 하는 사실은 "한 적재 안에서 충돌했는가"가 아니라 "이 `doc_id` 가 담고 있는 대장 행이
바뀌었는가"다.** 충돌 묶음은 그 사실이 생기는 **한 가지 경로**일 뿐이고, 운영에서 흔한 다른 경로가 있다 —
사명 변경 주에 별칭표를 통합하면서 **옛 법인명 행이 대장에서 빠지는** 것이다(실측은 아래).
그러면 두 행이 한 적재에 함께 있지 않으므로 충돌 묶음이 만들어지지 않는다.

그래서 같은 `doc_id` 아래의 대장 행을 두 조각으로 나눈다.

| | 필드 | 무엇을 답하나 |
|---|---|---|
| **행-정체** | `(sender, doc_number, seq_raw, title)` — 전부 대장 **원문** | 이 `doc_id` 가 대장의 **어느 행**을 담고 있나 |
| **행-내용** | `(result_raw, approval_status)` | 그 행이 지금 **무엇이라고 말하나** |

`doc_id` 재료 넷(`doc_type`·`sender_normalized`·`seq_normalized`·`title_identity`)은 어느 쪽에도 넣지
않는다 — 같은 `doc_id` 안에서는 정의상 언제나 같아 아무것도 구별하지 못한다. `sheet_name`/`source_row` 도
넣지 않는다(대장 앞에 행이 하나 끼면 전부 밀리는데 그것은 행이 바뀐 것이 아니다). 개정 1 의
`_register_row_signature` 는 이 여섯을 **한 덩어리로** 썼고, 그래서 "행이 바뀌었다"와 "대장이 처리결과를
정상 갱신했다"를 구별하지 못해 조건 ①(충돌 묶음)에 기대야 했다.

**발화 조건은 둘의 합집합이다.** 적재 전후로 살아 있는(= 이번 적재에 나타난 기존) `doc_id` 에 대해 —

- **(나-i) 행-정체가 달라졌다.** 충돌 묶음 소속을 **묻지 않는다.**
- **(나-ii) 이 `doc_id` 가 이번 적재에서 다른 `doc_id` 를 흡수했고**(= (다)의 결과 `absorbed_into` 의 값에
  이 `doc_id` 가 있다) **행-내용이 달라졌다.**

(나-ii)가 왜 필요한가는 §5-5 의 실측 P13 이 답한다 — **행-정체까지 똑같은 두 행**(문서번호 열이 없는 현장,
같은 발신·번호·제목이 시트 둘에 나뉘어 있다)이 `sheet_doc_types` 변경으로 하나가 되면 (나-i)는 침묵한다.
그 경우는 개정 1 의 조건이 **잡던** 경로이므로, (나-i)만으로 갈아타면 **고친 자리에서 다른 자리를 잃는다.**
합집합이어야 한다.

##### (다) 관측 3 — 담고 있던 행이 **다른 `doc_id` 아래로 갔다**(`absorbed`)

이번 적재에 나타나지 않은 기존 행 중, **그 행이 담고 있던 행-정체가 이번 적재의 다른 `doc_id` 아래에
그대로 살아 있는** 것. (가)가 이미 짝지은 행과 이미 고아였던 행은 제외한다(한 행은 한 경위에만 속하고,
사건이 일어난 적재에서 한 번만 발화한다).

**"충돌 묶음 구성원과 제목이 같고 문서번호가 호환된다"를 쓰지 않는다(개정 2 정정).** 개정 1 의 그 조건은
두 군데서 틀렸다. ① 충돌 묶음을 요구해 (나)와 같은 이유로 위 재현의 대칭 짝(판단이 **사라지는** 쪽)을
놓쳤다. ② 문서번호가 한쪽이라도 비면 통과시키므로(대장에 문서번호 열이 없는 현장을 위한 완화),
**문서번호 열이 없는 현장에서는 "제목만 같으면 통과"로 퇴화**해 진짜 삭제를 흡수로 오보고했다(실측 P5).
행-정체 **전체 일치**를 요구하면 두 문제가 함께 사라진다 — 진짜로 지워진 행의 행-정체는 이번 적재
어디에도 없기 때문이다.

##### (라) `merged`(충돌 묶음)의 자리 — 조건이 아니라 **보고**다

한 적재 안에서 두 개 이상의 대장 행이 같은 `doc_id` 로 수렴하는 것은 계속 관측하고
(`_collision_groups`) `DOCUMENT_IDENTITY_COLLISION` 경고로 보고한다 — 행 하나가 실제로 사라지고
`document_count` 와 실제 행 수가 어긋나는 것은 그 자체로 보고할 값이다. 덮어쓰기 동작도 유지한다
(대장이 정본 — 마지막 행이 이긴다).

**바뀐 것은 `merged` 가 더 이상 (나)·(다)의 전제가 아니라는 점이다.** 개정 1 은 이것을 게이트로 썼고,
그 결과 ① 충돌 없이 행이 바뀌는 경로가 통째로 조용했고 ② 충돌이 상시화된 대장(같은 두 행이 매주
올라온다)에서는 조건 ①이 **항상 참**이라 가드가 ②만 남아 대장의 정상 처리결과 갱신이 오탐이 됐다
(실측 P4 — 그때 붙는 문구 "내용이 **다른 대장 행**으로 바뀌었습니다"도 거짓이었다. 실제로는 **같은 행**의
처리결과가 갱신된 것이다).

##### (마) 사람의 판단이 오염되는 경위 — `lost_decisions[].cause`

관측(가)·(나)·(다)에 걸린 `doc_id` 를 가리키는 `activity_document_mappings` 중 `reviewed_by is not None`
인 것을 모아 `lost_decisions` 로 싣는다. 한 `doc_id` 는 한 경위에만 속한다(우선순위 (가) → (나) → (다)).

**그러나 한 적재는 여러 경위를 만든다(개정 2 보정 — 명시하지 않아 오해를 샀다).** 위 문장은 **한 `doc_id`
안에서** 경위가 겹칠 때 하나를 고르는 규칙이지, 한 적재가 경위 하나만 만든다는 뜻이 아니다. 실측 — (바)
표의 R1(= 회귀 V7a)과 P11(= V7c)은 **서로 다른 사건이 아니라 같은 적재의 양쪽**이다 — 대장 두 장도
config 변경 한 줄도 똑같고, 다른 것은 CM 의 판단을 어느 쪽에 걸었는가뿐이다. 사명 변경 주 재현 한 번이
살아남은 `doc_id` 를 `row_replaced` 로, 사라진 `doc_id` 를 `row_absorbed` 로 **동시에** 판정한다
(`persist_document_register_import` 의 `details` 는 판단 유무와 무관하게 두 항목을 다 만든다). 그 두 줄에서
`lost_decisions` 가 각각 1건인 것은 **사람 판단을 한쪽에만 걸어 재현했기 때문일 뿐**이고, 양쪽에 걸면 한
적재가 두 경위를 함께 싣는다 — 실측:

```
확정: 살아남는 쪽 / 반려: 사라지는 쪽 (같은 대장·같은 config 변경)
  lost_decisions = [(row_replaced, confirmed), (row_absorbed, rejected)]   검토요청은 여전히 적재당 1건
```

(회귀 `test_v7_mixed_causes_title_writes_each_cause_side_by_side`.) 그래서 소비자는 **경위별로 묶어 각
경위를 건수와 함께 나란히** 적어야 하고, 하나로 뭉뚱그리면 반드시 거짓이 된다(§5-3: `row_replaced` 에는
다시 판단할 곳이 없고 `row_absorbed` 에는 있다). `_identity_drift_review_title` 의 절 구성과 화면의
`groupLostDecisionsByCause` 가 그 형태다.

**항목 계약(개정 2 — 필드가 늘었다).**

```
{activity_id, doc_id, decision, cause, new_doc_id, changed_fields, approval_flipped}
```

| 필드 | 값 | 왜 필요한가 |
|---|---|---|
| `cause` | `row_moved` \| `row_replaced` \| `row_absorbed` | 생략 불가. 소비자가 문구를 사실대로 쓰는 유일한 입력 |
| `new_doc_id` | `row_moved`/`row_absorbed` → 그 행이 지금 있는 `doc_id`. `row_replaced` → **`null`** | "다시 판단할 곳이 있는가"를 **값으로** 답한다. `null` 은 "없다"는 사실이지 "모른다"가 아니다 |
| `changed_fields` | `row_replaced` 에서 달라진 행-정체 필드 목록(`sender`·`doc_number`·`seq_raw`·`title`). (나-ii)로만 걸렸으면 `[]` | CM 이 "다른 문서로 바뀐 것"과 "대장이 문서번호 오타를 고친 것"을 **한 줄 안에서** 가른다(아래 오탐 참조) |
| `approval_flipped` | 이 적재에서 `approval_status` 가 달라졌는가 | 착수 가능 판단이 실제로 뒤집혔는지. `row_moved`/`row_absorbed` 는 언제나 `false`(현재 행이 없다) |

**`cause` 이름을 바꾼다(개정 2).** 옛 이름 셋은 전부 사실과 어긋난다 —

| 옛 이름 | 왜 거짓인가 (실측) | 새 이름 |
|---|---|---|
| `orphaned` | 시트명 변경 경로에서 `moved=8` 인데 그 행들은 **고아가 아니다**(`is_orphaned=False`, 실측 P3). 개정 1 이 §5-2 (가)의 좌변에서는 "고아로 좁히지 않는다"고 고쳐 놓고 **경위 이름과 문구는 고아라고 말한다** | `row_moved` |
| `merge_overwritten` | 새 조건이 잡는 **주된** 경로에는 병합이 없다(실측 `merged=0`). 병합이라 적으면 CM 이 없는 충돌을 찾는다 | `row_replaced` |
| `merge_absorbed` | 대칭 짝도 마찬가지로 `merged=0` 에서 발화한다 | `row_absorbed` |

| `cause` | 데이터가 어떤 모습인가 | CM 이 해야 할 일 |
|---|---|---|
| `row_moved` | 대장 행은 그대로인데 우리 식별 규칙이 그 행을 **다른 `doc_id`** 로 옮겼다. 옛 행은 고아가 될 수도, 안 될 수도 있다(시트명 변경 경로는 안 된다) | `new_doc_id` 위에서 같은 판단을 다시 내린다 |
| `row_replaced` | **행도 `reviewed_by` 도 살아 있고 고아 표시조차 없다.** 바뀐 것은 그 `doc_id` 가 담고 있는 **대장 행**이다 | 화면의 승인 상태를 믿지 않는다. **다시 판단할 새 `doc_id` 가 없다**(`new_doc_id=null`) |
| `row_absorbed` | 판단이 가리키던 대장 행이 다른 `doc_id` 아래로 갔고 이 `doc_id` 에는 대장 행이 남지 않았다 | `new_doc_id` 위에서 다시 판단한다 |

`row_replaced` 가 §3 이 스스로 최악이라 적은 경로다 — 판단이 **사라지는** 게 아니라 판단의 **대상**이
바뀐다. 그래서 고아·이동 조건 어디에도 걸리지 않는다.
`decision`(확정/반려)의 구분은 `document_mapper.is_rejected_mapping()` 에 맡긴다 — 판정 키 문자열을
적재 모듈이 직접 읽지 않는다(ADR 0007 §4-2 규칙 6 ⑥ 불변식).

##### (바) 실측 — 새 조건이 무엇을 잡고 무엇을 놓치는가 (전부 TestClient 로 태웠다)

**이 표를 만든 기준.** ① 이번 blocker 와 그 대칭 짝, ② 리뷰어가 보고한 minor 2건, ③ **개정 1 이 잡던
것을 새 조건이 잃지 않는지**(역방향), ④ 새 조건이 만들 수 있는 오탐 후보 — 대장측 정정 셋
(`doc_number`·발신 표기·제목). 각 줄을 개정 1 코드와 개정 2 조건에서 **각각** 돌려 비교했다.

**P6·P7 을 오탐인 채로 둔다 — 그 근거.** 두 경우는 `doc_id` 재료가 아닌 대장 원문 필드를 대장이 스스로
고친 것이고, 우리 식별 규칙은 움직이지 않았다(실측 `fingerprint_changed=False`). 그럼에도 발화하게 두는
이유는 셋이다.

1. **구별할 수 있는 관측값이 없다.** "문서번호를 고쳤다"와 "다른 문서로 바뀌었다"는 대장 원문만 보면
   같은 모양이다. 지문은 둘 다 그대로다(R1 은 지문이 바뀌지만 P13·P4 는 안 바뀐다 — 지문은 판정에 쓸 수
   없다, §5-2 서두).
2. **"내용도 함께 바뀌었을 때만"으로 좁히면 안 된다(§6-3 역방향 확인).** 그 한정어를 넣으면 승인 상태가
   **우연히 같은** 다른 문서로 바뀐 경우가 표 밖으로 나간다. 그때도 CM 의 확정은 자기가 보지 않은
   도면에 붙어 있고, 그 도면의 다음 주 처리결과가 CM 이 내린 적 없는 판단 위로 흘러든다. 한정어 하나가
   변종을 밀어내는 것이 이 ADR 이 세 번 반복한 실패다.
3. **비용이 비대칭이다.** 오탐의 대가는 CM 큐의 **확인 전용** 요청 1건이고(§5-3 — 부수 효과가 없다),
   그것도 그 문서에 사람의 판단이 걸려 있을 때만 생긴다. 누락의 대가는 미승인 도면 위의 착수 가능이다.

대신 **문구가 아는 것만 말하게** 한다: `changed_fields` 를 실어 "문서번호가 `X` → `Y` 로 바뀌었습니다"라고
적고, 우리가 알 수 없는 것("다른 문서로 바뀌었습니다")을 단정하지 않는다(§6-4 규칙 2 — 산문 대신 값).
**P8b·FP1 도 같은 판단으로 남긴다** — 둘 다 `doc_id` 를 움직이지 않는 대장측 표기 변경이고, 좁히는 조건
("내용도 함께 바뀌었을 때만")을 넣으면 승인 상태가 **우연히 같은** 변종이 표 밖으로 나간다. 비용도 같은
비대칭이다(확인 전용 요청 1건 ↔ 미승인 도면 위의 착수 가능).

**FP1 이 드러내는 긴장 — 같은 원문이 한 층에서는 못 믿을 값, 다른 층에서는 정체성의 증거다.**
`seq_normalized` 가 `번호` 원문에서 숫자만 남기는 이유는 **그 원문이 불안정하기 때문**이다
(ADR 0007 §2-3: `26-049`→`26049`, `제26-07-09호`→`260709`). 그런데 행-정체는 정확히 그 **원문**
(`seq_raw`)을 담는다 — `doc_id` 재료 넷은 같은 `doc_id` 안에서 정의상 언제나 같아 아무것도 구별하지
못하므로((나) 표), 구별에 쓸 수 있는 것은 재료가 **아닌** 원문뿐이기 때문이다. 그래서 `doc_id` 를 한 칸도
움직이지 않는 표기 변경이 행-정체를 움직인다(실측: `_seq_normalized("26-210") == _seq_normalized("제26-210호")
== "26210"` 이고 `compute_doc_id` 결과가 같다. 같은 이유로 P8b 는 `identity_title` 이 두 제목을 같은
문자열로 접는데 `title` 원문은 다르다). **결함이 아니라 두 층이 서로 다른 질문에 답하는 결과**이고,
좁히는 쪽(예: `seq_raw` 를 행-정체에서 뺀다)은 숫자가 같고 표기만 다른 두 행이 서로를 덮어써도 침묵하게
만든다(이 반대 방향은 **아직 태우지 않았다** — 추론이다). 그래서 남기고, `changed_fields` 가 "번호"를
실어 CM 이 한 줄 안에서 가른다.

**이 기준이 놓치는 것(개정 2 가 남기는 구멍).**

1. **행-정체가 같은 두 행이 서로 다른 doc_type 아래 있고, 그중 하나가 진짜로 지워지는 경우.** (다)의
   행-정체 대조는 `doc_type` 을 보지 않으므로(시트명 변경 경로가 정확히 `doc_type` 을 바꾼다) 그 삭제를
   흡수로 오보고할 수 있다. 방향은 보수적이다(없는 사건을 만들지 않고, 있는 사건을 놓치지 않는다).
2. **부분 업로드.** (다)는 이번 적재에 없는 기존 행 **전부**를 좌변으로 삼는다(고아 규칙과 달리 doc_type
   범위로 좁히지 않는다 — 좁히면 `sheet_doc_types` 변경 경로를 놓친다). 다른 doc_type 의 행과 행-정체가
   네 필드 모두 일치하면 오보고가 가능하다. 실무에서는 문서번호에 종류가 박혀 있어 거의 불가능하지만
   **"없다"고 단정하지 않는다.**
3. **`column_aliases.sender`/`seq_raw` 를 바꾸는 변경.** 대장 원문에서 읽는 **열 자체**가 바뀌므로
   행-정체가 통째로 달라진다. (가)의 짝짓기는 `title` 원문으로 하므로 그쪽이 잡지만, (다)는 잡지 못한다.

   **실측(개정 2 보정 — 이 자리는 더 이상 비어 있지 않다).** `column_aliases.sender` 를 `["공종"]` 으로
   바꿔 **발신을 다른 열에서 읽게** 하고, 대장 파일은 **한 바이트도 바꾸지 않은 채** 재적재했다
   (회귀 `test_v7i_column_alias_change_moves_every_row_and_is_reported_as_row_moved`):

   ```
   created=10  orphaned=10          문서 10건 전부가 새 doc_id 를 얻는다(폭발 반경 10/10 — §5-1 과 일치)
   identity_drift_moved=10          (가)가 title 원문으로 10쌍을 전부 짝지었다
   identity_drift_merged=0
   lost_decisions=1                 cause=row_moved, new_doc_id=<옮겨 간 doc_id>,
                                    changed_fields=[], approval_flipped=False
   identity_drift_review_id         있음 → CM 검토요청 1건
   ```

   **결론: (다)는 이 경로를 못 잡지만 (가)가 전부 덮는다 — 놓치는 사건이 없다.** 구멍은 "관측이 없다"가
   아니라 "관측이 (가) 한쪽에만 있다"였고, 그 사실이 값으로 확인됐다. 다만 이것은 `title` 원문이 그대로일
   때의 결과다 — `column_aliases.title` 까지 함께 바꾸면 (가)의 짝짓기 근거도 사라진다(그 경우와
   `seq_raw` 쪽은 **아직 태우지 않았다**).

   **이것이 CLAUDE.md §6-1 이 요구한 "적어 둔 블라인드 스팟 최소 한 건 실측"의 첫 이행 사례다.** 그 규칙을
   만든 것이 바로 이 ADR 의 반대 사례였다 — 계획 0003 §1-a 블라인드 스팟 1(워크북 시트명 변경)을 적어
   두기만 하고 태우지 않았고, 그래서 폭발 반경은 같지만 **관측 가능성이 전혀 다르다**는 사실
   (`orphaned=0`, `fingerprint_changed=False`)을 초판 §5-2 가 통째로 빗나갔다(§5-2 (가) 개정 1 정정).
   "놓칠 수 있다"고 적는 것은 커버리지가 아니고, **적어 둔 것과 태워 본 것은 이 목록에서 구분해 적는다** —
   위 1·2 와 `seq_raw` 는 여전히 전자이고, 아래 4 는 후자다.
4. **흡수와 같은 적재에서 살아남는 쪽 행의 행-정체가 함께 움직이는 경우(리뷰어 실측 RP3b).**
   (다)의 짝짓기는 행-정체 **전체 일치**를 요구한다(`_absorbed_doc_ids` 의 `holders` 조회 — 그 엄격함이
   P5 오탐을 없앤 근거다). 그래서 흡수가 일어나는 그 주에 대장이 **살아남는 행의 `doc_number` 를 고치면**
   조회가 빗나가 흡수가 관측되지 않는다. 실측 — **적재 전체가 침묵한다**: `identity_drift=None`,
   IDENTITY 경고 0건, 검토요청 0건. 사라지는 쪽에 걸린 CM 판단은 `lost_decisions` 에 들어가지 못하고,
   살아남는 쪽은 (나-i)로 잡히지만 그 `doc_id` 에 사람 판단이 없으면 `lost_decisions` 가 비어
   `moved or merged or lost_decisions` 게이트가 닫힌다.

   **그런데 발화하는 기준선(RP3a — 같은 흡수, 번호 정정 없음)과 관측 결과가 같다**:
   `drawing_approval` 0.0 → 0.5, blocker `document_unapproved` → `document_mapping_pending`. 즉
   **흡수와 진짜 삭제를 가를 관측값이 우리에게 없다.** 그래서 이 침묵의 방향은 보수적이고(없는 사건을
   만들지 않고 점수를 내리는 쪽으로 틀린다) 방어 가능하다 — 완화하려면 행-정체 **부분** 일치를 들여야
   하는데 그것은 P5 오탐(제목만 같으면 통과)을 그대로 되살린다. **문제는 침묵 자체가 아니라 이 구멍을
   적어 두지 않았던 것이다**(CLAUDE.md §6-1: 기준이 놓치는 것을 목록 옆에 적는다). 이 줄이 그 이행이다.
5. **(나)·(다) 축은 사람의 판단이 걸려 있지 않으면 관측 자체가 없다(재심 실측 — 위 (바-2) 6행).**
   `moved` 축과 `merged` 축은 판단이 없어도 각각 DRIFT·COLLISION 경고를 낸다. (나)·(다) 축에는 그
   대조군이 없다: 두 관측은 `lost_decisions` 를 **통해서만** 밖으로 나오고, `lost_decisions` 가 비면
   보고서 게이트(`moved or merged or lost_decisions`)와 경고 게이트(`moved` / `lost_decisions and not
   merged`)가 함께 닫힌다.

   **결정: 이 비대칭을 의도로 유지한다.** 게이트를 넓히지 않는다. 근거 넷 —

   1. **두 축은 서로 다른 것을 관측한다.** `moved`·`merged` 는 **우리 쪽**의 사건이다(식별 규칙이 행을
      옮겼다 / 한 적재가 행을 삼켰다). 드물고, 원인이 config·시트명·대장 구조라 언제나 보고할 값이
      있다. (나)·(다)가 관측하는 것은 **대장이 바뀌었다**이고, 그것은 매주 일어나는 정상 운영이며
      **대장이 정본**이다(ADR 0007 §1 규칙 1).
   2. **넓히면 위 (바) 표의 오탐 넷(P6·P7·P8b·FP1)이 매주 경고가 된다.** 그 넷은 지금 "사람의 판단이
      걸려 있을 때만" 이라는 조건에 비용이 묶여 있다(§5-2 (바) 근거 3 의 비대칭 계산이 그 조건 위에
      서 있다). 조건을 풀면 대장이 문서번호 오타 하나를 고칠 때마다 DRIFT 경고가 뜨고, 그 끝은 이
      ADR 이 두 번 적은 실패다 — **운영자가 탐지를 끈다.**
   3. **경고는 이 저장소에서 이미 "아무도 되돌아보지 않는 것"으로 분류돼 있다**(§5-2 "왜 job 경고가
      아니라 검토요청인가"). 사람이 볼 일이 없는 관측을 경고로 늘리는 것은 안전 장치가 아니라 소음이다.
   4. **결정적으로, 넓혀도 위 4(RP3b)가 닫히지 않는다.** RP3b 에서 잃는 것은 **사라지는 쪽**에 걸린
      판단인데, 그 `doc_id` 는 흡수로 **관측되지 못해** `lost_decisions` 에 애초에 들어가지 못한다.
      게이트를 넓히면 살아남는 쪽의 (나-i) 경고가 하나 더 뜰 뿐 사라진 판단은 여전히 큐에 닿지 않는다.
      RP3b 의 유일한 완화는 행-정체 **부분** 일치인데 그것은 P5 오탐을 되살린다(위 4). **게이트 확장과
      RP3b 는 같은 게이트를 공유하지만 같은 문제가 아니다.**

   **유지의 대가(적어 둔다).** (나)·(다) 축은 **사람 판단이 없는 프로젝트에서 회귀가 보이지 않는다.**
   판정을 통째로 지워도 그런 적재는 지금과 똑같이 침묵한다. 그래서 이 침묵은 **계약**이어야 하고,
   `qa` 가 축마다 음성 대조군을 세워 고정해야 한다(CLAUDE.md §6-2 규칙 3 — 음성 대조군을 한 축에만
   몰지 않는다). 지금 있는 판단-없음 대조군은 `moved` 축(`test_v4_n3_*`)과 `merged` 축
   (`test_v5_n3_*`)뿐이고 (나)·(다) 축에는 없다. 필요한 것은 위 실측을 그대로 고정하는 한 건이다 —
   **V8a 에서 CM 확정만 제거하면 `identity_drift is None` 이고 DRIFT·COLLISION 경고가 둘 다 없다.**

6. **제목 편집이 식별 표면 변경과 *같은 적재*에 오면 (가)도 rename 경고도 잡지 않는다(재심 실측 —
   위 (바-2) 4행).** (가)의 짝짓기는 제목 원문이 글자 그대로 같기를 요구하고, `document_possibly_renamed`
   는 `(doc_type, sender_normalized, seq_normalized)` 키가 그대로이기를 요구한다. 사람이 제목을 고친
   주에 별칭표도 건드리면 **두 요구가 동시에 깨진다.** 실측: `moved` 7 → 6, 그 문서는 고아가 되고
   `lost_decisions=[]`·요청 0건, renamed 경고도 없다. 적재 자체는 다른 6쌍 때문에 DRIFT 경고가 뜨므로
   **완전한 침묵은 아니지만, 그 문서에 걸린 CM 판단은 어디에도 보고되지 않는다.**

   방향은 보수적이다(문서가 고아가 되므로 `drawing_approval` 은 내려간다). 완화하려면 이동 짝짓기의
   좌우변을 제목 **정규화**로 느슨하게 해야 하는데, 그것은 §3 이 `title_identity` 를 동결한 이유
   (대조용 정규화가 정체성에 새는 것)와 정면으로 부딪친다. **그래서 이번 사이클에서는 고치지 않고
   이름을 붙여 둔다** — 위 3("놓치는 것")이 이름만 들고 있던 `column_aliases.title` 동시 변경보다
   **훨씬 흔한 변종**이고, 그 3 이 이 변종을 덮고 있는 줄 알았던 것이 이번 재심이 찾은 구멍이다.

##### (바-2) 용어집 두 줄을 다시 쓰며 한 한정어 역방향 확인 (개정 2 보정 2)

`docs/glossary.md` 의 `식별 드리프트`·`오염된 판단` 두 줄은 **개정 1 에 멈춰 있었다** — 관측을 "둘"이라
적고 `merged` 를 "**한 적재에서** 두 대장 행이 같은 `doc_id` 로 수렴"으로 정의해 **판정처럼 읽히게** 뒀고
(그 한정어가 이 사이클 세 번째 blocker 의 전제 그 자체다), `cause` 정본을 옛 이름 셋으로 등록해 두고
"`orphaned`=판단이 가리키던 행이 **고아가 됐다**"라고 — 개정 2 가 거짓이라고 선언한 바로 그 문장을 —
적고 있었다. 두 줄을 개정 2 기준으로 다시 썼고, **새로 쓴 문장에 남는 한정어마다** CLAUDE.md §6-3 의
역방향 확인을 했다. 같은 조건절이 이 사이클에서 이미 세 번 틀렸으므로(초판 "고아" → 개정 1 "새" →
개정 1 "한 적재 안에서") **네 번째를 문서에서 만들지 않기 위해 표로 남긴다.**

| 한정어 (새로 쓴 문장) | 이 한정어가 표 밖으로 미는 시나리오 | 그 시나리오가 **실제 코드**에서 어떻게 되는가 | 정당한가 |
|---|---|---|---|
| `merged` 정의의 **"한 적재 안에서"** | 크로스-적재 병합(사명 변경 주: 별칭표 통합 + 옛 법인명 행이 대장에서 빠짐) | `_collision_groups` 는 정말로 한 적재 안의 수렴만 만든다. 그러나 그 경로는 `merged=0` 이어도 `_replaced_doc_ids`/`_absorbed_doc_ids` 가 잡는다(R1·P11) | **○ — `merged` 가 보고 값일 때만.** 같은 줄에 "판정 조건이 아니라 보고 값"과 (나-i)∪(나-ii)를 함께 적어, 이 한정어가 판정으로 새지 못하게 막았다. 이 한정어를 판정에 건 것이 개정 1 의 실패다 |

확인이 **"한 적재 안에서"는 정의로는 참이지만 판정으로 읽히는 순간 세 번째 blocker 를 그대로
재생산한다**는 것을 드러냈다. 그래서 정의는 남기되 같은 줄에서 **판정 조건이 아니라 보고 값**임을 못
박고 (나-i)∪(나-ii)를 함께 적었다.

##### (바-3) 이 표가 **놓친 것** — 네 번째 거짓은 이 표 안에 있었다 (재심 보정)

**리뷰어가 위 표 6행에서 네 번째 거짓을 찾았다.** 같은 조건절이 초판 "고아" → 개정 1 "새" → 개정 1
"한 적재 안에서"로 세 번 틀렸고, **그 재발을 막으려고 만든 이 표가 네 번째를 담고 있었다.**

**왜 표를 쓰면서도 놓쳤는가(architect, 2026-09-04) — 원인 둘, 둘 다 새 사실이다.**

1. **6행의 "실제로 어떻게 되는가" 칸을 다른 절 참조로 갈음했다.** 그 칸에 적힌 것은 실측값이 아니라
   "((사) 표)"라는 **가리킴**이었고, 가리킨 (사) 표의 해당 줄(`lost_decisions` 가 비었다 → "경고까지가
   적절한 크기다")도 같은 경로에서 코드와 달랐다. **문서 안에서 서로를 가리키는 두 줄은 서로의 근거가
   될 수 없다.** CLAUDE.md §6-1 의 "다른 절을 가리켜 확인을 갈음하지 않는다"가 정확히 이것인데,
   **그 위반이 §6-3 이 요구한 산출물(이 표) 안에서 일어났다.** 표를 만드는 것과 표의 각 칸을 태우는
   것은 다른 일이다.
2. **같은 문서가 26줄 위에서 이미 반박하고 있었다.** 바로 위 "놓치는 것" 4(RP3b)가
   "…그 `doc_id` 에 사람 판단이 없으면 `lost_decisions` 가 비어 `moved or merged or lost_decisions`
   게이트가 닫힌다"라고 **정확히 반대**를 적었다. 근거는 문서 안에 있었고 결론이 그것을 따라가지
   못했다 — 표를 채울 때 **자기 문서의 인접 절과 교차 확인하는 단계가 없었다.**

**그래서 나머지 9행을 전부 다시 태웠다.** 아래가 그 결과이고, 각 줄은 **참조가 아니라 이번 재심에서
실행한 값**이다(픽스처는 `tests/integration/test_17_document_identity_drift.py` 의 헬퍼를 재사용해

리뷰어도 뮤테이션을 단독 적용해 같은 결론에 닿았다. 즉 **거짓이 아니라 미검증**이었고, 고칠 것은 한

**새 사실 — 앞의 넷과 다른 점.** 앞의 네 번은 규칙을 쓴 뒤 **다음 개정·다음 산출물**에서 어겼다.
이번은 **그 규칙을 새로 쓴 바로 그 커밋이, 그 규칙이 지배하는 표를 재검증하려고 만든 표에서** 어겼다 —
CLAUDE.md §6-3 의 "표의 각 칸을 다른 절 참조로 갈음하면 그 행은 검증되지 않은 것이다"·§6-5 의
"대조표의 칸이 다른 절 참조로 갈음돼 있으면 그 행은 미검증으로 본다"와 이 (바-3) 표는 **둘 다
`685cbc5` 한 커밋에서 태어났다.** 규칙과 그 위반은 **같은 커밋 안에서 함께 태어날 수 있다.**
그리고 §6-3 이 요구하는 "각 칸을 태우기"는 **한 겹 더 안쪽**(그 표를 재검증하는 표)에도 그대로
적용되는데, 나는 그것을 "내가 검증하는 표"의 요구로만 읽고 "내가 지금 쓰는 표"에는 적용하지 않았다. 이 둘을 CLAUDE.md §6-3 에 근거 줄로 올렸다.

| "규칙과 그 위반" — **위반**이라고 부르는 것 | 내용이 거짓이었다면 "위반"이 아니라 "거짓"이고 처방이 다르다 | 내용은 참이고 근거 자리만 비었다 → 이 항목의 처방은 "판정을 뒤집는 것"이 아니라 **"칸을 채우는 것"** 이다. 그래서 6행 판정("거짓")은 (바-2) 6행의 서술에 대한 것이고, 여기서 새로 붙는 딱지는 그 서술이 아니라 **이 재검증 표의 근거 칸**에 대한 것이다 |
| "한 겹 **더 안쪽**" | 재검증 표에만 해당한다고 읽으면 세 겹째(이 문단을 재검증하는 표)가 다시 밖으로 나간다 | 그래서 §6-3 근거 줄은 겹수를 세지 않고 **"지금 쓰고 있는 표"** 로 적었다 — 이 문단 자체도 그 요구를 받으며, 바로 위 표가 그 이행이다 |

**5행에 딸린 오기 정정.** 시트명 변경 경로의 실측은 `moved=8` 이다(회귀 `test_v4_sheet_rename_*` 도
`len(drift["moved"]) == 8` 로 고정하고 있다). 이 ADR 이 세 자리에서 `moved=9` 라고 적고 있었고
(§5-2 `cause` 개명 표, (바) 표 P3 행, §5-3) `docs/glossary.md` 의 `오염된 판단` 줄도 그랬다.
소유가 다른 자리는 §5-6 작업 분배에 올렸다(`services/progress/document_mapper.py` 3곳,
`services/ingest/persistence.py` 1곳, `apps/web` 4곳 — 각 소유 에이전트가 이미 고쳤다).

**그런데 이 전수 목록도 한 자리를 빠뜨렸다 — `packages/core/models/review.py:25` 의 `ReviewKind`
머리 주석이고, 그것도 `architect` 소유다**(CLAUDE.md §2). 그래서 내 몫은 넷이 아니라 **다섯**이었다.
왜 빠졌는지는 아래 (바-4)에 적는다 — **같은 파일이 두 사이클 연속으로 내 전수 목록에서 빠졌기 때문에**
오타 하나로 넘기지 않는다.

##### (바-4) 같은 파일이 두 사이클 연속으로 전수 목록에서 빠진 이유 (재심 보정 2)

**사실.** `packages/core/models/review.py` 의 머리 주석은 두 번 연속으로 내 전수 목록 밖에 있었다.

| 사이클 | 무엇을 세는 목록이었나 | 그 파일이 담고 있던 것 | 어떻게 드러났나 |
|---|---|---|---|
| 개정 2 | §Deferred 5 의 **`cause` 정본 복제 자리** | 옛 이름 셋(`orphaned`/…) 서술 | 리뷰어 지적 → "세 곳 → 네 곳"으로 정정 |
| 재심(이번) | (바-3) 의 **`moved=9` 오기 자리** | `moved=9` | 리뷰어 지적 → 이 줄 |

**왜 빠졌는가 — 추측이 아니라 내가 실제로 밟은 절차다.** 이번에 목록을 만든 명령은 하나였다:

```
grep -c "moved=9" docs/glossary.md docs/adr/0009-….md ;  grep -rn "moved=9" services/ apps/
```

왼쪽은 **내가 그때 이미 열어 놓고 고치던 두 파일**을 이름으로 찍은 것이고, 오른쪽은 **남에게 넘길
트리 둘**을 재귀로 훑은 것이다. `packages/` 는 어느 쪽 경로에도 없었다. 즉 목록의 생성 기준은
"`moved=9` 라는 문자열이 이 저장소 어디에 있는가"가 **아니라** —

> **"내가 지금 고치는 파일 + 남에게 넘길 트리"**

였다. 이 기준은 **작업 분배의 모양**을 하고 있고, 그래서 **"내 것이지만 지금 열고 있지 않은 파일"**
이라는 칸이 애초에 없다. `packages/core/models/` 가 정확히 그 칸이다 — `architect` 소유인데 `docs/` 도
아니고 넘길 트리도 아니다. 개정 2 의 §Deferred 5 도 같은 모양이었다(생산 `services/ingest` · 소비
`services/progress` · 화면 `apps/web` 을 "값이 흐르는 세 층"으로 셌고, 데이터 모델 주석은 그 흐름도에
없었다). **두 번 다 같은 칸이다 — 우연이 아니다.**

**두 번째 요인(둘 다 필요했다).** 그 자리는 **주석**이라 어떤 테스트도 실패시키지 않는다(§Deferred 5 가
이미 적어 둔 사실이다). 목록이 빠뜨려도 CI 가 잡아 주지 않는다. 그래서 이 칸은 **목록 생성 기준으로만**
방어된다.

**정정.** 전수 목록은 앞으로 **저장소 루트에서** 만든다(`grep -rn <문자열> .`, 소유는 그 뒤에 나눈다).
소유 디렉터리를 머리로 나열해 경로를 좁히는 순간, 좁힌 기준이 목록의 한계가 된다 —
CLAUDE.md §6-1 그대로다. 그 근거 줄을 §6-1 에 추가했고, **`packages/core/models/` 를 이름 붙은
블라인드 스팟으로** 함께 적었다.

##### (사) 발화 규칙

**축을 갈라 적는다(재심 보정).** 초판은 "`lost_decisions` 가 비었다 → 경고까지가 적절한 크기다"라고
**한 줄로** 적었는데, 그 문장은 `moved`·`merged` 축에서만 참이다. (나)·(다) 축에는 판단이 없으면
**아무 관측도 남지 않는다.** 아래 표의 모든 칸은 이번 재심에서 **실행해 얻은 값**이다.

| 축 | 사람 판단(확정·반려)이 **걸려 있을 때** | 사람 판단이 **하나도 없을 때** |
|---|---|---|
| **(가) 이동** `moved ≥ 1` | `DOCUMENT_IDENTITY_DRIFT` 경고(이전/새 `doc_id` 쌍·이동 건수·이전/현재 지문·`fingerprint_changed`·오염된 판단 수) + 요청 1건. 실측(시트명 변경): `moved=8, lost=1`, DRIFT True, 요청 1건 | **DRIFT 경고까지는 뜬다.** 실측(`sender_aliases` 표준명 변경): `moved=7, merged=0, lost=0`, DRIFT **True**, COLLISION False, `review_id=None`, 요청 0건 |
| **`merged`(충돌 묶음)** `merged ≥ 1` | `DOCUMENT_IDENTITY_COLLISION` 경고를 **묶음마다**(`doc_id`·행 수·제목들 + **이 병합 한 건이 건드린 판단 수**) + 요청 1건. 실측: `merged=1, lost=1`, COLLISION **True**, DRIFT **False**, 요청 1건 | **COLLISION 경고까지는 뜬다.** 실측(상시 충돌 대장의 첫 적재): `merged=1, lost=0`, COLLISION **True**, DRIFT False, 요청 0건 |
| **(나) 대체 / (다) 흡수 단독**(`moved=0`, `merged=0` — 이번 사이클 blocker 의 모양) | `DOCUMENT_IDENTITY_DRIFT` 경고를 **이동 쌍을 언급하지 않고** 발화한다(경위별 건수만 — "0건 이동했고"라고 쓰던 옛 문구가 그 거짓이다) + 요청 1건. 실측(사명 변경 주): `moved=0, merged=0, lost=1`, DRIFT **True**, 요청 1건 | **아무것도 뜨지 않는다 — 적재 전체가 드리프트 축에서 침묵한다.** 실측(V8a 에서 CM 확정만 제거): `identity_drift=None`, `moved=merged=lost=0`, DRIFT **False**, COLLISION **False**, 요청 0건. **이 비대칭은 의도다 — 근거는 아래 "놓치는 것" 5** |

| 그 밖의 조건 | 결과 |
|---|---|
| 이동 후보 쌍의 `title` 원문이 **다르다** | 지금까지대로 `document_possibly_renamed` 경고. 사람이 제목을 고친 정상 상황. **단, 같은 적재에서 식별 표면도 바뀌면 이 경고의 키가 어긋나 뜨지 않는다**(위 (바-2) 4행 실측 — "놓치는 것" 6) |
| `lost_decisions` 가 **비어 있지 않다** (경위 무관) | **`ReviewRequest(kind="document_identity_drift", assignee_role="cm")` 를 적재당 1건 생성.** 본문(`conflicting_sources`)에 이전·현재 지문, `moved`, `merged`, 그리고 **`cause`·`new_doc_id`·`changed_fields`·`approval_flipped` 가 실린 `lost_decisions`** 를 싣는다. 실측: 경위가 둘이어도 **1건**(`[(row_replaced, confirmed), (row_absorbed, rejected)]` → 요청 1건) |
| `lost_decisions` 가 비었다 | **요청을 만들지 않는다**(큐 오염 방지). 경고가 남는지는 **축에 달렸다** — 위 표 오른쪽 열 |
| 같은 `current_fingerprint` 로 열린 요청이 이미 있다 | 새로 만들지 않고 최신 관찰로 갱신한다(적재당 1건 불변식) |

**`IdentityDriftReport` 를 만드는 게이트는 `moved or merged or lost_decisions` 다(개정 2 — 함께
넓히지 않으면 위 수정이 무효다).** 개정 1 의 게이트는 `if moved or merged` 였다. 그 조건에서는 (나)·(다)가
잡은 사건이 `moved`·`merged` 를 **둘 다 비운 채** 발생할 수 있고(위 R1·P11·P9 가 정확히 그 모양이다),
그러면 판정이 옳게 발화해도 보고서가 만들어지지 않아 **검토요청이 게이트에서 다시 조용히 삼켜진다.**
실측으로 확인했다 — 새 조건 + 옛 게이트로 R1 을 태우면 `identity_drift=None`,
`identity_drift_lost_decisions=0`, `identity_drift_review_id=None` 으로 **고치기 전과 똑같이 침묵한다.**
`lost_decisions` 는 정의상 (가)·(나)·(다)의 부분집합이므로 이 항을 게이트에서 뺄 수 있는 조건은 없다.

**왜 job 을 실패시키지 않는가.** ADR 0007 §1 규칙 1(대장이 정본)은 "대장 데이터의 성질 때문에 적재를
거부하지 않는다"는 규칙이다. 여기 원인은 대장이 아니라 우리 config 이므로 거부해도 규칙 위반은 아니다.
그럼에도 거부하지 않는 이유는 다른 데 있다 — 새 협력사 별칭을 추가한 주에 현장의 주간 대장 업로드가
통째로 막히면, 운영자는 config 를 되돌리는 대신 **탐지를 끄는 방향**으로 움직인다. 대신 잃어버린 사람의
판단이 실제로 있을 때만 CM 검토 큐에 올린다.

**왜 job 경고가 아니라 검토요청인가.** 이 저장소의 8차 리뷰가 이미 같은 실패를 겪었다 —
`needs_review=True` 매핑이 쌓여도 검토요청을 만드는 코드가 없어 CM 큐가 영원히 비어 있었고 어떤
테스트도 실패하지 않았다. job 경고는 업로드 응답에만 실려 지나가고 아무도 되돌아보지 않는다.
**사람이 봐야 하는 일은 사람의 큐에 넣는다.**

#### 5-3. `document_identity_drift` 검토요청의 성질

`ReviewKind` 에 값을 추가하지만 **해소에 부수 효과가 없다.** `services/api/usecases.resolve_review` 의
공통 폴백이 `status`/`resolution_note`/`resolved_by` 만 기록한다 — `document_mapping` 처럼 매핑 행을
건드리는 분기를 추가하지 **않는다**. 이 요청은 "봤다"를 남기는 확인 전용이고, 무엇을 할지(config
되돌리기 / §6 마이그레이션)는 본문이 안내한다. 이 kind 에 매핑을 되살리는 액션을 붙이는 설계는
반려한다 — 그것은 사람의 확정을 시스템이 복원하는 것이라 ADR 0001 불변식과 충돌한다.

**제목은 경위마다 갈라 쓴다(개정 1).** 하나로 뭉뚱그린 초판 제목("doc_id 가 N건 이동했고 … 고아 문서에
남았습니다 … 새 doc_id 위에서 다시 확정하십시오")은 병합 경로에서 세 군데가 거짓이었다 — 자세한 것은
§5-4. 경위가 섞이면 각 경위를 건수와 함께 **나란히** 적는다. 요청 본문의 `lost_decisions[].cause` 가
그것을 가능하게 하는 유일한 필드이고, 화면도 그 값(산문이 아니라 기계 판독 값)으로 카드를 가른다.

**개정 2 — 개정 1 의 제목도 두 군데가 거짓이었다(실측).**

1. `row_moved`(옛 `orphaned`) 절은 "…이 **고아 문서**에 남았습니다"라고 적는다. 그런데 §5-2 (가) 자신이
   "고아로 좁히지 않는다"고 고친 그 경로(워크북 시트명 변경)에서 옛 행은 **고아가 되지 않는다**
   (실측 P3: `moved=8`, `is_orphaned=False`). 판정은 고아를 안 보는데 문구는 고아라고 말한다.
2. `row_replaced`(옛 `merge_overwritten`) 절은 "**서로 다른 대장 행이 한 doc_id 로 병합돼**"로 시작한다.
   개정 2 의 조건이 잡는 주된 경로에는 **병합이 없다**(실측 R1·P6·P7·P9: `merged=0`). CM 은 있지도 않은
   충돌 묶음을 찾게 된다.

그래서 문구는 **경위 이름이 아니라 관측한 값**으로 쓴다. `row_moved` 는 "대장 행은 그대로인데 우리
식별 규칙이 그 행을 새 doc_id(`new_doc_id`)로 옮겼습니다"라고만 적고 고아 여부를 단정하지 않는다.
`row_replaced` 는 `changed_fields` 를 그대로 적는다("이 문서가 담고 있던 대장 행이 바뀌었습니다 —
발신 `동부` → `한빛이앤씨`, 문서번호 …"). 병합이라는 말은 그 `doc_id` 가 실제로 `merged` 묶음에 있을
때만 쓴다. `approval_flipped` 가 참일 때만 "도면 승인 근거가 뒤집혔습니다"를 붙인다 —
`new_doc_id`/`changed_fields`/`approval_flipped` 는 그러기 위해 §5-2 (마)가 실어 보내는 값이다.

##### 5-3-b. 개정 3(결정) — 개정 2 의 제목에도 **무조건 문장**이 하나 남아 있었다 (재심)

`row_replaced` 절은 지금 이 문장을 **한정어 없이** 붙인다:

> …CM 판단 1건(확정 1 · 반려 0)이 그 문서에 걸려 있고, **화면의 승인 상태는 CM 이 보고 판단한 그 대장
> 행의 것이 아닙니다.** 다시 판단할 새 doc_id 는 없습니다 …

**V8a·V8b(P7·P6)에서 이 문장은 거짓이다.** 그 시나리오는 대장이 **같은 행의 발신 표기/문서번호 오타를
스스로 고친 것**이고, 회귀가 그 사실을 값으로 단언한다 — `approval_flipped=False`, `drawing_approval`
0.0 → 0.0, `is_orphaned=False`, `changed_fields=['sender']`. 승인 상태 **값**은 CM 이 판단할 때와 한
글자도 다르지 않다. 같은 판단으로 남기기로 한 P8b(제목의 공백만 정정)·FP1(`번호` 표기 변경)도 전부
같은 모양이다(`doc_id` 불변 · 행-정체 원문만 이동 · 승인 상태 그대로).

**왜 이 자리에서만 뚫렸는가.** 바로 위 `else` 분기(대장 원문이 그대로일 때)와 바로 아래
`if not any(new_doc_id)` 에는 역방향 확인 주석이 붙어 있고, `approval_flipped` 를 쓰는 절에도 붙어
있다. **이 한 절에만 없다.** CLAUDE.md §6-3 은 한정어를 **빼는** 방향도 확인 대상이라고 적었는데,
"모든 `row_replaced` 에 공통으로 참인 문장"이라고 여겨 확인을 건너뛴 자리다.

**그리고 이것은 §5-2 (바)의 비용 계산을 흔든다.** 우리는 P6·P7·P8b·FP1 을 오탐인 채로 두면서 그 근거로
"오탐의 대가는 **부수 효과 없는 확인 요청 1건**"을 들었다. 그런데 그 요청의 **본문**이 CM 에게 "네가
본 승인 상태가 그 행의 것이 아니다"라고 말하면 CM 은 도면을 다시 연다. 대가는 요청 1건이 아니라
**CM 의 도면 재확인 1회**다. 오탐을 남기는 결정은 그대로 유지하되, **문구가 그 결정의 전제를 지키도록**
고친다.

**결정 — 이 문장을 값으로 가른다. 근거는 `approval_flipped` 이고, 경위 이름으로 단정하지 않는다.**

| `lost` 항목들의 값 | 붙일 문장 | 왜 그것이 참인가 |
|---|---|---|
| `any(d["approval_flipped"])` 가 **참** | 지금 문장을 유지한다(단, 앞의 "뒤집혔습니다" 절과 중복되지 않게 **"그 판단은 지금 화면에 떠 있는 승인 상태와 다른 값 위에서 내려졌습니다"** 로 적는다) | 관측한 사실 그대로다 — 이 `doc_id` 의 `approval_status` 가 이번 적재에 달라졌고 CM 의 판단은 옛 값 위에 있다 |
| 모든 항목이 `approval_flipped=False` **이고** `changed_fields` 가 비어 있지 **않다** | **"승인 상태 값 자체는 CM 이 판단할 때와 같습니다 — 달라진 것은 이 doc_id 가 담고 있는 대장 원문이고, 대장이 같은 행을 고쳐 적은 것인지 다른 행으로 바뀐 것인지는 이번 적재의 값으로 가릴 수 없습니다."** | 우리가 아는 것은 딱 여기까지다. §5-2 (바)가 "구별할 수 있는 관측값이 없다"고 적은 그 사실을 **문구도 그대로 말한다** |
| 모든 항목이 `approval_flipped=False` **이고** `changed_fields` 도 **비었다**((나-ii)로만 걸렸고 `result_raw` 만 바뀐 경우) | **"승인 상태 값은 CM 이 판단할 때와 같습니다"** 까지만 적고 대장 원문을 언급하지 **않는다** | **역방향 확인이 이 줄을 만들었다.** 이 조합에서 "달라진 것은 대장 원문"이라고 적으면 `changed_fields == []` 가 말하는 바로 그 사실(원문 네 필드는 그대로)을 뒤집는 거짓이 된다. 위쪽 `else` 분기가 이미 "대장 원문은 그대로인데 담은 내용이 달라졌다"고 적고 있으므로 이 절은 승인 상태만 말하면 된다 |

**왜 `changed_fields` 나 `new_doc_id` 를 근거로 쓰지 않는가(역방향 확인).**

- `changed_fields` 는 **무엇이** 달라졌는지만 답한다. `['sender']` 하나로는 대장측 오타 정정(V8a)과
  사명 변경 주의 행 교체(V7a)를 가를 수 없다 — **둘 다 `['sender']` 로 시작한다**(V7a 는
  `['sender','doc_number']`). 필드 이름을 조건으로 걸면 그 순간 "발신만 바뀌면 안 붙인다" 같은
  한정어가 생기고, 그것이 이 ADR 이 네 번 반복한 실패다.
- `changed_fields == []`((나-ii) 전용)에서는 대장 원문이 그대로다. 실측한 그 경로(P13)는
  `approval_flipped=True` 라 첫 줄로 간다 — **새 조건이 P13 을 밖으로 밀어내지 않는다.** 다만 (나-ii)의
  발화 조건은 행-내용 `(result_raw, approval_status)` 의 **어느 한쪽**만 바뀌어도 참이므로,
  `result_raw` 만 바뀌고 `approval_status` 는 그대로인 조합이 가능하다 — **추론으로 두지 않고 태웠다.**

  **실측(P13b, 이번 재심에서 새로 만든 시나리오).** 문서번호 열이 없는 대장에서 행-정체 네 필드가
  같은 두 행을 시트 둘에 두고 처리결과만 `반려`(TFA) / `부적합`(TFR)로 적었다 — 둘 다 `DOCST-001` 로
  `REJECTED` 다. `sheet_doc_types` 로 합치면:

  ```
  1주차            TFA=('반려','REJECTED')  TFR=('부적합','REJECTED')
  moved=0  merged=1  lost_decisions=1
  cause=row_replaced  changed_fields=[]  approval_flipped=False
  drawing_approval 0.0 → 0.0            (뒤집히지 않는다)
  ```

  즉 **`changed_fields` 도 비고 `approval_flipped` 도 거짓인 `row_replaced` 가 실제로 존재한다.**
  그 적재의 제목에도 지금 그 무조건 문장이 그대로 붙는다(**같은 거짓의 다섯 번째 자리**) — 승인 상태
  값은 CM 이 판단할 때와 한 글자도 다르지 않다. 위 표 셋째 줄이 이 경우를 받는다. 이 줄을 두지
  않았으면 여기에 "달라진 것은 대장 원문"이라는 **또 다른** 거짓이 붙었을 것이다.

  **곁가지 관찰(같은 제목의 앞 절, `progress-engine` 이 함께 볼 것).** 이 적재의 첫 절은
  "그 doc_id 가 담은 내용(**처리결과·승인 상태**)이 달라졌습니다"라고 적는데 실제로 달라진 것은
  `result_raw` 뿐이다. 괄호를 "무엇이 달라졌는가"가 아니라 "행-내용이란 무엇인가"의 설명으로 읽으면
  참이지만, CM 에게는 승인 상태가 달라졌다는 말로 읽힌다. 이 절도 `approval_flipped` 로 가르는 것이
  자연스럽다 — 결정은 위 표와 같은 근거를 쓴다.
- `new_doc_id` 는 `row_replaced` 에서 **언제나 `None`** 이라 이 절을 가르는 데 쓸 수 없다(그 값은
  "다시 판단할 곳이 있는가"에만 답한다).
- **발화 자체는 가르지 않는다.** `approval_flipped` 는 지금도 문장의 **순서만** 가르는 값이고
  (`document_mapper` 주석), 여기서도 **문장 하나의 표현만** 가른다. 이것을 발화 게이트로 올리면
  §5-2 (바) 근거 2 가 밀어낸 변종(승인 상태가 **우연히 같은** 다른 행으로 바뀐 경우)이 다시 표 밖으로
  나간다. 그 경우 CM 은 여전히 요청을 받고, 문구는 **가릴 수 없다고 적는다** — 그것이 참이다.

**구현은 `progress-engine` 이 한다**(`services/progress/document_mapper.py`). `architect` 는
`services/` 를 수정하지 않는다. 회귀는 `qa` 가 붙인다 — V8a·V8b 는 지금 `"뒤집혔습니다" not in title`
만 걸고 있어 **이 거짓 문장을 그대로 통과시킨다**(§6-4 규칙 3: 문장을 베끼지 말고 "그 상황에서 참일
수 없는 말이 없다"를 단언한다).

**서버는 세 갈래, 화면은 네 갈래다 — 이 비대칭은 의도다(재심 보정 3-b — "실측" 태그를 뗀다).**
위 결정표는 `approval_flipped` 를 **boolean 으로 읽을 수 있다**는 전제 위에 서 있다. 그 전제는
**생산 시점에는 언제나 참**이다: `LostDecision` TypedDict 가 `approval_flipped: bool` 을 필수로
요구하고(`services/progress/document_mapper.py`), 필드가 빠지면 pydantic 이 **적재 job 을 시끄럽게
실패시킨다**(§5-2 (마) 항목 계약 — "조용히 죽지 않는 쪽이 맞다"). 그래서 서버 문구에는 "모른다"
갈래가 필요 없고, 있으면 **도달할 수 없는 분기**다.

**화면은 그 전제를 쓸 수 없다.** 화면이 읽는 것은 생산 시점의 값이 아니라
`review_requests.conflicting_sources` 에 **저장된 JSON** 이다. 부재를 `false` 로 읽으면 화면은
**관측하지 못한 것을 단정한다**("승인 상태 값은 CM 이 판단할 때와 같습니다") — 개정 2 가 옛 `cause` 를
새 갈래로 **번역하지 않기로** 한 것과 정확히 같은 실패다. 그래서 화면에는 네 번째 갈래
`approvalFlippedUnknown`(모든 항목이 `approval_flipped` 를 boolean 으로 싣지 않았다 → **승인 상태에
대해 아무 말도 하지 않는다**)이 있다.

**그러나 이 갈래는 "지금 실제로 일어나는 일"이 아니다 — 실측이 아니라 선제 방어다(재심 보정 3-b).**
이 절의 초판은 "개정 2 **이전에 저장된** 요청에는 `approval_flipped` 필드가 아예 없다 → 화면이 관측하지
못한 것을 단정한다"라고 적고 절 제목에 **실측 태그**를 달았다. **그 시나리오는 그 결과를 내지 않는다.**
근거 셋, 전부 이번에 실행·코드로 확인했다:

1. **구버전 요청은 그 문장에 닿지 않는다.** 그 요청들은 `cause` 도 옛 이름(`orphaned`·
   `merge_overwritten`·`merge_absorbed`)이라 `classifyIdentityDriftCause` 가 `unspecified` 로 보낸다
   (`SERVER_CAUSE_TO_LOCAL` 에 옛 이름이 없다 — §5-3-a 의 결정 그 자체다). 승인 상태 문장은
   `identityDriftGroupFacts` 의 `group.cause === "row_replaced"` 블록 **안에만** 있다.
2. **새 `cause` 를 싣고 `approval_flipped` 는 안 싣는 저장 기록은 생긴 적이 없다.** 둘은 같은 커밋에서
   함께 들어왔다 — `git show 71fc0de:services/ingest/persistence.py` 에 `approval_flipped` 7회 ·
   `_CAUSE_ROW_REPLACED` 2회이고, `71fc0de~1` 에는 **둘 다 0회**다. 생산 자리도 하나뿐이라
   (`services/ingest/persistence._lost_decisions` 의 단일 `lost.append({...})`) 네 키가 언제나 함께 실린다.
   저장 경로도 그 dict 를 통째로 넣고(`document_mapper` 가 `sources` 에 `"lost_decisions": drift.lost_decisions` 를 그대로 담는다),
   갱신 경로는 본문을 **통째로 교체**하므로 절반만 새 모양인 기록도 생기지 않는다.
3. **그래서 이 갈래를 죽이는 것은 손으로 만든 단위 입력뿐이다.** 구버전 요청 회귀
   (`ReviewsPage.test.tsx` 의 `LEGACY_DRIFT_REVIEW`)는 `approvalFlippedUnknown` 을 `false` 로 만들어도
   초록이다 — 그 묶음이 `unspecified` 라 두 블록 어느 쪽에도 들어가지 않기 때문이고, **그게 맞다.**

**그러므로 이 갈래는 "관측된 오류의 수정"이 아니라 "다음 필드 추가를 위한 선제 방어"다.** 아래 규칙
문장은 그대로 유효하고, 바뀌는 것은 **왜 지금 이 코드가 있는가**뿐이다.

**계약은 단위 테스트가 진다 — 통합 회귀를 세우지 않는다.** 지금 생산자 계약으로는 이 저장 기록을
만들 수 없으므로, 통합 픽스처로 재현하려면 **생산자 계약을 깨야** 하고 그러면 그 픽스처가 *존재할 수
없는 데이터*를 계약으로 고정하게 된다(CLAUDE.md §6-4 규칙 3 이 경계하는 자리). `identityDrift.test.ts`
가 `cause: "row_replaced"` + `approval_flipped` 부재를 직접 구성해 `approvalFlippedUnknown === true` 와
"승인 상태를 어느 쪽으로도 말하지 않는다"를 고정하는 것으로 충분하다.

**역방향 확인 — "닿지 않는다"는 어떤 조건에서 닿게 되는가.** (§6-3: 새로 쓴 조건절도 예외가 아니다)

| 조건 | 지금 그 조건은 | 닿으면 무엇이 막는가 |
|---|---|---|
| ① 저장된 요청 본문의 옛 `cause` 를 새 이름으로 **마이그레이션**한다 | 없다 — §마이그레이션 표 6번이 "확인 전용 기록이므로 옛 값을 그대로 두는 선택도 가능하다"로 두었고 지금 마이그레이션은 없다. 이 결정을 뒤집는 순간 `row_replaced` + `approval_flipped` 부재가 **처음으로 실재**한다 | `approvalFlippedUnknown` 뿐이다. 그런 마이그레이션은 `approval_flipped` 를 함께 채울 수 **없다** — 그 적재의 승인 상태 이력은 남아 있지 않다 |
| ② 화면이 옛 이름을 새 갈래로 번역한다(`SERVER_CAUSE_TO_LOCAL` 에 옛 이름 추가) | 없다 — §5-3-a 가 근거 넷으로 금지했다 | 같음. ①과 ②는 **같은 사건의 서버판·화면판**이고, 둘 중 하나만 막아도 나머지가 열려 있다 |
| ③ `LostDecision` 에 **새 필드**를 더한다 | 다음 개정에서 얼마든지 일어난다. 그 순간 **오늘 저장되는 요청들**이 그 새 필드에 대해 "구버전"이 된다 | 갈래의 **모양**(값 있음 / 명시적 `null` / 부재)이 그대로 필요하다. **이것이 이 갈래를 남기는 진짜 이유다** |
| ④ `lost_decisions` 를 만드는 생산자가 하나 더 생긴다 / DB 본문을 손으로 고친다 | 없다(생산 자리 1곳). 위 "pydantic 이 시끄럽게 실패시킨다"가 성립하는 것은 값이 `IdentityDriftReport.lost_decisions: list[LostDecision]` 을 **통과할 때**뿐이다 — 그 모델을 거치지 않고 `conflicting_sources` 에 dict 를 직접 넣는 새 경로에는 그 방어가 없다 | 같음 |

**반대편도 답한다 — 이 갈래를 지금 지우면 무엇을 잃는가.** ①~④ 중 하나가 일어난 날, 화면은 부재를
`false` 로 읽어 "승인 상태 값은 CM 이 판단할 때와 같습니다"를 **관측 없이** 적는다. 그것이 이 보정이
서버 문구에 대해 방금 고친 바로 그 거짓이다. 대가는 **지금 도달하지 않는 분기 하나**이고 이득은 그
거짓이 다시 태어나지 않는 것이다 — **남긴다.**

**규칙으로 적는다.** `lost_decisions[]` 의 필드를 **생산 시점의 계약**으로 읽는 소비자(서버 문구)와
**저장된 과거 기록**으로 읽는 소비자(화면·리포트)는 갈래 수가 다를 수 있고, **후자는 언제나 "값이
없다" 갈래를 하나 더 가진다.** 새 필드를 `LostDecision` 에 더할 때마다 이 질문을 함께 답한다 —
"개정 이전에 저장된 요청에서 이 필드가 없을 때, 소비자는 무엇을 말하는가?" 기본값으로 떨어뜨리는
답은 금지다(§Deferred 5 폴백 금지 규칙과 같은 규칙이며, 그 규칙이 `cause` 에 대해 답한 것을
`approval_flipped` 에 대해 답한 것이 `approvalFlippedUnknown` 이다).

> **"언제나"의 역방향 확인(§6-3).** 이 "언제나"는 관측의 일반화가 **아니라 정의**다 — 저장된 기록은
> 필드보다 오래될 수 있고, 그 가능성은 필드를 더하는 **모든** 개정에서 새로 생긴다(위 표 ③). 관측
> 표본으로 뒷받침한 문장이 아니므로 표본 수를 근거로 좁히지 않는다. 반대로 이 문장이 **틀리는** 조건은
> 하나뿐이다: 저장된 본문에 마이그레이션이 있어 모든 기록이 최신 모양임이 보장될 때. 이 저장소의
> `conflicting_sources` 는 그렇지 않다(§마이그레이션 표 6번).

**같은 규칙을 `changed_fields` 에도 적용한다(재심 보정 3-b, minor 1 — 판단은 여기, 구현은 `frontend`).**
`groupLostDecisionsByCause` 는 `item.changed_fields ?? []` 로 **부재를 조용히 `[]` 로** 만든다. 그런데
`[]` 는 이 화면에서 **관측된 사실**로 문장이 된다 — `identityDriftGroupFacts` 의 `row_replaced` 꼬리
"대장 원문(발신·문서번호·번호·제목)은 그대로인데, 그 doc_id 가 담은 내용이 달라졌습니다". 부재는 그
사실이 아니라 **모른다**다. **"이 필드는 왜 갈래가 없는가"라고 적을 근거를 찾지 못했으므로 규칙을 그대로
적용한다**: `changedFieldsUnknown`(모든 항목이 `changed_fields` 를 배열로 싣지 않았다)일 때 그 꼬리
문장을 적지 않는다.

**세 필드가 같은 모양인지 역방향으로 확인했다.** `new_doc_id` 는 `null` 이 사실("다시 판단할 곳이 없다")
이라 부재와 `null` 을 갈라야 하고(`noNewDocId`), `approval_flipped` 는 `false` 가 사실이라 부재와
`false` 를 갈라야 하고(`approvalFlippedUnknown`), `changed_fields` 는 `[]` 가 사실((나-ii): 행-정체는
그대로, 행-내용만 달라졌다)이라 부재와 `[]` 를 갈라야 한다. **셋 다 같은 모양이다** — 한 객체의 세 필드
중 둘에만 적용할 이유가 없다.

**닿는가 — `approval_flipped` 와 같다.** 그 꼬리 문장도 `group.cause === "row_replaced"` 안에 있어
구버전 요청(옛 `cause` → `unspecified`)은 닿지 않고, 새 `cause` 를 싣고 `changed_fields` 를 안 싣는
저장 기록은 위 근거 2와 **같은 이유로**(같은 커밋·같은 단일 생산 자리) 존재한 적이 없다. 그러니 이것도
선제 방어이고 계약은 단위 테스트가 진다 — 통합 회귀를 세우지 않는 이유도 같다. 다만 경위 게이트 **밖**에
있는 "달라진 대장 원문: …" 목록은 `unspecified` 묶음에도 닿는데, 거기서는 **값이 있을 때만** 적으므로
부재는 이미 침묵이다(고칠 것이 없다).

##### 5-3-a. 개명 **이전에 저장된** 요청이 화면에 닿는 경로 (개정 2 보정 — 어느 문서에도 없었다)

`cause` 개명은 **생산 시점의 값**을 바꿨을 뿐이고, 개명 전에 만들어진 `document_identity_drift` 요청은
`review_requests.conflicting_sources` JSON 안에 **옛 `cause`(`orphaned`/`merge_overwritten`/
`merge_absorbed`)와 개정 2 에서 늘어난 필드(`new_doc_id`·`changed_fields`·`approval_flipped`)의 부재**를
그대로 담은 채 DB 에 남아 화면에 도달한다. 이 요청 본문에는 마이그레이션이 없다(§마이그레이션 표 6번이
같은 자리를 두고 "확인 전용 기록이므로 옛 값을 그대로 두는 선택도 가능하다"고 적었다).

**결정: 화면은 옛 이름을 새 갈래로 번역하지 않는다.** 셋 다 `unspecified`("경위 미상")로 두고 서버가 보낸
원문 문자열을 그대로 드러낸다(`classifyIdentityDriftCause` — 옛 이름을 `SERVER_CAUSE_TO_LOCAL` 에 넣지
않는다). 근거 넷:

1. **번역하면 개명이 걷어낸 거짓이 그대로 되살아난다.** `orphaned` 를 `row_moved` 로 옮기면 화면은
   "대장 행은 그대로인데 식별 규칙이 그 행을 새 `doc_id` 로 옮겼습니다"라고 적는다. 그런데 그 옛 요청은
   **개정 1 이전 조건**이 만든 것이라 그 문장이 그 적재에서 참이었는지 아무도 확인한 적이 없다. 이름을
   바꾼 이유가 "이름이 관측과 어긋난다"였으므로, 옛 이름을 새 이름으로 사상하는 것은 **그 어긋남을 새
   이름 아래로 옮기는 것**일 뿐이다.
2. **옛 값 → 새 값 사상은 관측이 아니라 추측이다.** 개정 1 의 세 경위와 개정 2 의 세 경위는 잡는 집합이
   다르다(§5-2 (바) R1·P11·P4·P5 — 침묵하던 것이 발화하고, 발화하던 것이 음성이 된다). `merge_overwritten`
   요청은 **충돌 묶음을 전제로** 만들어졌고 `row_replaced` 는 그 전제를 버렸다. 1:1 로 옮길 근거가 없다.
3. **필드의 부재는 `null` 이 아니다.** 옛 항목에는 `new_doc_id` 키 자체가 없다. 이것을 "비었으니 없다"로
   읽으면 화면이 "다시 판단할 새 doc_id 는 없습니다"라는 **관측한 적 없는 사실**을 단정한다 — §5-2 (마)가
   `new_doc_id=null` 을 "모른다"가 아니라 "없다"는 **사실**로 계약한 것의 반대편이다. 그래서 화면은
   **모든 항목이 명시적 `null`** 일 때만 그 문장을 적는다(`LostDecisionGroup.noNewDocId`).
4. **이 요청은 확인 전용이라 번역의 이득이 작고 대가가 크다.** 액션이 없고 "봤다"를 남기는 것이 목적이다
   (§5-3). 라벨이 "경위 미상"이어도 CM 은 본문의 `doc_id`·Activity 를 열어 직접 확인할 수 있고,
   `unspecified` 문구가 지시하는 행동이 정확히 그것이다("어느 쪽으로도 가정하지 말고 직접 열어 확인").
   반대로 잘못 번역된 라벨은 CM 이 **확인을 건너뛰게** 만든다.

**검토요청 제목 쪽도 같은 규칙이다(개정 2 보정 2 — 어느 문서에도 적혀 있지 않았다).** 위 결정은
화면(`classifyIdentityDriftCause`)의 것이고, 서버가 만드는 제목도 같은 말을 한다:
`_identity_drift_clause` 는 아는 경위 셋에만 전용 절을 쓰고 **그 밖의 값은 번역하지 않고 원문을 그대로**
따옴표에 넣어 "이 문구가 설명할 수 없는 경위입니다 — `lost_decisions` 를 직접 보십시오"로 적는다
(= "경위 미상 + 원문 노출", 위 결정과 같은 처리). 다만 **`cause` 키 자체가 없는 항목**에서는 드러낼
원문이 없어 그 자리에 우리 자리표시자가 그대로 들어간다(`lost.get("cause") or _CAUSE_UNSPECIFIED`).
**그래서 제목의 `경위 'unspecified'` 는 "생산자가 그 리터럴을 보냈다"가 아니라 "경위 값이 오지 않았다"를
뜻한다** — 이 문단이 그 사실을 적어 두는 자리다. 두 경우(값이 없다 / 모르는 값이 왔다)에 CM 이 할 일은
같으므로(어느 쪽으로도 가정하지 말고 `lost_decisions` 를 직접 연다) 지금은 문구를 가르지 않는다.
가를 이유가 생기면 그때 나눈다 — 지금 나누면 관측된 적 없는 사건을 위한 분기가 하나 더 생긴다.
**어느 쪽이든 `row_moved` 로 떨어뜨리는 폴백은 금지다**(§Deferred 5).

**기각한 대안: 마이그레이션으로 옛 요청의 `cause` 를 새 값으로 다시 써 넣는다.** 근거 2 로 기각한다.
게다가 이 요청은 "그 시점의 관측"을 남기는 기록이므로, 지금의 사실로 고쳐 쓰면 기록이 아니게 된다
(§마이그레이션 표 6번과 같은 판단 — 어느 쪽이든 **판단해서 적어야 하고 목록에서 빠져서는 안 된다**).

이 결정은 §Deferred 5 의 폴백 금지 규칙과 같은 규칙이다: **모르는 `cause` 는 모른다고 적고, 가장 흔한
값으로 떨어뜨리지 않는다.** 옛 이름 셋은 지금 그 "모르는 값"에 속한다.

#### 5-4. 개정 1 — 초판 §5-2 가 어떻게 틀렸나 (지우지 않고 남긴다)

이 사이클 막바지에 잡힌 blocker 는 구현 실수가 아니었다. **담당들은 초판 §5-2 표대로 구현했고, 그 표가
틀렸다.** 초판 표의 세 행을 그대로 옮긴다:

| 초판 조건 | 초판 결과 | 무엇이 틀렸나 |
|---|---|---|
| `title` 원문이 **같다** | `DOCUMENT_IDENTITY_DRIFT` 경고 | 조건의 좌변을 "**고아** ↔ 신규"로 적었다. 시트명 변경 경로는 고아를 만들지 않는다(실측 `orphaned=0`, `moved=8`) |
| 위에 더해, **고아가 된 문서**에 `reviewed_by is not None` 인 매핑이 있다 | 검토요청 1건 생성 | **이것이 blocker 의 원인이다.** `merge_overwritten` 은 고아가 아니므로 이 규칙대로면 **영원히 큐에 닿지 못한다** |
| 두 개 이상의 `doc_id` 가 하나의 **새** `doc_id` 로 수렴 | 같은 경고를 **병합 사유로 발화**(경고까지만) | ① "**새**"라는 한정어가 운영에서 실제로 일어나는 변종(이미 있던 id 로 수렴)을 표 밖으로 밀어냈다 ② 가장 위험한 경로를 **경고 쪽**에 배정했다 |

세 번째 행이 특히 뼈아프다. **같은 절이 스스로** "job 경고는 업로드 응답에만 실려 지나가고 아무도
되돌아보지 않는다. 사람이 봐야 하는 일은 사람의 큐에 넣는다"고 적어 놓고, 바로 그 문장 위의 표에서
**가장 위험한 경로를 경고 쪽에 뒀다.** §3 은 이미 병합을 "복구 불가 / 미승인 도면 위에서 착수 가능"으로
분류해 두었으므로, 근거는 ADR 안에 전부 있었는데 결론이 그것을 따라가지 못했다.

그리고 초판 §5-2 는 요청 본문을 **"잃어버린 확정·반려 건수와 doc_id 목록"** 으로만 적었다. `cause` 가
없으면 소비자는 세 경위를 하나로 뭉뚱그릴 수밖에 없고, 그 결과 §5-2 가 만든 **새** 검토요청 제목이
병합 경로에서 세 군데 거짓을 갖고 태어났다: ① 고아가 아닌 것을 고아라 하고 ② 존재하지 않는 새 `doc_id`
위에서 "다시 확정하라"고 하고 ③ `moved == 0` 인 적재에 "0건 이동했고"라고 적었다.

이 절이 이 ADR 에 남는 이유: **조건을 좁게 적으면 가장 위험한 변종이 표 밖으로 나간다.** 이 사이클의
다른 반복 패턴들과 함께 **CLAUDE.md §6** 에 규칙으로 올렸다.

#### 5-5. 개정 2 — 개정 1 §5-2 가 어떻게 틀렸나 (지우지 않고 남긴다)

개정 1 은 이 사이클의 blocker 를 고치면서 **같은 자리에서 같은 종류의 오류를 다시 만들었다.** 담당들은
개정 1 §5-2 표대로 구현했고, 그 표가 틀렸다. 초판(§5-4)과 나란히 읽어야 모양이 보인다.

| | 조건절 | 밖으로 밀려난 것 |
|---|---|---|
| **초판** | 검토요청을 "**고아**가 된 문서에 사람 판단이 있으면" | `merge_overwritten` — 행이 살아 있고 내용만 바뀐다. **영원히 큐에 닿지 못했다** |
| **초판** | 병합을 "두 `doc_id` 가 하나의 **새** `doc_id` 로 수렴" | 운영에서 실제로 일어나는 병합은 **이미 있던** id 로 수렴한다 |
| **개정 1** | 병합을 "**한 적재 안에서** 두 개 이상의 대장 행이 같은 `doc_id` 로 수렴" | **사명 변경 주**의 실제 운영 — 별칭표를 통합하면서 옛 법인명 행이 대장에서 빠진다. 두 행이 한 적재에 함께 있지 않으므로 충돌 묶음이 만들어지지 않는다 |

**개정 1 의 오류가 만든 데이터(실측, TestClient).**

```
1주차 대장: A(동부, 반려, seq 26180, 제목 T) / B(한빛이앤씨, 승인, seq 26180, 제목 T) → 서로 다른 doc_id
CM: A 매핑을 확정해 A300 차단 → drawing_approval 0.0, blocker document_unapproved
2주차: sender_aliases 에 "한빛이앤씨"를 동부건설 아래로 통합(한 줄)
       + 대장에서 옛 법인명 행 A 가 사라짐(새 이름 B 만 올라온다)
결과(개정 1 코드):
  survivor approval: APPROVED   orphaned: False   doc_number: 한빛-…-26-181
  drawing_approval 0.0 → 1.0    drift: None   review_id: None   DOCUMENT_IDENTITY_* 경고 0건
대조군(같은 삭제, config 만 안 바꿈):
  approval REJECTED  orphaned: True  drawing_approval 0.0 → 0.5   ← 보수적 실패라 관측 가능
```

**승인 상태를 뒤집은 것은 대장이 아니라 우리 config 인데, 그 사실이 통째로 사라진다.** `a8c89bb` 가 고친
blocker 와 데이터 모양·결과가 같다 — 행도 `reviewed_by` 도 살아 있고, 고아 표시 없고, 담긴 대장 행만
바뀐다. 다른 점은 두 행이 **같은 적재에 함께 있지 않다**는 것뿐이다. 판단이 **사라지는** 쪽(대칭 짝)도
같았다 — 고아만 되고 검토요청은 없다.

같은 조건절에 딸려 온 오탐 둘도 함께 정정했다(§5-2 (라)·(다)).

- 충돌이 **상시화된** 대장에서는 조건 ①(충돌 묶음)이 항상 참이라 가드가 ②(행 지문)만 남는다 → 대장의
  정상 처리결과 갱신이 오염으로 보고되고, 문구도 거짓이다("내용이 **다른 대장 행**으로 바뀌었습니다" —
  실제로는 같은 행의 처리결과 갱신).
- `merge_absorbed` 의 문서번호 완화("한쪽이 비면 통과")는 **문서번호 열이 없는 현장에서 "제목만 같으면
  통과"로 퇴화**해, 무관한 충돌이 하나 있는 적재에서 진짜 삭제를 흡수로 오보고한다.

**이 절이 남는 이유 — 세 번의 공통 모양.** 세 번 모두 ① 한정어를 **하나** 더 붙였고 ② 그 한정어가
§3 이 "복구 불가 / 미승인 도면 위에서 착수 가능"이라고 분류해 둔 경로를 표 밖으로 내보냈으며
③ 근거는 **문서 안에 이미 다 있었다**. 특히 세 번째는 CLAUDE.md §6-3 이 이미 쓰여 있는 상태에서, **그
규칙을 쓴 사람이 바로 다음 개정에서** 저질렀다. 규칙을 아는 것으로는 부족하다 —
**한정어마다 역방향 확인을 문서에 적고, 그 확인을 실행으로 태워야 한다.** 개정 2 는 그 절차를 §5-2 (바)
표로 못박았고, 그 표가 실제로 한 건을 잡아냈다(P13: 새 조건만으로 갈아탔으면 개정 1 이 잡던 경로를
잃을 뻔했다 — 그래서 조건이 합집합이 됐다). CLAUDE.md §6-3 에 이 재발을 근거 줄로 추가했다.

## Consequences

- **매칭 임계값 보정이 안전해졌다.** ADR 0007 이 예고한 "실데이터가 들어오면 `min_similarity` 를 다시
  잰다"는 작업이 이제 정체성을 건드리지 않고 진행된다. 실측으로 확인했다 — 매칭 설정 8가지를 흔들었을 때
  새 `compute_doc_id` 기준 `doc_id` 변경은 전부 0/10:

  ```
  OK  strip_patterns += '승인요청'         doc_id 변경 0/10
  OK  strip_chars 에서 괄호 제거             doc_id 변경 0/10
  OK  lowercase: false                 doc_id 변경 0/10
  OK  strip_patterns += 차수제거           doc_id 변경 0/10
  OK  min_similarity 0.22→0.30         doc_id 변경 0/10
  OK  seq_weight/token_weight 재조정      doc_id 변경 0/10
  OK  discriminative_tokens 추가         doc_id 변경 0/10
  OK  mapping_weights 재조정              doc_id 변경 0/10
  ```

- **위험이 없어진 것이 아니라 좁아졌다.** 같은 실측의 나머지 절반:

  ```
  변동   normalization.sender_aliases (표준명 변경)        doc_id 변경 7/10
  변동   register_layout.sheet_doc_types (별칭 변경)      doc_id 변경 8/10
  변동   register_layout.column_aliases.sender        doc_id 변경 10/10
  ```

  가장 자주 만지는 손잡이(매칭 튜닝)를 표면에서 뺐을 뿐, 표면 자체는 남아 있다. 남은 것에 대한 답은
  동결이 아니라 §5-2 탐지다. **이 문단을 지우고 "정체성 문제는 해결됐다"고 적는 후속 개정은 틀렸다.**

- **`doc_id` 형식이 `doc-<16hex>` 에서 `doc-v1-<16hex>` 로 바뀐다.** 오늘 존재하는 모든 `doc_id` 가 한 번
  바뀐다(§6). 이 변경 자체가 이 ADR 이 막으려는 사고와 같은 모양이라는 점을 숨기지 않는다 — 차이는
  **의도했고, 한 번뿐이고, 마이그레이션 판단을 명시했다**는 것이다.

- **`ReviewKind` 가 다섯 개가 되어 프론트엔드의 라벨 표(`REVIEW_KIND_LABELS: Record<ReviewKind, string>`)가
  누락을 컴파일 단계에서 잡아 준다.** TS 타입에 값을 추가하지 않으면 새 kind 가 화면에서 `undefined`
  라벨로 뜬다 — 계획의 frontend 항목이 이를 처리한다.

- **`title_identity` 가 API 응답(`DocumentView`)에 노출된다.** 의도한 것이다: "이 문서가 어떤 문자열로
  해시됐는가"가 화면·로그에서 보여야 드리프트를 사람이 눈으로 확인할 수 있다.

- **(개정 1) 병합이 CM 큐에 오르지만, 뒤집힘 자체는 막지 않는다.** 살아남은 행은 대장의 다른 행이고
  대장이 정본이다(ADR 0007 §1 규칙 1). `drawing_approval` 이 0.0 → 1.0 으로 뒤집히는 것은 그대로 일어나고,
  이 ADR 이 바꾼 것은 같은 적재가 그 사건을 사람의 큐에 올린다는 점뿐이다. **이 문단을 지우고 "병합은
  이제 안전하다"고 적는 후속 개정은 틀렸다.**

- **(개정 1) `lost_decisions[].cause` 는 화면·문구의 계약이다.** 검토요청 제목, `DOCUMENT_IDENTITY_*`
  경고 문구, 프론트엔드 카드가 모두 이 값으로 갈린다. 소비자는 **산문을 부분 문자열로 되읽어 분류하지
  않는다**(이 저장소가 `Blocker.kind` 도입으로 이미 걷어낸 패턴이다). 새 경위를 추가하는 변경은 세
  소비자를 함께 고쳐야 하며, 모르는 `cause` 를 `orphaned` 로 떨어뜨리는 폴백은 금지다 — 모르는 것을
  고아라고 적으면 §5-4 가 고치려는 바로 그 거짓이 된다.

## Alternatives considered

1. **`identity_normalization` 을 config 에 두고 `_assert_invariant` 로 지킨다.** 기각 — §2. 코드가 읽어야
   하는 값이라 §9 패턴이 성립하지 않고, 진실 원천이 둘로 늘어난다.
2. **`title_matching.normalize` 를 그대로 두고 "바꾸지 마라"고 문서에만 적는다.** 기각 — ADR 0007 §2-1 이
   이미 그렇게 적어 두었고(개정 1), 그럼에도 이 ADR 의 §2 재현이 성립한다. 문서는 손잡이를 없애지 못한다.
3. **제목을 `doc_id` 재료에서 뺀다.** 기각 — §4. 승인·반려가 뒤섞인 6건이 한 행으로 붕괴한다.
4. **`doc_number` 를 자연키로 쓴다.** 기각 — ADR 0007 §2-1 이 이미 기각했다(수식 파생·공란·중복).
   §3 (나) 재현에서 두 재제출 행의 `문서번호` 를 다르게 두자 `duplicate_doc_number` 경고가 사라진 것이
   이 필드의 신뢰도를 그대로 보여 준다.
5. **드리프트를 감지하면 대장 적재 job 을 실패시킨다.** 기각 — §5-2. 탐지를 끄는 방향으로 운영이 움직인다.
6. **`doc_id` 대신 `(project_id, doc_type, sender_normalized, seq_normalized)` 자연 복합키.** 기각 —
   §4 의 충돌 실측이 그대로 적용되고, 게다가 §4-1 대로 `seq` 가 행번호로 폴백될 수 있다.
7. **버전 접두사 대신 `documents.doc_id_scheme` 컬럼.** 기각 — 컬럼은 `documents` 안에서만 유효하다.
   `doc_id` 는 `activity_document_mappings`·`review_requests.conflicting_sources`·`Evidence.source_id`·
   프론트 URL 로 흘러 나가며, 그 자리에서도 스킴을 알아야 한다. 문자열 자체에 실어야 한다.

## 마이그레이션

**판단: 마이그레이션 코드를 쓰지 않는다. 문서 데이터를 폐기하고 대장을 다시 올린다.**

근거 — 실측:

- 저장소에 DB 파일이 없다(`ls *.db` → 없음, `.gitignore` 처리). 테스트는 매번 임시 SQLite 를 새로 만든다.
- `packages/core/db.init_db` 는 `Base.metadata.create_all` 뿐이라 마이그레이션 도구 자체가 아직 없다.
- 문서 기능은 이번 사이클에 들어온 것이고 아직 운영 현장 대장이 적재된 적이 없다 — 이 ADR 이 존재하는
  이유가 "실데이터 적재 **전**"이다.
- **대장이 정본이다**(ADR 0007 §1 규칙 1). `documents` 는 전부 대장에서 재생성 가능하다.

폐기 대상과 재생성 방법:

| 대상 | 처리 |
|---|---|
| `documents` | 전량 삭제 → 대장 재업로드로 재생성 |
| `activity_document_mappings` | 전량 삭제 → 재업로드가 후보를 다시 만든다. **CM 확정·반려는 복구되지 않는다** |
| `review_requests` 중 `kind in ("document_mapping",)` | 전량 삭제 |

**확정·반려가 복구되지 않는다는 점을 숨기지 않는다.** 오늘 저장소에 그런 행이 있다면 개발 중 만든 것이고,
현장 데이터가 아니다. 만약 이 ADR 을 적용하기 전에 현장 대장이 이미 적재됐다면 이 판단은 **무효**이고
아래 재계산 마이그레이션을 써야 한다.

**나중에 `DOC_ID_SCHEME` 를 올릴 때(그때는 데이터가 있다) 써야 할 마이그레이션의 형태**를 지금 적어 둔다 —
§5 규칙 4가 "값만 올리는 PR 은 반려"라고 말할 때 그 PR 이 무엇을 담아야 하는지가 여기다.
`documents` 가 재료(`doc_type`/`sender_normalized`/`seq_normalized`/`title`)를 원문 그대로 보관하므로
**옛 `doc_id` → 새 `doc_id` 사상은 계산 가능하다.** 그 사상으로 다음 **여섯** 자리를 한 트랜잭션에서
고친다(`grep doc_id` 로 만든 목록이며, 그 기준이 놓칠 수 있는 것은 §4 블라인드 스팟 2에 적었다):

| # | 자리 | 형태 |
|---|---|---|
| 1 | `documents.doc_id` | PK 구성요소 |
| 2 | `activity_document_mappings.doc_id` | PK 구성요소 + 복합 FK `(project_id, doc_id)` |
| 3 | `activity_document_mappings.evidence` → `source_id` | JSON 안의 문자열 (`document_mapper._build_mapping`) |
| 4 | `review_requests.conflicting_sources["doc_id"]` | JSON 안의 문자열 (`document_mapper._document_mapping_review`) |
| 5 | `review_requests.evidence` → `source_id` | 4번 요청이 매핑 evidence 를 그대로 실어 저장한다 |
| 6 | **(개정 1 추가)** `review_requests.conflicting_sources` 의 `moved[].previous_doc_id`/`new_doc_id`, `merged[].doc_id`, `lost_decisions[].doc_id` | `kind="document_identity_drift"` 요청 본문. **JSON 배열 안에 묻힌 자리라 `conflicting_sources["doc_id"]` 만 보는 4번 규칙으로는 잡히지 않는다** — §4 블라인드 스팟 2("다른 키 이름으로 저장하거나 자유형 JSON 안에 묻힌 자리는 놓친다")가 초판 이후에 실제로 실현된 사례다. 다만 이 요청은 **확인 전용 기록**이므로(§5-3) 옛 `doc_id` 를 그대로 두는 선택도 가능하다 — 그때는 "그 시점의 관측"임을 요청 본문이 말해야 한다. 어느 쪽이든 **판단해서 적어야 하고, 목록에서 빠져서는 안 된다** |

   §5-2 탐지가 이 경로도 함께 잡는다(고아 ↔ 신규 쌍의 `title` 이 같으므로 드리프트로 분류된다).
2. ~~**`document_possibly_renamed` 메시지 정정.** 지금 문구("제목만 다르고 …")는 드리프트 상황에서 사실과
   다르다. §5-2 가 두 경우를 분리하면서 이 문구는 진짜 rename 에만 붙게 되지만, 문구 자체의 정확도는

   미뤘다. 그런데 **그 §5-2 가 만든 새 검토요청 제목이 똑같은 종류의 거짓을 갖고 태어났다**(§5-4:

   왜 버티지 못하는가: 이 저장소에서 문구는 장식이 아니라 **CM 이 다음 행동을 고르는 유일한 입력**이다.
   "고아가 됐으니 새 doc_id 에서 다시 확정하라"를 읽은 CM 은 `merge_overwritten` 상황에서 **존재하지 않는
   행을 찾다가 결국 아무것도 하지 않는다** — 그동안 미승인 도면 위의 착수 가능은 그대로 서 있다.
   부정확한 문구는 "나중에 다듬을 표현"이 아니라 **작동하지 않는 안전 장치**다.

   그래서 규칙으로 바꾼다(CLAUDE.md §6-4): **사실과 다른 문구는 그것을 만든 사이클이 고친다.** 다음
   사이클로 넘기면 다음 문구가 같은 거짓을 물려받는다. 지금 `document_possibly_renamed` 는 §5-2 (가)가
   제목 원문이 같은 쌍을 걸러 내므로 진짜 rename 에만 붙지만, 문구 자체("제목만 다르고 …")를 이 규칙에
   따라 정정하는 것은 `progress-engine` 의 남은 일이며 **Deferred 가 아니라 미결 항목**이다.
3. **문서 매핑 확정을 사람이 되돌리는 경로.** ADR 0007 §4-2 규칙 6 의 Deferred 가 그대로 남는다 —
   이 ADR 은 "정체성이 흔들려 확정이 무효가 되는" 경로만 다루고, "CM 이 확정을 취소하고 싶다"는 다루지 않는다.
4. **식별 표면 지문의 사람이 읽을 수 있는 diff.** §5-2 는 지문이 달라졌다는 사실까지만 보고한다.
   "어느 키가 어떻게 바뀌었는가"를 보여 주는 것은 운영 편의이지 안전 장치가 아니므로 뒤로 미룬다.
5. **[닫힘 — 개정 3, 2026-09-05] `cause` 값의 정본이 여러 자리에 복제돼 있다.** 닫은 기록은 이 항목
   끝의 **개정 3** 블록에 있다. 아래 본문은 **닫히기 전의 기록으로 그대로 둔다**(항목을 지우지 않는다) —
   다만 목록만은 지금 거짓이므로 그 사실을 개정 3 이 적는다.

   `row_moved`/`row_replaced`/`row_absorbed`(개정 2 이전 이름: `orphaned`/`merge_overwritten`/
   `merge_absorbed`) 문자열은 다음 네 자리에 적혀 있다 —

   ### 개정 3 — 이 항목을 닫는다 (2026-09-05, 계획 0005 작업 2·7·8)

   **정본은 `packages/core/models/review.py` 의 `IDENTITY_DRIFT_CAUSE_*` 다.** 같은 파일이
   `IDENTITY_DRIFT_CAUSES`(튜플)와 `IdentityDriftCause`(Literal)를 함께 갖고,
   `IDENTITY_DRIFT_CAUSE_UNSPECIFIED` 는 그 집합 **밖**의 소비 전용 자리표시자다. 파이썬 생산자
   (`services/ingest/persistence`)와 소비자(`services/progress/document_mapper`)의 `_CAUSE_ROW_*` 는
   그 정본을 가리키는 **별칭**이고 값을 다시 적지 않는다(커밋 `568f012` 정의 · `7ae4e34` 소비 ·
   `248a061` 생산). 위 표 1번의 "(**정본**)" 표시는 그래서 지금 거짓이다.

   **위 표를 다섯으로도 여섯으로도 고치지 않는다 — 열거를 문서가 유지하지 않기 때문이다.** 이 항목이
   "네 곳"이라 적은 목록은 한 사이클 안에서 두 번 늘었다: 계획 0005 §2-a 가 저장소 루트에서 값 셋을
   다시 훑어 `apps/web/src/api/types.ts` 와 `config/document_register.yaml` 을 더했고, 그 뒤 §6-1 대로
   축을 넓혀(값 셋 **+ 정본 심볼 이름**) 다시 세자 `apps/web/src/pages/ReviewsPage.tsx` 가 나왔다 —
   거기서 `g.cause === "row_replaced"` 가 `notice strong` 과 "가장 먼저 확인" 배지를 켜므로, 개명이
   거기 닿지 않으면 **가장 위험한 경위의 강조가 조용히 꺼진다**. 목록이 두 번 틀렸다는 사실이 이 항목의
   결론을 바꾸지는 않는다 — 결론은 "정본이 한 자리이고 나머지는 그것을 가리킨다"이지 **자리의 개수가
   아니다**. 바뀌는 것은 **누가 열거를 유지하는가**이고, 답은 사람이 아니다.

   **열거를 대신하는 것: `tests/invariants/test_identity_drift_cause_contract.py`**(계획 0005 작업 8, qa).
   그 파일은 값을 다시 적지 않고 정본을 import 해 비교하며, `apps/web/src` **전수**를 훑어
   `cause === "…"` 비교 자리가 감사 목록과 어긋나면 그 파일 이름을 대고 실패한다
   (`test_web_source_tree_has_no_unaudited_cause_literal`). 새 경위를 추가하거나 이름을 바꾸는 변경이
   함께 고쳐야 할 자리를 **이 항목이 아니라 그 테스트가** 말한다.

   **감사가 무엇을 잡는가 — 심어 보고 잰 값**(2026-09-05, 작업 트리 `/home/user/Bim/buildtwin`,
   전량 기준선 `781 passed`. 각 심기 뒤 저장소 루트 `git status --porcelain` 이 빈 출력임을 확인했다):

   | 심은 결함 | 감사 밖 | 감사 |
   |---|---|---|
   | 파이썬만 일관 개명(`row_absorbed` → `row_relocated`; 생산·소비·파이썬 테스트 전부, TS·yaml 그대로) | 감사 제외 pytest 전량 **746 passed** · vitest 전량 **268 passed** | **7 failed** |

   첫 행이 이 항목이 존재한 이유다: 파이썬 안에서 일관되기만 하면 파이썬 검사도 웹 검사도 전부 초록인데,
   그 제품은 서버가 보낸 값을 `SERVER_CAUSE_TO_LOCAL` 이 찾지 못해 **모든 항목을 "경위 미상"으로**
   보내고 `config/document_register.yaml` 의 경고 문구는 존재하지 않는 이름을 CM 에게 읽어 준다.

   **이 감사의 생성 기준과 블라인드 스팟(§6-1 ①②).** 기준은 **"정본 값 집합과 대조할 수 있게 구조적으로
   추출되는 선언·비교 자리"** 다. 그 기준이 놓치는 것 —

   ① **표기 변종.** 축이 값의 문자 그대로라 `row-moved` 같은 표기는 밖이다. 실측(저장소 루트,
      `grep -rniE "row[- ]moved|row[- ]replaced|row[- ]absorbed" . | grep -v "row_"` + node_modules·.git 제외):
      히트는 **`docs/` 안에서만** 나오고 — 계획 0005 가 이 블라인드 스팟을 서술하며 그 패턴을 인용한 줄과
      **이 문장 자신** — **`docs/` 밖에는 0건**이다. 한국어로 값을 적는 자리도 `docs/` 밖에 0건이다
      (`행 교체` 는 코드 트리에서 `services/progress/document_mapper.py` 와
      `tests/integration/test_17_document_identity_drift.py` 에 나오는데 값이 아니라 개념을 설명하는
      산문이다. 저장소 전체로는 이 ADR 의 줄들도 함께 잡힌다).
      *개수를 적지 않는 이유.* 여기서 결론이 기대는 것은 "`docs/` 밖에 표기 변종이 없다"는 **부재**이지
      개수가 아니다 — 그리고 이 문장을 개수로 적었더니 **그 문장 자신이 히트가 되어** 다음 커밋에서
      거짓이 됐다(초판은 "히트 1건"이라 적었고 실측은 2건이었다). ④ 대로 `docs/` 는 감사 대상이 아니라
      실해는 없었지만, 개수 단정은 결론이 개수에 기댈 때만 쓴다(CLAUDE.md §6-1).
   ② **값 이름을 쓰지 않고 `cause` 를 소비하는 자리.** 실측(비테스트 런타임 트리에서 `\bcause\b`):
      나오는 파일은 감사가 이미 보는 자리들뿐이고 **추가 0건**이다.
   ③ **아직 존재하지 않는 네 번째 경위 이름**은 원리상 이 축 밖이다. 그리고 config 칸의 축은
      `\brow_` 접두사라, `row_` 로 시작하지 않는 새 이름은 그 칸에서 보이지 않는다.
   ④ **`docs/` 는 대상이 아니다.** ADR·계획·glossary 는 옛 이름을 **의도적으로 보존**하고(§5-2 (마)
      개명 표, glossary "옛 이름 셋 … 번역하지 않는다") 개명 뒤에도 참인 채로 남아야 한다 —
      감사에 넣으면 감사가 정본을 거짓으로 만든다.
   ⑤ **값 집합만 비교하고 의미는 비교하지 않는다.** 두 이름을 서로 맞바꾸는 개명은 **모든 칸을 통과한다.**
      이것이 이 감사의 가장 큰 구멍이고, 값 대조로는 닫히지 않는다.
   ⑥ 파일 목록의 자동 유지는 **`apps/web/src` 의 비교 자리에만** 있다. 파이썬 별칭 자리와
      `config/document_register.yaml` 은 감사가 경로를 손으로 적고, 그 경로에 없는 **새 파일**은 밖이다
      (파일이 옮겨지면 추출이 공집합이 되는 대신 그 자리에서 죽도록 존재 단언이 앞에 있다).
