# ADR 0006 — 프로젝트 멤버십과 인가

- 상태: Accepted (개정 1: 2026-09-03 — §2-1 `admin` 멤버십 금지 규칙 추가)
- 작성: architect
- 날짜: 2026-09-03
- 관련: ADR 0001 §4-1(역할→actor), ADR 0005 §3·Consequences(인가 전제), 리뷰 3·4·5차 관찰, 리뷰 6차 지적 2

## Context

현재 인가는 **역할만** 본다. `UserRow.role`이 전역이고, `require_role("cm")`은 "이 사람이 CM인가"만 묻는다. "이 사람이 **이 프로젝트의** CM인가"는 아무 데서도 묻지 않는다. 결과:

- `GET /api/projects`가 모든 프로젝트를 돌려준다. 로그인하면 남의 현장이 보인다.
- `usecases.resolve_object`는 호출자가 준 `project_id`를 그대로 신뢰하고, 생략되면 전 프로젝트에서 `global_id`를 찾는다(ADR 0005 §3이 "요청자의 접근 가능 프로젝트로 좁혀 해석한다"고 적었지만 미구현).
- `GET /review-requests/{id}`, `POST .../resolve`, `GET /activities/{id}/readiness`는 프로젝트를 아예 묻지 않는다.

BuildTwin은 발주처·CM단·시공사가 **같은 화면을 다른 권한으로** 보는 제품이다. 한 회사가 여러 현장을 하고, 한 현장에 여러 시공사가 들어온다. 프로젝트 격리 없이는 실사용은커녕 데모도 어렵다. 리뷰어가 3·4·5차에서 연속으로 관찰로 남긴 항목이다.

## Decision

### 1. 멤버십 테이블

```
project_members
  project_id  FK → projects.project_id   ┐ PK
  user_id     FK → users.user_id         ┘
  role        contractor | cm | client
  added_by, added_at
```

프로젝트 접근권은 **행의 존재**로 정의된다. 행이 없으면 그 프로젝트는 존재하지 않는 것처럼 취급한다.

### 2. 역할의 두 층

| 층 | 저장 위치 | 의미 |
|---|---|---|
| 시스템 역할 | `users.role` | `admin`은 플랫폼 관리자이며 **어떤 프로젝트의 멤버도 될 수 없다**(§2-1). 그 외 값(`contractor`/`cm`/`client`)은 **인가 판단에 쓰지 않는다** — `users.role`을 읽는 인가 검사는 `require_role("admin")`뿐이다(§4) |
| 프로젝트 역할 | `project_members.role` | 그 프로젝트에서 이 사람이 무엇인가. **모든 프로젝트 범위 인가 판단과 `actor` 결정의 근거**(규칙 1·7). 프로젝트를 묻지 않는 라우트(멤버십 관리 자체 — §4)는 예외적으로 시스템 역할 `admin`으로 검사한다 |

`admin`은 멤버십 없이 모든 프로젝트를 **조회**할 수 있고 멤버십을 관리한다. 그러나 **행위 역할은 없다** — ADR 0001 §4-1대로 확정·검측 승인·작업일보 제출은 여전히 불가하며, `actor_for_role`이 계속 거부한다. 단 이 거부는 **admin이 프로젝트 역할을 얻을 수 없을 때에만** 성립한다(§2-1이 쓰기·읽기 두 겹으로 그것을 강제한다). 관리자가 실제로 현장 판단을 해야 하면 별도의 cm 계정을 발급한다.

#### 2-1. 규칙: 전역 `admin` 계정은 어떤 프로젝트의 멤버도 될 수 없다

인가의 기본 구조는 **멤버십이 전역 역할을 이기는** 것이다 — `services/api/deps.py`의 `project_role`은 멤버십 행을 조회해 있으면 그 역할로 결정하고, `admin` 분기는 그 뒤에 있다. 그러므로 위 문단의 방어를 `actor_for_role`에만 맡기면 성립하지 않는다: admin이 `POST /projects/{pid}/members {user_id: <자기 자신>, role: "cm"}`을 호출하면 프로젝트 역할이 `cm`이 되고 `actor_for_role("cm") → Actor.CM`이 되어 CONFIRMED 전이·검측 승인·검토요청 해소가 전부 통과한다. admin이 **스스로 확정 권한을 발급**할 수 있게 되고, 승인 로그의 `actor_id`가 admin 계정이 되어 ADR 0001 §4-1의 "admin은 확정 불가"가 감사 관점에서 무의미해진다.

따라서 이 금지를 입구에서 강제한다.

1. **`POST /api/projects/{pid}/members`는 대상 사용자의 `users.role == "admin"`이면 거부한다** — **422 `admin_cannot_be_member`**. 대상이 호출자 자신인지와 무관하고, 요청한 `role` 값과도 무관하다. 검사 순서는 `user_not_found`(대상 존재) 다음, `duplicate_member`(중복) 앞이다.
2. 이 금지가 §2 표의 "admin은 행위 역할이 없다"를 실제로 성립시키는 **쓰기측** 방어다. `actor_for_role`의 거부는 admin이 프로젝트 역할을 **얻지 못할 때에만** 유효하므로, 둘 중 하나만으로는 불변식이 지켜지지 않는다. 그래서 **읽기측에도 같은 금지를 한 겹 더 건다**: `services/api/deps.py`의 `project_role()`과 `services/api/usecases.py`의 `caller_project_role()`은 호출자의 `users.role == "admin"`이면 멤버십 행이 있어도 무시하고 admin 분기(조회만 가능·행위 역할 없음, `role=None`)로 보낸다. 즉 admin 호출자에게는 위 "멤버십이 전역 역할을 이긴다"가 적용되지 않는다 — 이 예외가 규칙 자체이며, 그 결과 이 규칙 도입 이전에 만들어진 admin 멤버 행이 남아 있어도 프로젝트 역할이 admin에게 흘러가지 않는다.
3. 관리자가 현장 판단(확정·검측 승인·검토요청 해소)을 해야 하면 **별도의 cm 계정을 발급**한다. 감사 로그에서 관리 행위(admin 계정)와 현장 판단(cm 계정)이 서로 다른 `user_id`로 분리되어야 한다.
4. 반대 방향(이미 멤버인 사용자를 전역 admin으로 승격)은 MVP에 경로가 없다(`users.role` 변경 API 없음). 그런 경로가 생기면 같은 규칙을 그쪽에도 건다(Deferred).

**상태 코드 422를 택한 근거.** 400이 아닌 이유: 요청 문법·타입·본문 파싱은 모두 정상이고, 거부 사유는 `user_id`가 가리키는 **대상의 의미적 자격**이다 — 잘 형성된 요청이지만 처리할 수 없는 경우로, `daily_report_invalid`·`alignment_input_insufficient`와 같은 부류다. 409가 아닌 이유: 409는 "현재 상태와 충돌하니 상태를 바꾸면 성공할 수 있다"를 뜻하고(`duplicate_member`가 그 예 — 멤버를 지우면 성공한다), admin 계정은 admin으로 남는 한 **어떤 상태에서도** 멤버가 될 수 없으므로 재시도 가능성을 암시해서는 안 된다.

**기존 데이터.** MVP 단계(운영 배포 전, ADR 0005와 같은 전제)이므로 마이그레이션·백필 스크립트를 두지 않는다. 이미 만들어진 admin 멤버 행은 개발·시드 DB에만 존재할 수 있으며 DB 재생성으로 사라진다. **마이그레이션이 없어도 불변식은 깨지지 않는다** — 항목 2의 읽기측 방어가 admin 호출자의 멤버십 행을 무조건 무시하므로, 남아 있는 행은 인가에도 `actor` 결정에도 관여하지 않는 잔여 데이터다. 정리는 위생 문제일 뿐 보안 문제가 아니다.

### 3. 인가 규칙

1. 프로젝트 범위 라우트는 `require_project_role(*roles)`로 검사한다. 멤버십을 읽어 역할을 정하고, 역할이 맞지 않으면 403(`forbidden_role`).
2. **멤버가 아니면 404**(`project_not_found`)를 준다. 403은 프로젝트의 존재를 알려주므로 열거 공격에 쓰인다.
3. `GET /projects`는 멤버인 프로젝트만 돌려준다(admin은 전부).
4. `ProjectView`에 `my_role`을 싣는다(admin은 `null`). 화면은 이 값으로 버튼을 가린다. 전역 역할로 가리면 안 된다.
5. `resolve_object`의 후보 조회는 **요청자가 멤버인 프로젝트로 한정**한다. 명시 `project_id`도 멤버십을 통과해야 한다. 이로써 ADR 0005 §3의 미이행 전제가 해소된다.
6. 프로젝트를 묻지 않던 라우트(`review-requests/{id}`, `activities/{id}/readiness`)는 대상 행의 `project_id`로 멤버십을 검사한다.
7. 상태 전이의 `actor`는 **프로젝트 역할**에서 나온다. 전역 역할은 쓰지 않는다.

### 4. 멤버십 관리

`GET/POST/DELETE /api/projects/{pid}/members` — admin 전용(MVP). 그 프로젝트 CM에게 위임하는 것은 필요해지면 별도 ADR로 다룬다.

`MemberCreate.role`(프로젝트 역할)은 요청자가 명시한다. 대상 사용자의 `users.role`을 기본 역할로 **제안**하는 UX는 **Deferred — 미구현**이다: 현재 `apps/web/src/pages/ProjectMembersPage.tsx`는 대상과 무관하게 항상 `contractor`를 기본 선택하고, `add_member`도 기본값을 유도하지 않는다. 이 UX가 생기더라도 시스템 역할은 **화면의 초기 선택값**일 뿐이며 인가 판단에는 여전히 쓰지 않는다(§2 표).

프로젝트를 만든 admin에게 자동 멤버십을 주지 않는다. admin은 이미 조회 가능하고, 행위 역할이 없으므로 멤버십이 의미가 없다 — §2-1에 따라 **줄 수도 없다**(`add_member`가 422 `admin_cannot_be_member`로 거부한다).

## Consequences

- 장점: 격리가 스키마와 의존성 양쪽에서 강제된다. ADR 0005의 "모호한 GlobalId" 문제도 자연히 줄어든다 — 후보가 내 프로젝트로 좁혀지므로 실사용에서 409를 볼 일이 드물어진다.
- 비용: 프로젝트 범위 라우트 전부가 의존성을 바꾼다. 프론트엔드는 전역 역할 대신 프로젝트별 역할을 봐야 하므로 `RequireRole`과 확정 버튼 게이팅이 바뀐다.
- 테스트: 기존 통합 테스트는 시드 사용자가 모든 프로젝트에 접근한다고 가정한다. 시드에 멤버십을 함께 만들어야 한다.
- 감사: 승인 로그의 `actor_id`는 **언제나** 프로젝트 역할을 가진 계정이다 — 관리 행위와 현장 판단이 계정 단위로 분리된다. 이 "언제나"는 §2-1 항목 2가 요구한 **두 겹**이 함께 서 있기 때문에 성립한다. ① 쓰기측: `add_member`가 대상이 admin이면 422 `admin_cannot_be_member`로 거부하므로 새 admin 멤버 행이 생기지 않는다. ② 읽기측: `project_role()`·`caller_project_role()`이 호출자의 `users.role == "admin"`이면 멤버십 행이 있어도 무시하므로, 규칙 도입 이전에 만들어진 admin 멤버 행이 남아 있는 DB(마이그레이션을 두지 않기로 한 §2-1 "기존 데이터")에서도 그 행에서 `actor`가 나오지 않는다. 어느 한 겹만으로는 이 단정이 성립하지 않는다. 누가 언제 누구를 넣었는지가 `added_by`/`added_at`에 남는다. 삭제는 행 제거이므로 이력이 사라진다 — 감사 요구가 생기면 `removed_at` 소프트 삭제로 바꾼다(Deferred).

## Alternatives considered

- **전역 역할 유지 + 프로젝트 필터만 추가**: 싸지만 "A현장 CM이 B현장에서도 CM"이 된다. 한 사람이 현장마다 다른 위치인 건설업 현실과 맞지 않아 기각.
- **조직(회사) 단위 권한**: 실제로는 회사 단위 계약이 맞지만, 조직 모델을 먼저 만들어야 하고 MVP에 과하다. 멤버십이 자리 잡은 뒤 그 위에 얹는다(Deferred).
- **비멤버에게 403**: 구현이 단순하나 프로젝트 id 열거를 허용한다. 404 채택.
