# ADR 0006 — 프로젝트 멤버십과 인가

- 상태: Accepted
- 작성: architect
- 날짜: 2026-09-03
- 관련: ADR 0001 §4-1(역할→actor), ADR 0005 §3·Consequences(인가 전제), 리뷰 3·4·5차 관찰

## Context

현재 인가는 **역할만** 본다. `UserRow.role`이 전역이고, `require_role("cm")`은 "이 사람이 CM인가"만 묻는다. "이 사람이 **이 프로젝트의** CM인가"는 아무 데서도 묻지 않는다. 결과:

- `GET /api/projects`가 모든 프로젝트를 돌려준다. 로그인하면 남의 현장이 보인다.
- `usecases.resolve_object`는 호출자가 준 `project_id`를 그대로 신뢰하고, 생략되면 전 프로젝트에서 `global_id`를 찾는다(ADR 0005 §3이 "요청자의 접근 가능 프로젝트로 좁혀 해석한다"고 적었지만 미구현).
- `GET /review-requests/{id}`, `POST .../resolve`, `GET /activities/{id}/readiness`는 프로젝트를 아예 묻지 않는다.

BuildTwin은 발주처·CM단·시공사가 **같은 화면을 다른 권한으로** 보는 제품이다. 한 회사가 여러 현장을 하고, 한 현장에 여러 시공사가 들어온다. 프로젝트 격리 없이는 실사용은커녕 데모도 어렵다. 리뷰어가 3·4·5차에서 연속으로 관찰로 남긴 항목이다.

## Decision

### 1. 멤버십 테이블

```
project_members
  project_id  FK → projects.project_id   ┐ PK
  user_id     FK → users.user_id         ┘
  role        contractor | cm | client
  added_by, added_at
```

프로젝트 접근권은 **행의 존재**로 정의된다. 행이 없으면 그 프로젝트는 존재하지 않는 것처럼 취급한다.

### 2. 역할의 두 층

| 층 | 저장 위치 | 의미 |
|---|---|---|
| 시스템 역할 | `users.role` | `admin`은 플랫폼 관리자. 그 외 값은 멤버십 생성 시 제안되는 **기본값**일 뿐 인가 판단에 쓰지 않는다 |
| 프로젝트 역할 | `project_members.role` | 그 프로젝트에서 이 사람이 무엇인가. **모든 인가 판단의 근거** |

`admin`은 멤버십 없이 모든 프로젝트를 **조회**할 수 있고 멤버십을 관리한다. 그러나 **행위 역할은 없다** — ADR 0001 §4-1대로 확정·검측 승인·작업일보 제출은 여전히 불가하며, `actor_for_role`이 계속 거부한다. 관리자가 필요하면 별도의 cm 계정을 발급한다.

### 3. 인가 규칙

1. 프로젝트 범위 라우트는 `require_project_role(*roles)`로 검사한다. 멤버십을 읽어 역할을 정하고, 역할이 맞지 않으면 403(`forbidden_role`).
2. **멤버가 아니면 404**(`project_not_found`)를 준다. 403은 프로젝트의 존재를 알려주므로 열거 공격에 쓰인다.
3. `GET /projects`는 멤버인 프로젝트만 돌려준다(admin은 전부).
4. `ProjectView`에 `my_role`을 싣는다(admin은 `null`). 화면은 이 값으로 버튼을 가린다. 전역 역할로 가리면 안 된다.
5. `resolve_object`의 후보 조회는 **요청자가 멤버인 프로젝트로 한정**한다. 명시 `project_id`도 멤버십을 통과해야 한다. 이로써 ADR 0005 §3의 미이행 전제가 해소된다.
6. 프로젝트를 묻지 않던 라우트(`review-requests/{id}`, `activities/{id}/readiness`)는 대상 행의 `project_id`로 멤버십을 검사한다.
7. 상태 전이의 `actor`는 **프로젝트 역할**에서 나온다. 전역 역할은 쓰지 않는다.

### 4. 멤버십 관리

`GET/POST/DELETE /api/projects/{pid}/members` — admin 전용(MVP). 그 프로젝트 CM에게 위임하는 것은 필요해지면 별도 ADR로 다룬다.

프로젝트를 만든 admin에게 자동 멤버십을 주지 않는다. admin은 이미 조회 가능하고, 행위 역할이 없으므로 멤버십이 의미가 없다.

## Consequences

- 장점: 격리가 스키마와 의존성 양쪽에서 강제된다. ADR 0005의 "모호한 GlobalId" 문제도 자연히 줄어든다 — 후보가 내 프로젝트로 좁혀지므로 실사용에서 409를 볼 일이 드물어진다.
- 비용: 프로젝트 범위 라우트 전부가 의존성을 바꾼다. 프론트엔드는 전역 역할 대신 프로젝트별 역할을 봐야 하므로 `RequireRole`과 확정 버튼 게이팅이 바뀐다.
- 테스트: 기존 통합 테스트는 시드 사용자가 모든 프로젝트에 접근한다고 가정한다. 시드에 멤버십을 함께 만들어야 한다.
- 감사: 누가 언제 누구를 넣었는지가 `added_by`/`added_at`에 남는다. 삭제는 행 제거이므로 이력이 사라진다 — 감사 요구가 생기면 `removed_at` 소프트 삭제로 바꾼다(Deferred).

## Alternatives considered

- **전역 역할 유지 + 프로젝트 필터만 추가**: 싸지만 "A현장 CM이 B현장에서도 CM"이 된다. 한 사람이 현장마다 다른 위치인 건설업 현실과 맞지 않아 기각.
- **조직(회사) 단위 권한**: 실제로는 회사 단위 계약이 맞지만, 조직 모델을 먼저 만들어야 하고 MVP에 과하다. 멤버십이 자리 잡은 뒤 그 위에 얹는다(Deferred).
- **비멤버에게 403**: 구현이 단순하나 프로젝트 id 열거를 허용한다. 404 채택.
