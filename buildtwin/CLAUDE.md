# BuildTwin — CLAUDE.md

> 이 파일은 BuildTwin 프로젝트의 단일 진실 원천(Single Source of Truth)이다.
> 모든 에이전트(사람·Claude 서브에이전트)는 작업 전에 이 문서를 읽고 따른다.
> 이 문서와 충돌하는 결정은 반드시 `docs/adr/`에 ADR로 남겨야 유효하다.

## 0. 프로젝트 정의 (변경 금지)

BuildTwin은 건설 PM/CM 회사를 위한 AI PM 플랫폼이다. 핵심은 3D 뷰어가 아니라 **"계획 상태 / 실제 상태 / 전문가 판단 상태 / 승인 상태"를 객체 단위로 비교하는 데이터 구조**다.

MVP 범위(이 범위 밖은 구현하지 않는다):

1. **도면 업로드·인식**: IFC(1순위), DWG/DXF(2D), RVT(3순위 — 아래 제약 참고)를 업로드하면 객체(기둥·보·슬래브·벽·덕트·배관·케이블트레이·외장패널)를 추출해 DB에 저장한다.
2. **2D↔3D 상호작용**: 3D 객체를 클릭하면 대응하는 2D 도면 위치가 하이라이트되고, 2D 도면에서 영역/객체를 선택하면 3D가 해당 객체로 이동·하이라이트된다. 3D 모델에서 층별 평면 단면을 자동 생성해 2D와 겹쳐 볼 수 있어야 한다.
3. **현장 스캔 비교**: 포인트클라우드(E57/LAS/PLY)를 업로드하면 BIM 좌표계에 정합하고, 객체별로 `미시공 / 시공중 / 완료추정 / 위치불일치 / 확인불가(가림)`를 판정한다.
4. **후공정 확인**: 공정표(CSV/XML/P6·MS Project export)를 객체와 연결하고, 각 작업의 **Work Readiness Score**(선행공정·검측·자재·도면승인·간섭)를 계산해 다음 착수 가능 작업과 차단 원인을 제시한다.
5. **3중 검증**: 시공사 신고(작업일보 입력) / 물리적 증거(스캔) / 시스템 논리(BIM 수량·선후행·자재 입출고)가 불일치하면 자동 확정을 막고 CM 확인 요청을 생성한다.

핵심 원칙:

- 스캔 AI는 **"완료 추정"까지만** 판정한다. "확정 완료"는 반드시 사람(CM) 승인 액션을 거친다.
- 모든 객체는 IFC GlobalId를 1차 키로 쓰고, 2D 엔티티·공정 Activity·자재·스캔 판정은 이 키에 매달린다.
- 모든 판정에는 `confidence`(0~1)와 `evidence`(근거 파일·좌표·규칙 ID)를 남긴다.

기술 제약(반드시 지킬 것):

- **RVT 파일은 네이티브 파싱 불가.** Revit 없이 서버에서 열 수 없다. 선택지는 ① 사용자에게 IFC 내보내기 요구 ② Autodesk Platform Services(APS) Model Derivative API로 변환 ③ Revit 애드인(pyRevit/C#)으로 IFC+메타데이터 내보내기. MVP는 ①+②로 가고, ③은 ADR로 남긴다.
- DWG는 ODA(Open Design Alliance) 라이선스 없이 직접 파싱하기 어렵다. MVP는 **DXF 우선**, DWG는 ODA File Converter 또는 APS로 DXF 변환 후 처리한다.
- 포인트클라우드 정합은 자동 ICP만 믿지 않는다. 현장 기준점(최소 3점) 또는 마커(AprilTag/QR) 좌표를 사용자가 입력하는 경로를 반드시 둔다.

소유 규칙:

- 각 에이전트는 **자기 담당 디렉터리만** 수정한다. 밖을 고쳐야 하면 `architect`에게 먼저 제안하고, `architect`가 계획에 명시한 경우에만 수정한다.
- `packages/core/models/`는 `architect`가 소유하되, 구현 에이전트는 필드 추가를 **제안**할 수 있다(직접 수정 금지).
- `docs/glossary.md`는 누구나 항목을 **추가**할 수 있으나 기존 항목 변경은 `architect` 승인이 필요하다.

## 3. 공통 규칙

1. **커밋 전 `make test` 통과.** 실패하는 테스트가 있으면 커밋하지 않는다. 테스트를 skip/disable해서 통과시키는 것은 금지.
2. **새 도메인 개념은 `docs/glossary.md`에 한국어+영어로 등록**한다. 코드 식별자·API 필드명·UI 라벨은 glossary의 영어 표기를 그대로 쓴다.
3. **판정 로직에는 항상 `confidence`(float 0~1)와 `evidence`(근거) 필드**가 있어야 한다. 스캔 판정, 2D↔3D 매핑, Activity↔객체 매핑, 규칙 엔진 판정, 3중 검증 모두 해당. `evidence`는 최소 `{source_file, coordinates | bbox, rule_id | method}` 구조.
4. **외부 API 키·시크릿은 `.env`에만** 둔다. 코드·YAML·테스트 픽스처에 하드코딩 금지. `.env.example`에 키 이름만 나열한다.
5. **한국어 주석 허용, 식별자는 영어.** 변수·함수·클래스·테이블·컬럼·API 경로는 모두 영어. 주석·docstring·커밋 메시지·문서는 한국어 가능.
6. **좌표계 변환은 하드코딩 금지.** 원점·회전·스케일·EPSG는 항상 `CoordinateSystem` 객체(`packages/core/models/`)로 전달하고, 값은 DB 또는 사용자 입력에서 온다.
7. **상태 전이는 반드시 `actor`(system/contractor/cm)와 `evidence`를 기록**한다. ADR 0001의 상태기계 밖 전이는 코드로 존재해서는 안 된다.
8. **"확정(CONFIRMED)" 상태는 `actor == cm`인 전이로만 도달**한다. `system` actor가 CONFIRMED로 전이하는 코드 경로가 있으면 `reviewer`가 즉시 반려한다. **역할→actor 매핑은 `contractor→contractor`, `cm→cm`뿐이다.** `admin`은 프로젝트·사용자 관리 역할이며 확정·검측 승인·검토요청 처리 권한이 없다(ADR 0001 §4-1). `client`는 조회 전용.
11. **API 계층(`services/api`)에는 도메인 규칙을 두지 않는다.** 재업로드·orphan 규칙은 `services/ingest/persistence.py`, 매핑 생명주기·검토요청 해소는 `services/sync`, 검측 ReviewRequest 생성·종료는 `services/progress/state_machine.py`가 소유한다. API는 이를 호출만 한다.
12. **API 필드명은 snake_case(glossary 영어 표기 그대로)**. 뷰어 TS 타입도 서버 계약 필드는 같은 표기를 쓴다(`global_id`, `coordinate_system`).
9. **비동기 작업(파싱·정합·판정)은 Celery 태스크**로 발행하고, API는 `job_id`를 돌려준 뒤 상태 폴링 엔드포인트로 진행률을 제공한다.
10. **MVP 범위 밖 기능은 구현하지 않는다.** 필요하면 `docs/adr/`에 "Deferred" ADR을 남기고 끝낸다.

## 4. 에이전트 호출 규약

기능 요청은 항상 다음 순서로 흐른다:

```
architect  →  담당 에이전트(1개 이상)  →  qa  →  reviewer
```

- **architect**: 요청을 받으면 "어느 에이전트가, 어떤 인터페이스(입출력 계약)로, 어떤 순서로" 구현할지 계획을 쓴다. 데이터 모델 변경이 필요하면 `packages/core/models/`와 ADR을 먼저 고친다. 직접 구현 코드는 쓰지 않는다.
- **담당 에이전트**: architect의 계획과 자기 파일의 입출력 계약대로 구현한다. 담당 디렉터리 밖은 건드리지 않는다.
- **qa**: 담당 에이전트의 "완료 조건"을 테스트로 강제한다. 픽스처가 없으면 만든다. `tests/metrics.json` 기준치를 갱신하거나 하락을 잡는다.
- **reviewer**: 5가지 체크(무승인 확정 경로 / confidence·evidence 누락 / 디렉터리 밖 수정 / 좌표계 하드코딩 / glossary 불일치)를 수행하고, 하나라도 걸리면 승인하지 않고 담당 에이전트에게 돌려보낸다. 직접 수정하지 않는다.

에이전트 목록(`.claude/agents/`):

| 에이전트 | 모델 | 담당 |
|---|---|---|
| `architect` | opus | 설계·ADR·데이터 모델·작업 분배 |
| `bim-ingest` | sonnet | `services/ingest/` |
| `viewer-3d` | sonnet | `apps/web/src/viewer3d/` |
| `viewer-2d` | sonnet | `apps/web/src/viewer2d/` |
| `sync-2d3d` | sonnet | `services/sync/` |
| `reality-capture` | sonnet | `services/scan/` |
| `progress-engine` | sonnet | `services/progress/`, `config/` |
| `knowledge` | sonnet | `services/knowledge/`, `rules/` |
| `api` | sonnet | `services/api/`, `docs/api.md` |
| `frontend` | sonnet | `apps/web/` (뷰어 디렉터리 제외) |
| `qa` | sonnet | `tests/`, `.github/workflows/`, `Makefile` |
| `reviewer` | opus | 머지 전 리뷰(수정 권한 없음) |

호출 예시:

```
@architect 스캔 판정 결과를 객체 상세 API에 노출하려고 해. 계획 세워줘.
@bim-ingest architect 계획대로 IFC 파서 구현해줘.
@qa bim-ingest 완료 조건을 pytest로 붙여줘.
@reviewer services/ingest 변경분 리뷰해줘.
```

## 6. 계획·ADR·검증을 쓸 때 반복된 실패 (0007·0008·0009 실측)

> **이 절이 왜 CLAUDE.md 에 있는가(architect 판단, 2026-09-04).** 아래 네 패턴은 최근 세 사이클에서
> **각각 여러 건씩** 반복됐고, **전부 하류(구현·qa)가 실행으로 잡았다.** 즉 계획을 쓰는 시점에는 아무도
> 못 보는 종류의 오류다. 그래서 사건을 겪은 ADR 안에 두면 안 된다 — ADR 0009 §5-4 에 묻으면 다음
> 사이클은 그 ADR 을 열 이유가 없어 같은 함정에 다시 빠진다. 별도 문서로 빼는 것도 같은 이유로 기각했다
> (링크되지 않은 문서는 읽히지 않는다 — 이 저장소의 "job 경고는 아무도 되돌아보지 않는다"와 같은 실패다).
> **모든 에이전트가 작업 전에 반드시 읽는 문서는 이 파일 하나뿐이므로**, 규칙은 여기 두고 사건의 전모는
> 각 ADR·계획에 남긴다. 아래 각 항목은 **근거 → 규칙** 순으로 적는다: 규칙만 남기면 다음 사람이 그것을
> 재량으로 읽고 건너뛴다.

이 프로젝트의 지배적 실패 모드는 **"조용히 죽는 것"**(예외 없음·테스트 전부 통과·화면 정상·이력만 사라짐)
이고, 아래 넷은 그 실패가 **계획·ADR 단계에서 만들어지는** 네 가지 경로다.

### 6-1. 전수 목록의 **생성 기준**이 곧 그 목록의 한계다

- 0008 계획: `grep "session.get(...)"` 하나로 전수 목록을 만들었다 → **시그니처가 바뀐 호출부**와
  **Celery 잡 안에서 예외가 삼켜지는 경로**를 통째로 놓쳤다.
- 0009 계획 §1-a: 기준은 잘 적었으나 블라인드 스팟 1(시트명 변경)을 **적어 두기만 하고 태워 보지 않았다**
  → 폭발 반경은 같아도 **관측 가능성이 전혀 달랐다**(`orphaned=0`, `fingerprint_changed=False` — 초판
  탐지 규칙이 이 경로에서 전부 침묵).
- 0009 계획 §7: "결함이 있어도 통과하는 단언" 목록(반증 목록) 자체를 **실측 없이 생각으로** 적어 숫자가
  틀렸다(`mapping_count == 6` 은 정상 코드에서 4).

**규칙.** 전수 목록·반증 목록·영향 범위 표를 쓸 때는 ① **어떤 기준으로 만들었는지**를 목록 옆에 적고
② **그 기준이 놓치는 것**을 함께 적고 ③ **적어 둔 블라인드 스팟을 최소 한 건은 실제로 태워 본다.**
"놓칠 수 있다"고 적는 것은 커버리지가 아니다. 그리고 **다른 절을 가리켜 확인을 갈음하지 않는다** —
"→ §7 V4 가 이 구멍을 덮는다"는 문장은 V4 를 열어 확인하기 전에는 쓰면 안 된다(0009 계획이 그렇게 적었고
V4 에는 그 케이스가 없었다).

### 6-2. 검증 시나리오는 **결함을 못 잡도록** 세워질 수 있다

- 0008 계획 S4: 같은 파일을 양쪽에 올려 누수가 나도 점수가 **산술적으로 동일**했다 → 결함이 있는데 통과.
- 0009 계획 §7 V3b: 병합 충돌을 **사람 판단이 없는 프로젝트**로 세워 `identity_drift_review_id is None`
  이 **정답으로 고정**됐다 → 결함 있는 코드와 옳은 코드가 그 시나리오에서 **구별 불가능**했고, 그래서
  "병합은 절대 CM 큐에 올라가지 않는다"는 blocker 가 사이클 끝까지 살아남았다. 음성 대조군 N1~N3 도
  전부 한쪽 축(*moved*)의 것이라 병합 축은 양성에서도 음성에서도 검증되지 않았다.

**규칙.** 시나리오를 쓸 때마다 스스로에게 묻는다: **"이 단언의 기대값을, 결함 있는 코드가 그대로
만족하는가?"** 그렇다면 그 시나리오는 검증이 아니라 장식이다. 구체적으로 —

1. **양성 케이스는 "그 결함이 있으면 값이 달라지는" 상태로 세운다.** 판정 결과가 결함 유무와 무관하게
   같은 값(`None`·`0`·빈 목록)으로 고정되는 조건(사람 판단이 없는 프로젝트, 빈 입력, 동일 파일 등)을
   양성 케이스의 전제로 쓰지 않는다.
2. **탐지를 검증할 때는 발화의 *결과*까지 값이 갈리게 세운다**(경고가 떴는가 → 큐에 올라갔는가).
3. **음성 대조군을 한 축에만 몰지 않는다.** 판정 경로가 둘 이상이면 각 축마다 양성·음성을 세운다.
4. **두 사실이 함께여야 의미가 있으면 함께 단언한다**(0009 V5: "승인 상태가 뒤집혔다" + "같은 적재가
   그것을 큐에 올렸다" — 하나만 고정하면 다른 하나가 사라져도 초록이다).

### 6-3. 조건을 **좁게** 적으면 가장 위험한 변종이 표 밖으로 나간다

- 0009 ADR §5-2 초판: 검토요청 생성 조건을 "**고아**가 된 문서에 사람 판단이 있으면"으로 적었다 →
  `merge_overwritten`(행이 살아 있고 내용만 바뀐다)은 고아가 아니므로 **영원히 큐에 닿지 못했다.**
- 같은 표: 병합을 "두 `doc_id` 가 하나의 **새** `doc_id` 로 수렴"이라고 적었다 → 운영에서 실제로 일어나는
  병합은 **이미 있던** id 로 수렴한다. **한정어 하나**가 가장 위험한 변종을 밖으로 밀어냈다.
- 0009 계획 §3-e 3: 범위를 `drift.moved` 로 좁혀 적어, 구현이 계획대로 했는데 병합 경로가 **구조적으로**
  결과에 들어갈 수 없었다.
- 0009 ADR §5-2 **개정 1**(= 위 두 줄을 고친 개정): 병합을 "**한 적재 안에서** 두 개 이상의 대장 행이
  같은 `doc_id` 로 수렴"이라고 적었다 → 그 한정어가 구현의 조건이 됐고, **사명 변경 주의 정상 운영**
  (별칭표 통합 + 대장에서 옛 법인명 행이 빠짐)은 두 행을 한 적재에 두지 않으므로 다시 표 밖으로 나갔다.
  실측: 승인 상태가 뒤집혀 `drawing_approval` 0.0 → 1.0(미승인 도면 위 착수 가능)인데 **경고 0건·검토요청
  0건.** 초판이 고친 blocker 와 데이터 모양·결과가 같다 — **"고아"를 걷어낸 자리에 "한 적재 안에서"가
  남았을 뿐이다.** 같은 조건절, 같은 사이클, **세 번째 재발**(ADR 0009 §5-5).

**이 재발이 이 규칙의 가장 강한 근거인 이유(architect, 2026-09-04).** 세 번째는 **이 §6-3 을 쓴 사람이,
그 규칙을 쓴 바로 다음 개정에서** 저질렀다. 즉 **규칙을 아는 것으로는 부족하다.** 왜 부족했는지 —
개정 1 을 쓸 때 나는 초판의 한정어 두 개("고아"·"새")를 지우는 데 주의를 다 썼고, **그 자리를 메우려고
내가 새로 쓴 문장에는 같은 확인을 하지 않았다.** 역방향 확인을 "고칠 것"에만 적용하고 "고친 결과"에는
적용하지 않은 것이다. 그래서 §6-3 은 **점검표**가 아니라 **산출물**을 요구하는 규칙이어야 한다:

- **한정어마다 역방향 확인을 문서에 한 줄씩 적는다**(머릿속으로 하지 않는다 — 안 적으면 안 한 것이다).
  적는 자리는 그 조건절 바로 아래다. 새로 **쓴** 조건절도 예외가 아니다(개정 1 이 정확히 여기서 실패했다).
- **그 확인을 실행으로 태우고 결과를 표로 남긴다.** 새 조건이 무엇을 잡고 무엇을 놓치는지를,
  **옛 조건의 결과와 나란히** 적는다. ADR 0009 §5-2 (바)가 그 형식이고, 그 표가 실제로 한 건을 잡아냈다 —
  리뷰어 제안대로 조건을 갈아치웠으면 **고친 자리에서 옛 조건이 잡던 다른 경로를 잃을 뻔했다**(P13).
  즉 역방향 확인은 "새 조건이 놓치는 것"뿐 아니라 **"옛 조건이 잡던 것"** 도 물어야 한다.
- **조건을 바꾸면 그 결과를 소비하는 게이트·문구도 같은 PR 에서 확인한다.** 개정 2 의 판정은
  `if moved or merged` 게이트 뒤에 있었고, 판정만 고쳤으면 **고친 blocker 가 게이트에서 다시 조용히
  삼켜졌다**(실측). 조건절 하나를 고칠 때 "이 값을 누가 읽는가"를 끝까지 따라간다.

**규칙.** 조건절에 들어가는 **모든 한정어**(고아·새·최초·직접·해당 등)에 대해 "이 단어를 빼면 무엇이 더
들어오는가 / 이 단어 때문에 무엇이 빠지는가"를 한 번씩 답한다. 특히 **같은 문서가 이미 최악이라고 분류해
둔 경로**(위험도 표, 실패 모드 표)가 그 조건절에 걸리는지 **역방향으로** 확인한다 — 0009 는 §3 에서
병합을 "복구 불가 / 미승인 도면 위에서 착수 가능"으로 분류해 놓고 §5-2 에서 그것을 경고로 강등했다.
근거는 문서 안에 다 있었고 **결론이 근거를 따라가지 못했다.**

### 6-4. 문구 정확도를 미루면 **다음 문구가 같은 거짓을 갖고 태어난다**

- 0009 ADR §Deferred 2 초판: `document_possibly_renamed` 문구 정정을 미루면서 "§5-2 가 두 경우를
  분리하면 이 문구는 진짜 rename 에만 붙는다"고 적었다 → **그 §5-2 가 만든 새 검토요청 제목이 똑같은
  종류의 거짓을 갖고 태어났다**(고아가 아닌 것을 고아라 하고, 없는 새 `doc_id` 위에서 다시 확정하라 하고,
  0건 이동을 보고했다). 미룬 판단이 **한 사이클도 버티지 못했다.**
- 앞선 사이클: 존재한 적 없는 되돌리기 엔드포인트를 약속한 승인 다이얼로그 문구를, 웹 테스트 169건이
  **계약으로 고정**한 채 전원 통과했다.

**규칙.** 이 저장소에서 사용자에게 보이는 문구(검토요청 제목, 경고 메시지, 블로커 사유, 다이얼로그)는
장식이 아니라 **CM 이 다음 행동을 고르는 유일한 입력**이다. 부정확한 문구는 "나중에 다듬을 표현"이 아니라
**작동하지 않는 안전 장치**다. 따라서 —

1. **사실과 다른 문구는 그것을 만든 사이클이 고친다.** 문구 정정을 Deferred 로 미루는 근거로 "다음 변경이
   자연히 좁혀 준다"를 쓰지 않는다.
2. **문구가 "무엇이 일어났는가"를 여러 경위에 걸쳐 말해야 하면, 경위를 기계 판독 값으로 실어 보낸다**
   (0009 `lost_decisions[].cause`). 소비자가 **산문을 부분 문자열로 되읽어 분류하게 두지 않는다**
   (`Blocker.kind` 도입으로 이미 한 번 걷어낸 패턴이다). 모르는 값은 **모른다고 적고**, 가장 흔한 값으로
   떨어뜨리는 폴백을 두지 않는다.
3. **문구 테스트는 문장을 통째로 베끼지 말고 "그 상황에서 참일 수 없는 말이 없다"를 단언한다** — 문장을
   베끼면 거짓 문구가 계약이 된다.

### 6-5. 적용 지점

| 누가 | 언제 | 무엇을 |
|---|---|---|
| `architect` | 계획·ADR 을 쓸 때 | §6-1 생성 기준·블라인드 스팟 명시 + 한 건 실측, §6-3 한정어 역방향 확인을 **문서에 적고 실행 표로 남기기**(새로 쓴 조건절 포함, “옛 조건이 잡던 것”까지), §6-4 문구 정정을 Deferred 로 넘기지 않기 |
| `qa` | 검증 시나리오를 붙일 때 | §6-2 네 항목. 기대값이 결함 코드에서도 같은 시나리오는 **반려 사유**다 |
| `reviewer` | 머지 전 | 계획·ADR 이 §6-1·§6-3 을 지켰는지, 새 사용자 문구가 §6-4 를 지켰는지 |

**이 절을 갱신하는 규칙.** 항목을 지우지 않는다. 새 사이클에서 같은 패턴이 재발하면 근거 줄을 **추가**한다
— 재발 횟수가 그 규칙의 무게다. 새로운 종류의 반복이 두 사이클 이상에서 관측되면 항목을 추가한다.
